# Portal Development

该角色用于维护 `${code_root}` 中的 Portal 代码、执行后端和 runtime support，不代表 Portal 页面创建的业务 agent。

## 工作目录与来源

先确认当前部署形态。下述双检出、分支与发布命令只适用于已配置 Dev/Release 的 Portal 开发站。独立发行实例可以只有当前导出代码、没有 Git；按该实例实际工程规则维护，不为套用本文创建 Git 历史、远端或开发机目录。

使用 `${code_root}` 作为开发 cwd。改变行为前检查当前实现、本地注册信息和相关目录，包括 `management_portal/`、`knowledge_board_lan/`、PostgreSQL 中的资源注册表（`resource_registry`）与 Resident registry。不要根据通用 web app 模式推断 Portal 行为。

Portal 仓库只保留两个检出目录：Dev（`${code_root}`）和 Release 使用的代码目录。Release 的代码目录由发布流程维护，不要手动创建、切换或删除。所有开发直接在 Dev 中进行，不要为功能、修复、审计或回归对比建立长期存在的 git worktree。

分支同样只有两个：Dev 使用 `main`，Release 使用发布流程维护的一个分支。修改直接提交到 Dev 的 `main`；不要创建功能、修复、hotfix、审计或 review 分支，也不要向远端推送其他分支。

确实需要临时检出时（例如在改动前的提交上复现问题、对比新旧行为），按以下规则处理：

- 用 `git worktree add --detach` 创建，不为它新建分支；放在自己的 Resident Workspace 或 `${staging_root}` 下。
- 需要保留的改动先提交到 Dev，再删除这个检出。
- 用完立即运行 `git worktree remove` 删除，并在本次任务结束前用 `git worktree list` 确认它已经不在列表中。不要把临时检出留给后续任务或其他 Resident。

开始开发前从 Portal `SPEC.md` 找到任务相关的当前 Design，并读取对应的 `decision` 条目。`SPEC.md` 到当前 `decision` 条目的索引关系是 Portal 唯一的当前设计来源；模块说明、专题 Markdown 和其他文档目录不承担设计事实。

源码、配置、注册数据和测试用于核对系统现状。正式运维流程从当前 `SPEC.md` 的运维条目读取；任务记录和 Git 用于追溯实施过程。文档与实现含义不一致时，先核对运行实例和测试，再修正失真的规范或实现。

`SPEC.md` 是 Portal 唯一的当前规范索引；新增、替代或废止 Portal Decision 时必须同步更新该索引，并遵循索引中的规范治理条目，不把源站固定 ID 作为新实例的隐含依赖。

当用户对 Portal 开发 Agent 使用“请记录规范：……”或语义等价的明确指令时，将其视为 Design 登记操作，而不是普通文档记录：先检查 `SPEC.md` 与现有条目，判断应更新现有 Design 还是创建新的 `decision` 类型条目；将正文和必要的生命周期、关联或替代关系写入当前工程关联 Project 的知识库（用 `GetProject` 取得实际目录）；随后把当前有效的 ID 加入 `SPEC.md` 的适当分类，或在设计失效时移出索引。完成后向用户报告条目 ID 和索引变更。

Design 正文必须面向需要理解和修改系统的人，先讲清要解决的问题与整体模型，再说明核心对象的职责、对象之间的交互、状态所有权、关键流程、不变量、失败语义和演进边界。标题和正文使用设计对象本身作为主语，不以“决定采用”“决策结论”或时间线作为叙事骨架。不得把正文写成实现文件清单、实施计划、开发日志、测试报告、版本更新记录或方案表决记录；这些内容分别由源码、任务记录、Git、测试和历史条目承载。只有确实影响当前设计理解的取舍才保留，并应解释它如何塑造边界，而不是罗列未采用方案。

若用户所述内容实质上是一次性实施计划，应写入任务记录；若是 Portal 的现行运维步骤，应更新当前规范索引指向的运维文档 并保持 `SPEC.md` 索引有效，不另建重复的操作文档。不得为满足触发语句而创建错误类型的条目。

## 修改与验证

保留无关的 dirty worktree changes，但不要把最少文件或最小 diff 当作质量目标。修改范围必须覆盖任务所属责任边界内形成完整、统一实现所需的代码、contract、调用方、测试和文档。优先使用结构化 parser 和现有 helper API。保持 UI 行为与其他 Portal 页面一致，并根据改动运行有针对性的语法、单元、运行时或浏览器检查。

### 完整修改原则

不得把“只做窄范围补丁”“最小改动”或“先绕过问题”作为方案、实施方式或交付标准。先定位业务语义的唯一 owner 和问题根因，在权威实现中解决问题，并把变更完整传播到该职责边界内所有受影响的 contract 与调用方；不得为了少改文件而在症状位置叠加特殊分支、开关、fallback、重复 helper 或旁路实现。

同一责任边界内由本次问题暴露出的重复实现、废弃路径、临时兼容层、失效命名、死代码和过时测试必须一并清理。新实现应替换旧实现，不得让新旧路径无期限并存。确因仍然有效的外部 contract 需要迁移期时，兼容逻辑必须属于明确的迁移设计，具有唯一 owner、清晰的退出条件和覆盖迁移完成的测试，不能成为永久补丁。

彻底修改不等于无边界扩张：以职责归属和变化传播为边界，完整解决边界内的问题，同时不改动与该责任无关的代码或用户已有 worktree changes。交付前同时检查外部行为正确性和内部架构健康性，不得以测试通过掩盖重复权威、残余旧路径或结构性耦合。

### 测试预算

验证以能够发现本次改动回归的最小充分集合为准，不以测试数量或运行时长作为完成度。先按修改文件、职责 owner、共享 contract、直接调用者和关键用户路径确定受影响面，再按以下层级验证：

1. **开发迭代**：每一小批改动只运行直接相关的语法检查、单元测试或单个 Playwright 文件 / case。某项测试已经通过，并且它覆盖的源码、fixture、配置与依赖 contract 此后没有改变时，同一任务内不得重复运行。
2. **失败修复**：优先重跑失败 case 或受影响文件；不要在每次修复后立即重跑整套门禁。失败已修复且相关改动稳定后，再运行一次对应的聚合门禁。
3. **里程碑回归**：一个连贯里程碑的针对性检查通过后，至多运行一次与受影响面匹配的后端聚合门禁和一次 UI 聚合门禁。只有改动跨越共享 UI owner、多个页面或默认行为覆盖面时才运行 `npm run test:ui:behavior`；视觉、性能和 Live 测试只在本次改动直接影响对应能力时运行。

Playwright 浏览器测试负载高，会拖慢共享主机上所有人的页面和测试，包括 `tests/cases/ui` 中的界面 spec 和 TAU 实时用例。只在必要时运行：
- 改动直接影响某个页面或交互时，只运行覆盖它的 spec 文件，运行一次，使用 `--workers=1`。
- 整套界面测试和 TAU 实时用例，只在人类明确要求或本次改动直接改变对应能力时运行。
- 发布前后不把浏览器测试当作例行门禁，不因为准备发布或刚发布而运行。

聚合门禁通过后，若后续只修改了不影响其结果的文档或元数据，应复用已有结果。若修改了相关源码、fixture、配置或 contract，只重跑因此失效的检查以及最终一次相关聚合门禁。

交付时列出已运行的检查、复用的有效结果和有意未运行的门禁及原因，使测试预算可以复核。

修改 Portal 的模型调用、agent 入口、prompt、session、Execution request、shared agent 或 background agent 时，必须先读取并遵循：

- `./portal-context-injection.md`

完成 Portal 代码修改并通过定向验证后，运行 `./scripts/portal_services request-restart dev` 提交持久部署请求；浏览器重启倒计时固定为 5 秒。协调器按受影响组件激活；共同服务直接使用共同源码，同时更新两个服务池。ExecutionWorker 沿用平滑换代，不设置 Dev/Release 环境或版本准入。Source Reloader 每小时兜底检查。

已配置 Dev/Release 的开发站按当前规范索引中的部署流程运行；独立发行实例遵循自身部署规则。每完成一个功能或修复并通过定向验证，就将本次功能涉及的非共享部分及其必要依赖小批量发布到 Release，作为本次开发任务的交付步骤；不要停留在 Dev 生效，也不要等待其他功能或整轮开发结束再集中发布。用户已授权开发任务且未明确要求暂缓发布或仅修改 Dev 时，直接完成发布，无需再次请求确认。共享部分沿用上述共同源码和组件激活流程。

非共享部分通过 `./scripts/publish_portal_release --message '<说明>' --path '<路径>'` 小批量同步，路径可重复，完整同步显式使用 `--all`。不要求工作区或选中文件干净、全量测试、其他功能完成或人工版本号。功能发布默认暂存指定路径及必要依赖，全量发布执行 `git add -A`，然后在 Dev 的 `main` 上创建普通 Git commit；无变化时复用 `main` 最新的提交。发布工具随后把该 commit 推送到全部已配置远端，不强制推送；发布结果中的 `push` 记录各远端是否成功，失败时如实报告并处理后补推，不用 `--force` 覆盖远端历史。发布工具随后让 Release 唯一的分支 `release` 快进到该 commit，Release 唯一的代码目录检出这个分支；`release` 只接收 Dev 的提交，出现 Dev 没有的提交时快进失败、发布报错。允许同文件、已暂存及祖先提交中的其他改动一起发布，不增加纯净 diff 门槛。工作区中其他人或 Resident 尚未完成的改动随本次发布一起进入 Release 是正常情况：发布前不联系、询问或等待改动所属方确认完成状态，不为排除这些改动而缩小发布范围、拆分或重建提交、临时还原文件或推迟发布；这些改动在 Release 中引起的问题，由所属方在 Dev 中继续修正后再发布。暂存后的并行编辑继续保留，发布后工作区再次变脏不构成失败。共同源码、数据库、Session 与 Worker 保持共享；具备用户授权时也可直接同步两边，WALL 不是必经入口。发布后核对命令标准输出中的结果与 push、实际健康、目标功能在 Release 中的内容以及 release 分支的 commit，再向用户报告发布 commit；调用方中断后从独立 systemd 单元日志查看结果，发布工具不写发布报告或索引；发布失败时继续处理问题，并如实说明尚未生效的部分。Release 只有一份代码，没有回退命令；要撤销一次发布，在 Dev 中修正或 `git revert` 后再发布。发布不另打标签或写额外引用。

不要输出或提交 TFI Portal secrets、Codex/OpenClaw auth、SSH private keys 或 environment 中的 secret values。
