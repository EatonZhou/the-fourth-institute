# Chatroom：用户聊天室与 @ Resident 投递

Chatroom（聊天室）是用户之间的对话。成员只有用户；讨论中需要某个 Resident 参与时，任何成员在消息里写 `@resident_<12位十六进制码>`，这条消息就以发言者身份投递给那个 Resident，它的回复再显示回聊天室。聊天室因此可以随时召唤 Portal 上任何一个 Resident，而 Resident 自己的对话、上下文和执行方式都不变。

Portal 中由此有两种消息流：

| 消息流 | 归属 | 顺序的含义 | 存放 |
| --- | --- | --- | --- |
| Resident 对话 | 一个 Resident | Resident 实际看到的上下文顺序（decision_edc470e09f5a） | SocietyService 对话存储与 AgentData |
| Chatroom | 不属于任何 Principal，只有用户成员 | 聊天室收到消息的顺序 | 聊天室记录与 AgentData |

Resident 对话仍是 Resident 记忆和执行的唯一依据。被 @ 时，Resident 收到的是一次普通的 `DeliverMessage`：投递者是发言的用户，聊天室只作为业务来源出现在 `business_ref` 中。Resident 的回复留在它自己的对话里，同时显示在聊天室中。聊天室本身不是可以发消息的身份，它只是这类投递的来源。

## 基本概念

- **Chatroom**：统一资源 ID 为 `chatroom_<12位小写十六进制码>` 的讨论串，有名称、用户成员和按顺序排列的消息。私聊和多人讨论没有区别，都是聊天室。
- **成员**：在个人聊天室列表中关注这个讨论的用户，拥有自己的已读位置和提醒设置。
- **召唤**：消息正文中的 `@resident_<ID>`。一条消息最多召唤 5 个 Resident。
- **被召唤过的 Resident**：聊天室保存的召唤历史，用于候选排序、投递和回复关联。
- **投递记录**：聊天室为每次召唤保存的记录，用来把 Resident 的回复带回聊天室，并保证中断后可以继续。
- **未读数**：每位成员读到的位置之后的消息条数。

## Chatroom 面板

Chatroom 是 Society 页面左侧导航的一个面板，列出当前用户所在的聊天室：

- **置顶的聊天室排在最前，其余按最近活动从新到旧排列。** 置顶是个人设置，保存在当前用户的 UI Association（`lineage-workbench.chatrooms`，键为 Chatroom ID，值为置顶时间）；聊天室是否出现在列表中只由成员名单决定。
- **卡片显示名称、“作者：最后一条消息”、时间和未读数。** 没有名称的聊天室显示成员名称。名称独占第一行，后面只跟未读数和置顶标记；时间是次要信息，以短格式（当天 `HH:mm`，当年 `月/日`，更早 `年/月/日`）放在第二行最后一条消息之后，悬停显示完整时间，不挤占名称。
- **卡片和聊天窗口顶部的三个点共用同一份聊天室操作菜单。** 菜单提供置顶/取消置顶、消息免打扰/取消免打扰、改名、添加成员、退出聊天室；也可删除聊天室。两个入口共用菜单定义、操作处理与既有后端指令。 删除前需要确认。 添加成员和新建聊天室共用同一个用户选择器；选择器接入共享 Dialog 的 `portalDetailSurface`、标题、表单和底部操作区，不另建弹窗外壳。实色面板有视口高度约束，长成员列表可滚动，取消与确认操作保持可达；关闭、Escape 和焦点恢复由共享 Dialog 管理。
- **顶部操作入口只显示三个点。** 使用共享 Chat Workspace 的图标按钮样式，默认、悬停和菜单展开时均不显示底色或边框；保留键盘焦点提示。免打扰等动作放在菜单内。
- **状态刷新保留已展开的操作菜单。** 卡片按聊天室 ID 保留 DOM 与菜单触发按钮；消息、工作进度、未读状态和排序更新只更新变化的内容，不销毁菜单或丢失菜单焦点。菜单随触发位置重新定位，由用户选择操作、点击外部或按 Escape 关闭；聊天室被移除时关闭其菜单。弹层的定位、外部点击与 Escape 复用共享 PortalOverlay。
- **输入草稿使用共享 Chat Workspace 的草稿存储。** 聊天室只提供当前用户和聊天室的会话标识；刷新、切换聊天室、离开后重新进入时恢复未发送文本，不同聊天室和 Resident 对话之间保持隔离。不维护聊天室私有的草稿持久化逻辑。
- **面板标题栏的加号新建聊天室。** 新建时可以选择其他用户、填写可选的名称；只有自己一人的聊天室也可以创建，之后再添加成员。
- **聊天室同时是成员 User Mailbox（页面右边缘的“我的 Mailbox”，decision_15f7df737ed5）“对话”栏中的一条对话。** 它按最后一条消息的时间排序，自己或别人发言都把它提到前面；别人发言后显示未读，点击打开这个聊天室。未读只有一份：在聊天室里看过、在 Mailbox 中双击或清除未读，面板卡片和 Mailbox 一起变为已读。

选中聊天室时地址为 `/lineage?chatroom=<Chatroom ID>`；刷新页面或从外部链接进入时，页面切到 Chatroom 面板并重新打开这个聊天室。

## 聊天室中的显示与输入

选中聊天室时，聊天室覆盖在 Chat 面板之上显示，面板标题改为聊天室名称；顶部副标题像 Resident Chat 显示 resident_id 一样显示 `chatroom_id`（双击复制），后面是成员数和成员名单；下层的 Resident 对话保留自己的目标，覆盖期间不计为已读，选中任一 Resident 时聊天室收起。

聊天室就是一个 Chat Workspace 实例（decision_f560803947c6），与 Resident Chat 使用同一套消息渲染和输入框：

- **消息渲染与 Resident Chat 一致。** Markdown、资源标签（正文中的统一资源 ID，包括 `resident_<ID>`，点击后打开资源）、图片和文件附件都按 Chat Workspace 的规则显示；Resident 作者显示为资源标签。
- **只有自己的消息在右侧。** 当前用户自己的发言靠右；其他成员的发言靠左，用中性底色与自己的区分；Resident 回复和系统提示与 Resident Chat 中一样靠左。
- **右键消息可以引用回复和转发。** 有正文的消息在右键菜单中提供“引用回复”和“转发…”，与 Resident Chat 的引用回复、转发使用同一套后端；右键消息中的网页链接时，菜单同样多出“打开链接”（Chat Workspace 的通用行为）。输入框提示写明“输入 @ 提及成员或召唤 Resident；右键消息可引用、转发”；聊天室不处理 `/` 指令，没有 `/portal-help`。
  - 引用回复与 Resident 对话中的引用（decision_c524c775e0be）规则相同：输入框上方显示被引用的消息，发送时 `CreateChatroomMessage` 只给出 `quote: {message_id}`；被引用的必须是这个聊天室中有正文的消息，平台在接收时填写作者和正文开头（最多 1000 个字符），作为引用时的摘录保留；来源撤回后读取时统一遮蔽为撤回提示。消息上方显示引用块，点击跳到被引用的消息。
  - 被 @ 的 Resident 收到的消息先给出被引用的作者和摘录，再给出消息原文，与它在自己对话中收到引用回复的形式相同。
  - 转发打开与 Resident Chat 相同的转发窗口，可选择 Resident 或自己参加的聊天室并附加说明。`ForwardMessages` 的来源项给出 `resident_id` 或 `chatroom_id` 与 `message_id`，平台以转发者身份重新读取来源；目标由 `target_resident_id` 或 `target_chatroom_id` 二选一。发到聊天室时复用 `CreateChatroomMessage`，以转发者署名产生新消息，并沿用权限、长度、幂等、未读与实时更新规则。来源文字和作者作为引用保留，引用里的历史 @ 不触发提醒或召唤；附加说明中的 @ 按普通发言处理。
- **输入框可以添加附件。** 附件用 `CreateUpload` 上传，用途为 `conversation_attachment`，`target` 为聊天室 ID；发送时附件以 `{type: "image" | "file", upload_id}` 内容分段随消息保存，与 Resident 消息的内容分段相同。聊天室的读者都可以读取这些附件。
- **输入 @ 弹出聊天室成员和 Resident 候选。** 光标前的词以 `@` 开头时，输入框上方先列出“全员”，然后列出其他用户成员（头像、名称和用户名），再列出这个聊天室召唤过的 Resident（最近召唤的在前），以及发言者能发消息的其他 Resident（最近工作过的在前）；`@` 后面的文字作为关键词过滤，两组都用 `SearchResidents`（decision_d19b9909a674）读取。召唤过、但发言者没有权限发消息的 Resident 仍然列出，但不能选，并说明原因。方向键在可选项之间移动，Enter、Tab 或点击选中，选中后光标前的 `@…` 换成显示名字的提及节点和一个空格；Resident 与用户都优先显示名称，悬停显示完整 ID 或用户名，发送与草稿仍保存稳定的 `@resident_<ID>` 或 `@用户名`；Escape 关闭列表，文字和光标不变。手写 `@resident_<ID>` 仍然有效。
- **提及的显示名称与投递身份分离。** 输入框、恢复的草稿、消息正文和引用摘录优先显示 `@名称`；提及外层不增加背景色或阴影，Resident 名称保留共享资源标签的样式与点击行为；Resident 名称复用资源标签的解析与缓存，用户名称复用成员名称来源，无法解析时保留 ID。显示名称不写回消息正文，不按名称推断接收者；同名对象仍按稳定 ID 区分。输入框复制、剪切提及保留稳定标记。普通正文中的代码、链接和邮箱不改写；手写稳定 ID 与候选选择具有相同的发送含义。
- **成员候选显示用户设置的头像。** 复用消息区的用户头像组件、读取接口和缓存，支持上传图片和系统头像；没有头像时才退回姓名首字母。“全员”使用专用标记，不作为用户查询头像。头像异步加载和更换时只更新头像节点，不重建候选行、不移动输入焦点，也不改变键盘选择。
- **每个 @ 候选只占一条紧凑行。** 行高约 30px，头像、名称、不同于名称的用户名或 Resident ID、说明横向排列；相同名称不重复显示。长内容单行省略，悬停可查看完整身份和不可选原因；成员与 Resident 使用相同密度。
- **候选更新不能打断输入。** 查询等待和结果到达时保留输入焦点与光标，普通字符继续输入。候选渲染合并到浏览器下一帧，不在每个输入事件中同步重建和测量列表；方向键只更新选中行并滚动候选列表，不滚动外层对话或页面。中文输入法组合期间暂停查询和候选 DOM 更新，完成组合后按最终关键词刷新；输入法确认键不被候选菜单截获。
- **候选按查询进度显示。** 输入 `@` 后立即显示查找状态；两组查询独立返回，任一组返回即可显示和选择，另一组到达后按既定分组顺序合并、去重，并保留用户正在选择的 Resident。召唤过的 Resident 按明确 ID 定向读取。关键词连续输入时合并查询；更换关键词、关闭菜单或切换对话会取消旧查询，过期结果不能覆盖当前菜单。某组失败时保留另一组已有结果并提示重试。Escape 在加载时也可以关闭菜单；删除该 `@` 词后重新输入可以再次打开。
- **聊天室没有自己的运行状态条、队列、Stop、引用（Refs）和运行设置。** 被召唤的 Resident 的进度显示在召唤它的消息下方（见“进度显示在召唤消息下方”）；Resident 任务的撤回、停止和中间输出仍在 Resident 自己的对话中；聊天室消息的撤回不取消该任务。
- **看到聊天室时标为已读。** 聊天室在页面上可见时，页面按已展示到的位置提交已读；有尚未定位的 @ 时保留其未读状态；用户自己发言时，自己的已读位置也前进到这条消息。

## 个人免打扰与用户提及

- **消息免打扰只影响当前成员，跨设备同步。** 卡片和聊天窗口顶部的三个点菜单均可开关，持续到手动关闭。开关不发系统消息，不改变已读位置、置顶和最近活动排序；取消免打扰后已有未读恢复正常提醒。
- **普通未读在免打扰时显示灰色数量。** 聊天室卡片与 Mailbox 保留真实未读条数和静音图标，不亮红色提醒，也不计入“我的 Mailbox”入口的红色总角标。
- **直接 @ 自己的消息仍需关注。** 两个列表显示红色“@我 n”；总角标按一个需要关注的聊天室计数。打开有未读 @ 的聊天室时定位第一条并高亮，顶部“下一条 @ 我”逐条定位剩余消息。
- **@ 用户只针对发言时的其他用户成员。** 选择候选后输入框显示带名称的引用节点，发送和保存草稿使用稳定的 `@用户名`；手写完整用户名同样有效。每条消息对每位成员只计一次，自己、非成员以及代码、引用块、Markdown 链接和邮箱中的文本不产生提及。
- **@全员提醒发送时的所有其他用户成员。** 成员候选中的“全员”可按关键词筛选；选中后显示 `@全员`，正文和草稿也保存这个标记，手写同样有效。它按发送时的成员名单展开，排除发送者，后来加入的成员不会补收到旧提及；同一条消息中重复 `@全员` 或同时点名某个成员，都只给该成员计一次提醒。它沿用用户提及的正文识别、免打扰例外、红色 @我 提示、逐条定位和已读清理，不召唤 Resident、不创建额外通知，也不增加新的 ISA 或状态存储。
- **引用 Resident 的消息会再次召唤该 Resident。** 输入框自动补上显示 Resident 名称、序列化为 `@resident_<ID>` 的提及；已经出现时不重复插入。服务端同样根据被引用消息的作者补齐显式 @，使界面和 ISA 发言具有相同含义，并复用每位 Resident 一次的现有投递规则。
- **已读回执只确认这次展示到的位置。** 浏览器给出 `through`，服务端单调推进已读位置，保留之后到达的消息及 @。定位一条 @ 时确认到该条，其他未读 @ 保留；Inbox 的标为已读和清除未读仍可一次读到最新，包括灰色未读。
- **成员的个人阅读与提醒状态保存在他的 Mailbox 行中。** 每位成员在 `chatroom:<Chatroom ID>` 上有一行阅读状态（decision_15f7df737ed5）：提醒位置是聊天室最新消息的位置，读到位置是他的已读位置，另有免打扰开关和尚未读到的提及消息 ID 与位置。聊天室在自己的事务中读写这些行：新消息推进每位成员的提醒，阅读推进读到位置并清除已读到的提及，退出删除自己的行，删除聊天室删除全部成员的行；每次变化都给这一行新的修订号，聊天室接口和 Mailbox 条目返回同一个 `read_revision`。最新消息摘要保存其提及成员，以便把最新消息重新标为未读时恢复对应提醒。Mailbox 把聊天室标为已读或未读时，在房间锁内比较调用者看到的修订号，所以比较之后到达的新消息不会被一起读掉。2026-10-16 切换时，一次性迁移把原 `viewers` 表的状态带入这些行；验收后 `viewers` 表已删除。
- **聊天室读取同步共享提醒状态。** 打开侧栏时使用 `ListChatrooms`，打开或重新打开聊天室时使用 `GetChatroom`；返回的当前成员提醒字段直接更新 `PortalConversationStore`，不依赖 Mailbox 是否展开，也不为取得一间聊天室状态遍历完整会话索引。晚于已读确认返回的旧读取结果不覆盖该确认。
- **两个列表消费同一份提醒投影。** `unread_count` 表示真实未读数量；`muted` 表示当前成员开关；`unread_mentions`、`unread_mention_count` 表示待定位提及；`attention_unread` 表示是否应亮红并计入总角标。投影不为用户 @ 额外创建重复通知。
- **可见聊天目标决定标签标题。** Chatroom 覆盖 Resident 面板期间，标签始终显示聊天室名称；底层 Resident 状态刷新继续保留该名称。关闭覆盖后才显示 Resident 的标题。

## Chatroom 记录与消息

`rooms` 保存房间自身信息；`members` 保存成员关系；成员的阅读和提醒状态在 Portal UI 的 `conversation_states`，与房间记录在同一物理事务中写入；`called_residents` 与 `deliveries` 保存召唤及投递。子表均以外键关联房间，成员没有顺序列。单房间变更只读取和更新该房间的数据，个人阅读及投递更新使用各自范围的锁，不把全部聊天室读入内存后统一回写。消息仍由 AgentData 保存。绝对时间列使用 TIMESTAMPTZ，接口由所属领域转换为约定的 UTC 表示。

| 部分 | 内容 | 存放 |
| --- | --- | --- |
| 聊天室记录 | 名称、成员、最新消息位置与摘要、被召唤过的 Resident、投递记录 | PostgreSQL `chatrooms` schema；房间、成员、召唤和投递分别保存，按当前房间或具体记录进行事务更新 |
| 成员阅读状态 | 每位成员的已读位置、免打扰、未读提及和修订号 | Portal UI `conversation_states`，键 `chatroom:<Chatroom ID>`，与房间记录同一事务 |
| 消息 | 稳定消息 ID 和位置，对应不可修改的当前版本 Segment | AgentData 的 Segment，位于以 Chatroom ID 为 Agent ID 的轨迹中 |

- **消息 ID 和轨迹位置稳定，每个版本是一个不可修改的 Segment。** 编辑与撤回使用 AgentData 的当前版本替换，沿 `transformed_from` 保存旧版本，不覆盖旧 Segment。 用户发言 `role=user`；带回的 Resident 回复 `role=agent`，作者为该 Resident，`reply_to_message_id` 指向召唤它的消息；建立、改名、加入、退出、投递失败等系统提示 `role=system`、作者为 Portal 服务。消息顺序就是它在 Chatroom 轨迹中的序号（decision_b1ab45c4b3ec）。
- **文字合计最多 8000 个字符，附件最多 10 个。** 附件必须是发言者自己上传到这个聊天室、已经完成的上传。
- **用户发言可以带一个引用（`quote`）。** 引用记在消息上：被引用消息的 ID、作者和正文开头；作为该版本的引用快照保存；来源撤回时读取投影统一遮蔽摘录。
- **未读数 = 最新消息位置 − 该成员的已读位置。** 新加入的成员从头计算未读。

## 编辑、撤回、表情回应与历史搜索

- **编辑和撤回只作用于调用者自己发送的用户消息。** 菜单中的操作由服务端返回的 `can_edit`、`can_retract` 决定；服务端重新核对作者、角色和状态。两项操作必须提供当前 Segment 的 `expected_version`，冲突时拒绝覆盖。已撤回消息不能再编辑、撤回或添加回应。
- **编辑保留附件、消息 ID 和原位置，显示“已编辑”。** 使用共用多行输入对话框，不占用发消息草稿；请求失败后再次编辑保留未保存文字。编辑不产生新的未读、@ 用户提醒或 Resident 投递；移除的提及同时清除该条消息对应的旧提醒。
- **撤回隐藏正文和附件，保留“这条消息已撤回”的占位。** 最新消息预览、引用摘录和当前历史搜索统一遵守撤回状态，同时清除这条消息的表情回应。旧 Segment 保留用于版本追溯，撤回不承诺销毁已送达的副本。
- **已接受的 Resident 任务保持原版本。** 投递意图保存 `trigger_segment_id`；即使投递前用户已编辑或撤回，补发也读取该版本。编辑和撤回均不修改、重发或取消 Resident 任务；需要改变任务时另发一条消息或进入 Resident 对话处理。
- **表情回应紧贴对应消息下方，并随消息收发方向对齐。** 用户与 Resident 回复支持 👍、❤️、😂、🎉、👀、✅；回应通过 Chat Workspace 的消息底部区域呈现，与正文属于同一条消息，自发消息靠右，收到的消息与 Resident 回复靠左。多种表情在可用宽度内自动换行，已编辑标记位于回应之后，被召唤 Resident 的任务进度仍使用消息后的独立区域。消息菜单可以添加回应，点击已有回应加入或取消自己的回应，并显示人数、自己的选择和参与用户。相同消息、表情、用户只有一条回应；写入使用显式 `active`，重试不会反复切换。回应不改变正文版本、消息位置或未读数。
- **历史搜索复用 Chat Workspace 的搜索面板、分页和定位能力。** 服务端遍历本聊天室全部当前消息版本，按正文及附件名进行大小写不敏感的字面匹配，支持中文和标点。结果按时间从新到旧分页，排除已撤回消息；点击结果加载更早消息并定位到上下文，不受浏览器已加载历史限制。
- **变更同步与新消息位置分开。** `ListChatroomMessages` 返回 `change_cursor`；后续请求携带它，取得 `updated_messages`，即使变化发生在较早消息上也能更新已加载视图。变更游标单调前进，不把旧消息重新计为未读。
- **共同变更一次提交。** Chatroom 元数据、AgentData 当前消息版本及变更记录复用数据库层的跨 schema 原子事务，持有聊天室写锁；正文、提醒、预览、回应和变更游标不会部分提交。数据库层只负责事务与 schema 隔离，聊天室持有业务语义。

## 成员与权限

- 权限来自默认模板的规则（decision_600ae27b0538）：聊天室挂在 R 树“共享”下，全员对它有 viewer；创建者按创建者规则有 admin；每位当前成员按聊天室成员规则有 contributor，成员加入或退出时这条表项随之改变。管理员对它也有 admin。
- 聊天室创建、成员修改、退出和删除提交后通知权限系统更新聊天室的位置、成员与创建者事实；显式删除或最后一位成员退出时把它移出权限树。同步失败返回 `resource.mutation_post_commit_failed`、`domain_committed: true` 和聊天室 ID，业务动作已经提交，须先核对对象再恢复投影。
- **成员只有用户。** 新建或添加成员时只接受已注册、启用状态的用户；最多 50 位成员。
- **成员可以发言、改名和添加成员，创建者和管理员可以删除聊天室。** 发言（CreateChatroomMessage）和 UpdateChatroom 要求 contributor，DeleteChatroom 要求 admin，由权限系统判定（decision_b820faf42218）。名称和成员变化留下系统消息。退出只作用于调用者自己。
- **聊天室在显式删除或最后一位成员退出时删除。** 聊天室不会因为时间而过期；删除后所有调用者都无法继续读取，消息随聊天室归档。创建者退出后仍是创建者，保留删除能力。
- **读取按当前权限方案判定。** GetChatroom、ListChatroomMessages 等读取指令按目标聊天室的 viewer 要求检查；默认模板向全员授予共享聊天室的 viewer，因此默认可读不等于指令免检。具体指令要求和列表过滤以 decision_600ae27b0538、decision_b820faf42218 为准；聊天室领域保留身份、参数和对象状态校验。
- **成员、创建者与召唤历史是聊天室元数据。** 成员决定个人列表、未读和提及提醒，也是权限系统中聊天室成员规则的事实；created_by 是创建者事实；召唤历史不授予权限。解析地址与附件读取遵循聊天室的读取规则。

## @ Resident 投递

发言保存后，服务端为正文中召唤的每个 Resident 投递一次：

```text
保存聊天消息
  → 同一事务中记下投递意图（Resident、触发消息、发言者），并把该 Resident 记为被召唤过
  → 以发言者身份调用 DeliverMessage（排队；空闲时立即开始）
  → 投递记录标为已投递
```

- **投递内容是这条消息本身和聊天室 ID。** 消息开头说明是谁在哪个聊天室（名称与 Chatroom ID）中召唤了它，并提示它需要上下文时可以调用 `ListChatroomMessages` 自行读取聊天记录、回复会显示在聊天室中；随后是消息原文（带引用时先是被引用的作者和摘录），附件以同样的上传随消息送达。
- **投递由系统转交并保留发言者身份。** Chatroom 以系统入口调用 DeliverMessage，消息仍以原发言者为 caller；投递失败时显示系统消息，原聊天消息照常保存。
- **投递的业务关联是触发消息的地址。** `business_ref` 为 `<Chatroom ID>/<触发消息 ID>`，Resident 的执行终态据此回到聊天室。
- **投递意图先于投递保存，Resident 端消息 ID 由投递意图确定。** 进程在投递前后中断时，之后的读取用同一个消息 ID 和幂等键补发；Resident 不会收到两份。

### 回复显示在聊天室

- **成功时，输入状态 `reply_message_ids` 中有内容的 Agent 回复按顺序显示在聊天室**，只保留文字和附件分段，工具调用等中间过程不显示。回复同时留在 Resident 自己的对话中。
- **Resident 回复的正文上方引用当初召唤它的消息。** 引用块显示发言者、消息摘录和右侧“↑”，点击整块或键盘激活后定位并高亮原消息，必要时先加载更早历史。引用直接指向这次 @ 消息，即使该消息本身引用了另一条讨论，也不跨过它。
- **回复引用由聊天室读取投影统一生成。** `ListChatroomMessages` 根据已保存的 `reply_to_message_id`，在同一个聊天室读取原消息，并按用户引用的相同摘录规则返回 `quote`。已存在的回复同样适用，原消息不必位于当前分页；同页共享来源只读取一次。消息存储保持不可修改，来源缺失或没有正文时只显示回复正文。
- **失败或取消时，聊天室中出现一条系统提示**，说明该 Resident 未完成这次回复及原因。
- **两个入口带回回复，结果相同。** SocietyService 收到带有 Chatroom `business_ref` 的执行终态时立即带回；读取聊天室时，服务端也检查尚未完成的投递记录并补齐。带回的消息 ID 由 Resident 回复的消息 ID 确定，重复带回只得到同一条消息。
- **Resident 的回复不召唤其他 Resident。** 只有用户发言中的 @ 会投递；回复中出现的 `@resident_<ID>` 只是正文。

### 进度显示在召唤消息下方

- **Family 门面的转交不算任务完成（TFI portal 10-15）。** Chatroom 继续以门面和原输入 ID 读取 `GetInputState`；由 Family 沿已记录的转交关系（包括嵌套 Family）返回实际成员的排队、启动、运行和终态。成员仍在工作时不关闭投递，也不生成“没有回复内容”的提示；真正完成后，用同一门面的 `GetMessage` 取回最终回复，仍引用原召唤消息。成员的输入、队列和活动事件沿转交关系唤醒原聊天室；终态即使没有浏览器打开也会补齐回复，重复通知只投影一次。普通 Resident 的原有行为保持一致。

- **每个还没回复的被召唤 Resident，在召唤它的消息下方显示进度（TFI portal 10-07）。** 形式与 Family facade 请求下的进度相同（decision_44cf587c1721）：投递中显示“正在交给 X”；排队时显示“已交给 X · 排队中（前面还有 n 条）”；开始处理后先显示启动阶段（如“正在启动 Session”、等待 Worker/账号容量），运行中显示“X 运行中”和它处理这条消息的实时活动。中间输出不显示；回复带回后，进度随之消失。进度块没有撤回和停止按钮。
- **进度来自 `GetChatroom` 的 `active_deliveries`。** 每个未完成的投递记录给出 Resident、触发消息和状态：还没投递出去的是 `delivering`；已投递的以发言者身份读取 `GetInputState`（`include_progress: true`），`queued` 带前面的条数 `ahead`，`running` 带 `work_state`、`work_phase` 和 `activities`；已到终态的不再列出，回复由读取消息时带回。读不到某个 Resident 的状态时只略去它。
- **进度变化只唤醒聊天室视图。** 投递成功时，以及 SocietyService 发现 `business_ref` 指向聊天室的输入状态、队列位置、Resident 工作状态或活动发生变化时，发布聊天室投影通知（字段 `progress`），视图重新读取 `GetChatroom`。进度不是消息，不唤醒 Inbox。

## 指令

Chatroom 的读写属于 HATG ISA 公共讨论类（decision_3e063aac15b3），由 Portal Web 执行：`ListChatrooms`、`GetChatroom`、`CreateChatroom`、`UpdateChatroom`、`LeaveChatroom`、`DeleteChatroom`、`ListChatroomMessages`、`CreateChatroomMessage`、`UpdateChatroomMessage`、`RetractChatroomMessage`、`UpdateChatroomReaction`、`MarkChatroomRead`。参数、结果和错误语义见该 Design。聊天室搜索和输入历史使用对话类的 `SearchMessages`、`ListInputHistory`（decision_2fe6fd5367fb），传 `chatroom_id`；这两种形式同样由 Portal Web 执行，用 `page_token` / `next_page_token` 分页。转发聊天室消息使用对话类的 `ForwardMessages`（decision_2fe6fd5367fb）。

## 不变量

- Resident 对话只接收真实投递给它的输入；聊天室的消息只有被 @ 的那一条进入 Resident 上下文。
- 每条聊天室消息有且只有一个位置；带回的回复和 Resident 对话中的原回复是两条消息，前者引用后者。
- 同一触发消息对同一 Resident 至多产生一条 Resident 端输入。
- 当前成员通过聊天室成员规则对聊天室有 contributor；召唤记录不充当权限门槛。实际检查由权限系统按调用者自身的表项决定。聊天室不改变任何一方对其他资源的权限。

## 演进边界

- 在聊天室中新建 Resident 需要用户级 Lineage：新建的 Resident 属于该用户的个人 Lineage，并继承这位用户的权限。这部分另行设计，当前聊天室不提供新建 Resident。
- 按 Resident 职责（duty）召唤等能力应复用同一条 @ 投递路径；已有对话片段通过共享转发能力发到聊天室。
