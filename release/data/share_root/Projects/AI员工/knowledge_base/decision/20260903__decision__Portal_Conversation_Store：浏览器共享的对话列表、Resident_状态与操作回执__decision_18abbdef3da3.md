# Portal Conversation Store：浏览器共享的对话列表、Resident 状态与操作回执

Portal 的多个页面同时显示对话相关的信息：User Mailbox（页面右边缘的“我的 Mailbox”）列出用户参与的对话、发给他的通知和未读，Home 显示正在工作的 Resident，Society 页面的 Chat 显示一个 Resident 的消息和当前状态，HATG 画布在节点上显示运行状态。它们需要看到同一份事实：同一个 Resident 在各处的运行状态一致，用户刚标为已读的条目在所有入口同时变化，一个刚发出的停止请求不会被较晚到达的旧事件覆盖。

为此，每个浏览器标签页的顶层窗口中有两个共享的状态层：

- **`PortalConversationStore`（对话列表状态层）**：保存当前用户 Mailbox 中的条目、未读、置顶和清除状态。条目内容由服务端的会话索引生成（decision_15f7df737ed5）。
- **`PortalResidentProtocol`（Resident 协议状态层）**：按 Resident ID 保存每个 Resident 的消息、输入状态和运行状态，读取快照、接收事件并处理操作回执。

页面只订阅这两个状态层来显示内容，不各自维护一份缓存或运行状态。本篇说明两个状态层保存什么、怎样与服务端保持一致，以及页面怎样接入。消息与状态的服务端协议见 decision_c524c775e0be，共享刷新与变化通知见 decision_6e230393221c。

## 基本概念

| 名称 | 含义 |
| --- | --- |
| 当前用户 | 当前登录并发起读取的用户。两个状态层的缓存、未读和回执都按当前用户隔离。 |
| 身份代次 | 状态层内部的一个计数。每次切换登录用户时加一；请求发出时记下它，响应回来时代次已经变化，响应就被丢弃。 |
| 条目 | Mailbox 卡片背后的一条对话或通知摘要，字段见 decision_15f7df737ed5。 |
| 游标（cursor） | 服务端给出的只增不减的位置编号，表示一个 Resident 的对话事件已经处理到哪里。状态层用它判断一份结果是否足够新。 |
| 阅读修订号（`read_revision`） | 服务端为当前用户每个条目保存的阅读状态行（未读、置顶、清除时间）每次变化时取得的更大编号，见 decision_15f7df737ed5。列表条目、角标汇总、Resident 状态快照的 `viewer_state` 和指令结果都带着它。 |
| 删除标记 | 读取单个 Resident 的条目时，服务端明确说明它已被删除（`deleted`）或当前用户已无权访问（`forbidden`）。只有这两种结果能让状态层移除这个 Resident 的条目。 |
| 操作回执 | 发送消息、停止、调整队列这类操作被服务端接受后返回的结果，其中带有操作后的 Resident 状态和游标。 |

## 对话列表状态层

### 首次显示与后台刷新

- **页面先显示本地缓存，再用服务端结果更新。** 对话列表保存在浏览器本地存储中，页面打开时立即恢复；缓存中的“运行中”“排队”一律当作空闲恢复，当前运行状态以 Resident 协议状态层为准，还没有取得时显示为 `unknown`。
- **完整快照在当前登录身份确认后读取。** 首次身份校验会重建身份代次，校验前不启动随后必然作废的列表查询。确认身份后读取服务端快照，随后再批量补齐已加载条目的状态；离线期间的事实由快照恢复。
- **快照区分三种读取阶段。** 没有任何数据时为 `loading`（正在加载）；已有数据、用户主动刷新时为 `refreshing`；已有数据、后台同步时为 `syncing`。读取失败时已有条目继续显示，快照同时给出错误。
- **列表读取失败与实时连接断开分别处理。** 实时推送短暂断开时，重新读取列表快照核对当前内容，不直接显示“Mailbox 刷新失败”；该提示由列表或 Resident 状态的实际读取失败决定。列表快照遇到网络断开、408、429 或 5xx 时，保留已有条目，并在 1、2、4 秒后最多自动重试三次；读取成功后清除错误并重置退避。明确拒绝不自动重试，持续失败仍显示错误并允许手动刷新。切换登录用户时清除重试计数。
- **打开或主动刷新 Mailbox 同时校准列表和 Resident 状态。** 即使列表成员没有变化，也通过 Resident 协议状态层重新读取已加载成员的运行状态和当前用户未读；首次加载则共用成员订阅发起的快照读取。离线期间的完成和运行变化不依赖新事件才显示，主动刷新期间直到状态读取结束仍显示正在更新。首次状态读取失败后，重新打开或刷新可重试；错误在已有列表旁显示，不把未知状态当作空闲或已读。连续刷新共用进行中的校准，切换身份后旧校准不得影响新用户。
- **缓存订阅随 Portal 页面存活。** 页面首次加载读取列表及同一快照的全局未读摘要；Resident 未读从后台持久布尔记录读取，不通过遍历历史分页重算；Mailbox 收起只隐藏面板，不释放已加载 Resident 的状态订阅，也不跳过列表事件。没有变化时不做每分钟列表轮询；事件连接正常时每五分钟校准一次，页面恢复可见、获得焦点、连接恢复或收到 `snapshot_required` 时合并校准。隐藏页面暂停查询，恢复后补读。打开 Mailbox 仍主动校准一次，展示已有缓存。
- **事件优先定位条目。** Resident 摘要事件、按 Resident 指定的用户已读变化，以及 `agent-conversation-index` 通知中明确给出的 Resident 条目键，进入同一条有界定向读取队列；80 毫秒内同一对象的变化合并。完整运行状态事件交由 Resident 协议状态层直接应用。无法定位条目、通知类变化和 `snapshot_required` 才重新读取列表快照。重复通知不重复累计未读。
- **切换登录用户时丢弃旧用户的全部状态。** 条目、最近入口、正在进行的请求和未完成的已读操作全部作废，状态层恢复新用户自己的缓存并立即读取；旧用户的响应晚到时被丢弃。

### 完整读取与单个 Resident 的追赶

- **同时发起的完整读取共用一次请求。** 同一标签页中的多次读取合并为一个请求；不同标签页之间，500 毫秒内刚完成的同一请求直接复用结果。复用只发生在同一用户、同一身份代次内。
- **完整列表按条目键去重并保持服务端顺序。** 同一个 Resident 的多条结果保留游标最大的一条。完整列表中不再出现的条目被移除；已经观察到更新游标、正在单独追赶的 Resident 条目除外，它们不会被较早发出的完整读取删掉。
- **Resident 有了影响摘要的变化时，只读取这个 Resident 的条目。** Portal 变化通知中的 `resident_events` 列出发生变化的 Resident 和新游标。消息、摘要状态、输入终态的变化会触发读取；只影响聊天内部的事件——当前活动（`resident.activity.changed`）、等待队列（`resident.queue.changed`）和运行设置（`resident.runtime_settings.changed`）——不触发读取，下一次相关变化发生时再一并追上游标。
- **单个 Resident 的读取有并发和重试上限。** 同一个 Resident 的读取依次进行，全部 Resident 合计最多同时 6 个；等待期间来了更高的游标，只提高目标，不降低。返回结果的游标还没有追上目标时不采用，最多重试 6 次，间隔从 80 毫秒开始翻倍、最长 1 秒；6 次后改为强制读取完整列表。
- **只有删除标记能移除 Resident 条目。** 单个 Resident 的读取结果为空时，只表示没有需要更新的内容；返回 `deleted` 或 `forbidden` 时才移除这个 Resident 自身的条目，移除之后较早发出的响应也不能让它们重新出现。

### 已读、未读与清除

首批列表响应携带 `mailbox_summary`：服务端按同一份用户阅读状态行列出全局未读成员，旧页仅提供条目键、分类、阅读修订号等轻量字段，不读取其聊天历史、头像或运行状态。前端将摘要与已加载条目组成一份视图；外部角标、分类角标与行未读均由这份视图产生。后续 Resident 定向响应更新同一份成员集合。独立计数接口及其缓存不再存在。

- **每个条目只保留修订号最高的阅读状态。** 列表快照、角标汇总、单个 Resident 的读取、Resident 状态快照的 `viewer_state` 和指令结果，无论哪一份先到，状态层只接受修订号不低于手中的一份（TFI portal 2026-10-16）。修改之前发出、之后才到的快照带着较低的修订号，不能让已读的条目重新未读；真正的新提醒带着更高的修订号，从任何来源到达都会显示。角标汇总列出它那一刻的未读成员，并给出快照读到的最新修订号；汇总中缺席、而手中修订号更新的条目保留到更新的汇总到来。不再按完成签名匹配，也不以请求开始时的本地修改序号丢弃快照。
- **标记已读或未读时，未读点立即变化，服务端结果决定最终状态。** `setReadState` 记下一项进行中的修改，先显示目标状态，再调用 `MarkMailboxItemRead`，以页面看到的修订号作为 `expected_version`。服务端接受后，状态层采用结果中的状态和修订号并结束这项修改；服务端因条目之后有新提醒而拒绝时，状态层撤销显示并重新读取列表；其他失败撤销显示并报告错误。同一条目连续操作时只有最后一项进行中的修改决定显示。
- **清除以服务端处理时的条目为依据。** `clear("unread")` 或 `clear("all")` 调用 `ClearMailbox`（带当前栏 `section`）。“清除未读”点击后立即把视图中当前栏的未读条目显示为已读，不等待服务端遍历整个 Mailbox。服务端返回状态发生变化的各行（已读、修订号、清除时间），状态层采用它们；“清除全部”的条目在活动时间不晚于清除时间时隐藏，出现更晚的活动或新提醒后重新显示。请求失败时撤销显示并报告错误。
- **本地移除和清除会作废旧请求。** `discard`、`discardResident`、清除和切换用户都会取消较早的单个 Resident 重试，此后收到的新游标只能发起新的读取。

### 打开 Chat 后自动已读

- **用户在 Chat 中看到对话后，这个 Resident 的条目变为已读。** 共享 Chat 在 Resident 的消息快照显示出来之后调用 `observeResidentRead`；状态层确认观察者就是当前用户，先把本地条目显示为已读，再以条目键 `resident:<Resident ID>` 调用 `MarkMailboxItemRead`（不带 `expected_version`）。服务端核验当前用户可访问该 Resident 后，把这一行读到最新提醒，不查询历史结果；本地列表尚无该条目或摘要过时不影响这次已读。成功后状态层采用结果中的修订号并重新读取这个 Resident 的条目，失败时撤销显示。
- **自动已读只校准对应 Resident，不作废正在读取的完整列表。** 新浏览器恢复 Chat 时，即使这个 Resident 尚未出现在本地 Mailbox，也可以确认已读；其他 Resident 在离线期间完成或仍在运行的工作必须由同一次完整快照恢复。该 Resident 的已确认阅读由更高的修订号保护，旧列表响应不能使其重新未读。
- **只有看到对话才算已读。** 已读与滚动位置、最后一条消息是否进入视口无关。只是导航到 Resident、选中 HATG 节点、从详情页返回，或地址中带有 Resident ID，都不算看到；隐藏的 Chat、后台标签页也不会自动已读。以其他形式显示对话的界面（例如 Which Resident 的推荐视图）在推荐结果显示出来之后才确认已读。
- **用户主动标记已读或未读使用 `setReadState`**，与自动已读是两条独立的路径。

## Resident 协议状态层

### 运行状态只有一个来源

- **同一个 Resident 在各处显示同一份运行状态。** 是否在运行、是否排队、接单开关、排队消息数都由 Resident 协议状态层按 Resident ID 保存。Home、HATG、User Mailbox、最近 Resident 快捷入口和共享 Chat 都读取它；普通 Society 侧栏导航不显示运行状态，不从账号统计或会话索引中的旧字段推断。
- **对话列表只组合运行状态。** 对话列表输出的条目带有 `resident_state`、`resident_state_cursor` 和 `resident_state_ready`，都来自 Resident 协议状态层，不写回列表的游标。条目中最后一次结果为失败、中断或归档时，Resident 空闲期间继续显示这个结果；Resident 开始新工作时显示当前状态。
- **Resident 状态快照带有当前用户的未读。** 批量读取状态的 `ListResidentStates` 为每个 Resident 附带 `viewer_state.unread`，即当前用户对这个 Resident 的对话是否有未读结果。对话列表中这个 Resident 的条目以它为准（本地正在进行已读操作时除外）。用户的已读标记变化时，服务端发出 `resident-view-state` 变化通知；Resident 的一条输入进入终态时，状态层也重新读取状态。
- **状态订阅在同一标签页内共享。** `acquireStates` 为一组 Resident 建立订阅，复用每个 Resident 已有的状态和正在进行的读取，只读取缺少的成员；`stateSnapshot` 只读取已有状态，不发请求。页面恢复可见、获得焦点时，以及可见页面每两分钟，由状态协议统一作废已有订阅的快照并批量补读，修复漏掉的通知。最后一个订阅释放后，解除页面监听和计时器，缓存的生命周期由状态层管理。不同标签页各自读取服务端结果，通过 Portal 的变化通知保持一致。

### 人工接单与执行保护的共同投影

状态归一与显示解释由 PortalResidentProtocol 的 executionGate / executionGateView 统一负责，Chat、Family 成员表与 HATG 节点只消费同一结果，不各自按额度百分比推断状态。

- intake_state 是人工接单开关；人工关闭优先显示 CLOSED／人工关闭。执行保护读取服务端 execution_gate 的 open、closed 或 unknown 及 reason；人工打开本身不证明额度已恢复。
- 保护闭合显示 CLOSED 及已确认原因；unknown 或缺失状态显示未确认，不能当作 open。额度用尽与保护预留分别按服务端 used_up／配置阈值事实解释，不固定写成 2%；有效 override 以服务端结果为准。
- Open/Close 控件只修改人工 intake；发送是否允许仍取 controls.can_send，排队说明取后端 send_hint。闭合保护可以与允许排队发送并存。
- 服务端的对话快照、状态读取、`resident.state.changed` 事件补读和带 `state` 的操作回执使用同一执行保护与 `controls` 投影。每次响应的提示依据本次观测的 `execution_gate`；事件补读保留各事件原有的工作状态、人工接单状态及游标，不把当前额度观测写回历史事件。执行服务不可达仍返回 `unknown` 和明确原因，不能用空提示表示已经恢复。
- 事件或操作回执没有 execution_gate 时保留此前确认的保护信息；不能因缺字段清成开放。正式批量状态刷新可以独立于对话游标更新执行保护与发送提示；同游标或更旧对话位置不妨碍采用这次保护观测，其余工作状态与权限仍受原游标顺序约束。
- 未确认恢复、停用账号与服务不可达按各自原因呈现；不能从历史取消记录反推额度导致取消。

### 消息快照与事件补读

- **首次打开时读取快照，之后按游标连续接收事件。** 状态层用 `GetConversation` 读取一个 Resident 的对话快照（默认最近 200 条消息），用 `WatchConversationEvents` 读取之后的事件；更早的消息用 `ListMessages` 按页读取。重复的游标跳过，消息按消息 ID 更新。缓存记录已请求的历史容量；新的读取需要更多历史时重新取得快照，不复用只含少量历史的状态观察快照。
- **事件有缺口时自动补齐。** 通知跳过了游标，或只说明“有变化”而没有带上内容时，状态层从最后连续的游标开始补读事件；补读仍有缺口、只返回部分内容，或返回空页而服务端游标更大时，直接重新读取快照并继续显示。用户不需要刷新页面。
- **暂时的读取失败自动恢复。** 补读或快照读取遇到网络断开、408、429 或 5xx 时，保留已有内容，从 1 秒开始按倍数退避重试，最长间隔 10 秒，没有新通知也继续恢复；读取成功后退避清零。403、404 这类确定的错误直接作为错误显示。最后一个消息订阅释放时，取消重试并作废正在进行的读取。
- **切换登录用户时清空全部 Resident 的状态。** 旧用户的消息、状态、回执和重试全部清除，正在进行的请求不再复用，再为新用户读取快照。旧用户的成功响应、失败响应和停止回执都不能改动新用户的界面。

### 对话游标与状态游标分开前进

同一条有序的 Resident 事件流同时更新对话和运行状态，两者各自记录处理到的位置：

- **对话游标只在事件连续到达或补齐后前进。**
- **状态游标可以单独前进。** 状态只从 `resident.state.changed` 事件和完整的状态快照、操作回执中更新，跳过与状态无关的事件，不为填补这些事件去读取聊天历史。新的完整状态同时替换运行状态和可用操作（`controls`，例如能否发送、能否停止）；它可以推进状态游标，但不会让对话游标越过还没收到的事件。较旧的快照、回执或事件不能让工作状态与权限倒退；正式读取的执行保护观测按上节的独立刷新规则采用。
- **不完整的状态通知只当作“需要补读”。** 通知省略了内容，或缺少 `controls` 及其字段时，状态层只记下 Resident ID 和游标，重新读取完整的状态与可用操作后一次性更新；补读期间保留最后确认的状态和草稿，不把缺少字段理解为权限被撤销。服务端明确返回 `can_send=false` 时，界面按它禁用发送并显示原因。首次加载还没有取得可用操作时，输入框保持不可发送。

### 操作回执与事件的先后顺序

操作的回执和实时事件可能以任意顺序到达，Resident 协议状态层统一处理，页面不另建规则：

- **回执先到时，按回执的游标暂存操作后的状态。** 暂存内容包括运行状态、可用操作、输入状态、等待队列和输入消息，较旧的事件或正在进行的快照读取不能把它们退回操作之前。
- **回执不推进对话游标。** 中间的消息仍按连续事件补齐。事件追上回执的游标后，释放暂存的内容；较旧的回执不能覆盖已经处理过的更新终态。

例如，停止的回执比消息事件先到时，界面立即显示“正在停止”，之后连续事件补齐；“立即发送”的回执晚到时，也不能覆盖已经确认的输入终态。

### Resident 的即时发送与待确认消息

用户点击发送时，协议状态层按消息 ID 保存一份本地提交，并立即通知同一标签页内订阅该 Resident 的所有 Chat。Chat 显示“发送中…”气泡，输入框清空且继续可用。正文、图片顺序、附件、引用和提交时的目标均固定；后续草稿、附件和焦点不受旧回执影响。这份本地记录独立于服务端消息、队列、运行状态和游标，不能作为已受理或有权限的证据。

- 同一 Resident 的提交按点击顺序受理；异步准备业务上下文也在这个顺序内。前一条得到受理事实或明确拒绝后再提交下一条，输入框始终允许编辑和继续发送。
- 消息、输入状态、队列、回执与事件按同一消息 ID 对齐。正式消息出现时替换临时显示，只保留一条；服务端确认在队列中时移除临时气泡，显示服务端队列项。回执和事件先后到达都遵守原有游标规则。
- 403 等明确拒绝保留气泡并在下方显示错误，可移除或显式重试。重试复用原消息 ID 和已准备好的内容，不重新追加上下文，也不覆盖新草稿。
- 断线、超时或 5xx 无法证明请求未被受理，显示“正在确认发送状态”。有 Chat 订阅时每两秒查询原消息 ID，也可手动检查；只有匹配的服务端事实才确认。查询失败或暂未找到不自动重发。结果不确定时后续本地提交等待确认，输入框继续可用。
- 本地提交只保存在当前标签页内存中，重新打开同一 Resident 时继续显示；刷新或关闭标签页后仅恢复服务端已经保存的事实。切换登录身份时清空全部本地提交和查询计时器，未发出的旧身份提交不再发出，迟到结果不进入新身份的界面。

`sendInput(payload, { prepare, preview })` 负责上述提交；`retrySubmission`、`dismissSubmission` 和 `checkSubmissions` 分别用于明确失败后的重试、移除和查询。宿主只提供业务上下文准备回调与展示内容，不另建发送队列或重试规则。

### 会话重启请求的确认

重启是独立的 ResidentRuntimeController → PortalResidentService 流程，不由 Conversation Store 或 ResidentProtocol 再建状态机。四入口与保存刷新规则见 decision_8b2fa224616b；迁移状态、取消和服务端受理规则见 decision_c47a13e8b962。浏览器客户端的待确认记录与观察合同归入 decision_8b2fa224616b 的“重启客户端观察”，各 Chat 只订阅并呈现。

## 公开接口

### 对话列表状态层

`PortalConversationStore` 在顶层窗口中只有一个，按当前用户工作，没有 `destroy`。

| 方法 | 作用 |
| --- | --- |
| `snapshot()` | 返回当前快照。 |
| `subscribe(listener, options)` | 订阅快照变化；默认立即回调一次，返回取消订阅的函数。 |
| `refresh(options)` | 读取列表快照；`force: true` 在页面隐藏等情况下也读取，`foreground: true` 同时校准已加载 Resident 的运行状态和用户未读，并显示为用户主动刷新。 |
| `loadMore()` | 读取下一页条目。 |
| `refreshResident(residentId, wantedCursor)` | 读取一个 Resident 的条目，直到追上给定游标。 |
| `entry(key)` / `entries()` | 读取一个条目或当前全部条目（已合入 Resident 状态）。 |
| `isUnread(key)` | 查询条目是否未读。 |
| `discard(key)` / `discardResident(residentId)` | 在本地移除一个条目，或一个 Resident 自身的全部条目。 |
| `setReadState(keyOrEntry, unread)` | 用户主动标为已读或未读。 |
| `markRead(key)` | 用户主动标为已读的便捷入口；页面不因导航、地址变化或从详情返回而调用它。 |
| `observeResidentRead({ residentId, actor })` | 共享 Chat 显示出对话后调用，见“打开 Chat 后自动已读”。 |
| `clear(mode)` | 清除，`mode` 为 `"unread"` 或 `"all"`。 |
| `remember(entry)` / `recent()` / `dismissRecent(key)` / `clearRecent()` / `restoreRecent(entries)` | 管理当前设备上的“最近打开”列表，最多 32 项，不影响服务端的列表。 |

快照包含：`entries`、`recent`、`unreadCount`（包括未加载页的全局提醒未读数）、`sections`（本栏已加载条目数与全局提醒未读数）、`nextPageToken`、`loadingMore`、`paged`、`loaded`、`ready`、`loading`、`refreshing`、`syncing`、`clearing`、`error` 和 `revision`。`revision` 只是浏览器端的变化序号，与服务端的游标无关。快照中没有聊天正文。

### Resident 协议状态层

`PortalResidentProtocol` 提供：`acquire`（订阅一个 Resident 的消息与状态）、`acquireStates`（订阅一组 Resident 的状态）、`stateSnapshot`、`stateView`、`loadSnapshot`、`watchInputState`（观察一条输入的处理进度），以及发送与控制操作 `sendInput`、`injectInput`、`cancelTurn`、`cancelQueueItem`、`clearQueue`、`respondUserInput`、`searchMessages` 和 `invalidateViewerState`。发送与控制操作通过 `PortalResidentService` 调用对应的 HATG ISA 指令（decision_2fe6fd5367fb、decision_2a3ff353165c），回执按上文规则合入状态。

## 实现说明

### 本地缓存

对话列表的缓存键为 `tfi.portal.conversations.v7:<用户>`，保存前 50 个条目（带各自的阅读修订号）、列表内容签名和时间；格式版本不是 7 时不恢复。恢复的条目按修订号进入状态层，之后到达的较旧状态同样被忽略。“最近打开”列表使用独立的键 `tfi.portal.conversations.recent.v1:<用户>`。

### 一次读取怎样被采用

完整读取发出前，状态层记下身份代次和作废边界。共享读取器先按当前用户和身份代次隔离请求，同名请求不会让新用户等待旧用户的请求，也不会接收其他用户在其他标签页中广播的结果；身份或权限变化同时作废共享读取器和状态层中的旧工作（decision_6e230393221c）。响应回来后，状态层核对身份代次，变化时丢弃这份响应；核对通过后按条目键合并、排序，各条目的阅读状态按修订号取舍，再通知订阅者。这样，缓存可以让页面快速显示，较慢的旧请求也不会覆盖用户刚完成的已读、置顶、清除或身份切换。

单个 Resident 的读取记下事件游标、条目游标、目标游标和作废序号。响应先核对身份与作废序号，再核对游标是否追上；没追上就按上文的次数与间隔重试，追上后才合并条目或应用删除标记。一个读取结束后，状态层继续处理期间积累的完整读取或更高的游标。

### 各部分的职责

| 部分 | 负责 |
| --- | --- |
| 服务端会话索引 | 哪些条目可见、条目内容、排序依据、签名和未读（decision_15f7df737ed5）。 |
| 对话列表状态层 | 浏览器缓存、请求合并、单个 Resident 的追赶，以及已读和清除操作的并发保护。 |
| Resident 协议状态层 | 每个 Resident 的消息、输入状态、运行状态和可用操作，以及事件补读和回执处理。 |
| 页面 | 何时显示、何时要求强制刷新，以及怎样显示 `loading`、`refreshing` 和 `error`。 |

页面订阅快照来显示列表、角标、加载状态和错误，通过公开方法发起刷新和操作，不复制游标、删除标记或操作编号。User Mailbox 面板负责卡片与交互，Agent Console 负责把一个条目定位到对话，两者都不从对话列表状态层读取聊天正文。用户能看到什么始终由服务端按当前用户判断；本地缓存中有某个条目，或本地移除了某个条目，都不改变用户的权限。

## 聊天室的未读与提醒

Conversation Store 保留聊天室提供的真实 `unread_count`、个人 `muted`、待定位的 `unread_mentions` 与数量，以及 `attention_unread`。`unreadCount` 统计需要亮红提醒的条目，普通静音未读仍保留在条目中供灰色计数和清除操作使用。浏览器观察聊天室时提交实际展示位置 `through`，回执更新剩余未读和提及，旧请求不能读掉后续消息。卡片与 Mailbox 共享这一份投影。

最近快捷记录统一使用 `resident_id`、`lineage_id`、`title` 和时间戳 `t`，以 `resident:<resident_id>` 为键。浏览器旧格式记录在读取时丢弃并保存整理后的列表。状态投影只读取已读操作，已确认操作的清理在共享 Store 发出更新之前完成。

## 状态与活动分页的读取边界

需要未读状态的 Mailbox 订阅仍读取 `ListResidentStates` 的 `viewer_state`；同一浏览器中状态-only 请求先完成时，Mailbox 补取缺失的未读投影。Resident 状态协议在页面恢复可见或获得焦点时校准已有订阅，并在可见页面每两分钟校准一次，以补偿漏掉的实时事件；没有订阅时释放监听与计时器。会话摘要缓存应容纳正常的大批量成员读取，避免批量规模超过缓存容量时每次都重扫 Trace。

全站 User Mailbox 的活动分页在 SocietyService 的专用读池中执行，不占用打开 Resident 所用的普通读池；指定单个 Resident 的活动读取使用普通读池，不被全站分页阻塞。活动 SQL 分别从实际消息 Segment 和通知 Operation 读取候选，发给用户的通知先经已有的部分索引筛选，再按 Trace 位置及上下文重置位置计算可见活动；不得为筛选活动而把全部通知投影并入每次消息扫描。
