# Portal Refresh Coordinator 的刷新协调、事件订阅与共享读取

Portal 中的列表、状态摘要和详情需要持续反映服务端的变化。`PortalRefreshCoordinator` 是浏览器端的公共 JavaScript 模块，帮助页面安排读取、合并重复请求，并在切换对象后丢弃旧结果。它不负责业务接口或界面布局。

各页面共用这份模块代码，每份需要独立更新的内容创建自己的协调器实例。一个实例可以负责整个列表，也可以负责当前选中的详情。各实例分别维护读取状态和刷新安排，并通过 `PortalEvents` 共享全站事件连接，无需为每个区域单独建立连接。

## 基本概念

| 名称 | 在 Portal 中的含义 |
|---|---|
| 刷新目标 | 需要持续更新的一份内容，例如当前打开的文件或一个列表。 |
| 目标键 `key` | 标识当前读取对象的字符串。对象或查询范围改变后，页面用新的键启动协调器。 |
| 快照 | 一次读取返回的完整结果。协调器不解释其中的业务字段。 |
| 读取函数 `fetch` | 页面提供的取数函数，返回快照或一个等待快照的 Promise。 |
| 应用函数 `apply` | 页面提供的处理函数，收到仍属于当前目标的快照后更新状态和界面。 |
| 失效通知 `invalidate` | 表示现有内容可能已经过时，需要安排一次读取；通知本身不包含新的业务结果。 |
| 运行代次 | 协调器每次重新启动或切换目标时使用的新编号。即使两次打开的对象相同，也能分辨上一次打开时发出的请求。 |
| 尾随读取 | 当前读取结束后再执行的一次读取，用于处理读取期间收到的变更通知或手动刷新。 |
| 事件订阅 | 接收服务端变化提示的方式。`PortalEvents` 发布浏览器窗口事件，协调器的适配器从中筛选与目标有关的变化。 |
| 共享读取器 | 在同一页面或不同标签页之间复用相同请求和近期结果的工具，不负责页面更新。 |

## 设计点

- **同一目标的快照读取由一个实例安排。** 首次加载、变更通知、手动刷新、轮询和延迟重试都进入这个实例；各目标仍可选择不同的间隔和事件范围。
- **事件先通知，再读取。** 页面说明哪些事件与自己有关，适配器将它们转为失效通知。读取和结果应用经过协调器，与手动刷新共用并发控制。
- **Resident 详情事件按可见兴趣订阅。** Chat、Resident 状态或其他需要单个 Resident 细节的消费者通过 `watchResident(resident_id)` 登记引用计数；基础事件流仍只包含公共领域变化。最后一个消费者释放、页面隐藏或 frame 真正卸载后，对应 Resident 不再进入订阅 URL。
- **读取期间的新变化仍会得到处理。** 普通并发刷新等待正在进行的请求；变更通知会留下一个待刷新标记，前一次请求结束后再读一次。连续通知合并处理。
- **后台页面默认暂停自动读取。** 标签页隐藏时取消待执行的自动读取，记录这期间的变化；重新可见后合并读取最新内容。显式强制刷新和选择后台运行的目标另行处理。
- **旧页面状态不被迟到结果覆盖。** 停止、重新启动或切换目标后，旧请求不再进入应用函数。页面重新打开相同对象也遵循这项检查。
- **读取失败之后仍可继续更新。** 一次网络失败或读取函数立即抛出的错误不会中断后续调度。页面可为尚未准备好的数据或临时错误安排延迟再读。
- **连接故障与数据读取分别处理。** 事件订阅失效时回到轮询，并有限次尝试重新订阅；正常连接期间可用低频读取校准漏掉的变化。
- **自动校准与手动强制更新分开。** 自动校准是普通读取；由用户要求绕过业务缓存或重新采集时，页面通过 `force` 决定是否执行对应操作。
- **数据未变时保留现有界面。** 应用函数比较真正参与展示的内容，只更新发生变化的部分。协调器不强制重画列表，也不设置滚动位置。
- **共享结果仍考虑新鲜程度。** 同时读取相同内容的调用方可共用结果；由新事件触发的读取可以要求结果产生于指定时间之后，避免短时缓存遮住新变化。

## 组件怎样协作

```text
服务端 /api/events
       |
       v
PortalEvents：连接、广播、向同源内嵌页面转发
       |
       v
portalSubscription：按目标筛选事件，发出 invalidate
       |
       v
协调器实例 <--- 首次加载 / 手动刷新 / 轮询 / 延迟再读
       |
       +-- fetch --> 可选的共享读取器 --> 业务接口
       |
       +-- 检查目标键和运行代次
       |
       +-- apply --> 页面状态 --> 有变化的 DOM
```

`PortalEvents` 管连接，`portalSubscription` 管事件匹配，协调器管读取时序，页面管数据解释和展示。事件适配器没有自己的读取函数或防抖计时器；它把防抖延迟交给协调器的同一条调度路径。一个目标停止时，只释放自己的监听和请求状态，不关闭其他目标共用的事件连接。

## 一次读取与后续变化

`create(options)` 创建停止状态的实例。`start()` 取得当前目标键，尝试订阅，并在没有可用订阅时按 `initialDelay` 安排轮询。需要立即得到首份数据的页面在启动后调用 `refresh()`；需要延迟首读的页面调用 `invalidate({delay})`。事件适配器也可在接入已经连接的事件客户端时要求首读。

同一目标已在读取、等待轮询或等待重连时，再次调用 `start()` 会保留这些安排。页面可以在确认目标仍需更新时重复调用它，而不提前重试或重新计算连接重试次数。

实例保存当前读取 Promise。同一时刻的普通 `refresh()` 复用它，而不是再启动一个请求。读取期间收到的 `invalidate()` 设置一个待刷新标记；请求完成后，标记使协调器安排一次尾随读取。多个 `refresh({force: true})` 同样合并成一个尾随 Promise，调用方可以等待那次强制读取完成。

```text
读取 A 开始 ------ A 返回并应用 ------ 读取 B 开始
      |       |                           |
    变化 1  变化 2                         取得最新内容
      \_______/                           |
       一个待刷新标记 --------------------+
```

读取通过 Promise 链调用页面函数。因此，函数立即抛错和网络请求稍后失败都会进入相同的错误与收尾路径。收尾先处理待刷新标记，再考虑页面给出的 `nextDelay(result, error)`，最后安排普通轮询。`nextDelay` 返回毫秒数时表示还需要一次延迟读取，返回 `null` 时回到通常安排。等待后端生成首份数据、临时失败退避可使用这条路径。

已经排定的延迟读取保留原定触发时间。事件订阅断开、自动重连或显式 `reconnect()` 均不得取消这次读取，也不得用立即轮询绕过失败退避；页面隐藏时仍按可见性规则暂停，恢复后合并处理。这样即使事件连接和快照请求同时失败，快照读取仍会在约定时间重试。

读取和应用是两个阶段。页面的 `fetch` 返回内容，`apply` 更新页面；把取数与改写 DOM 混在一个读取函数里，会绕过协调器在应用前的检查。异步应用函数如果在内部等待其他操作，也可以在等待后调用 `context.isCurrent()`，确认目标仍有效。

## 切换对象与页面可见性

实例保存目标键与运行代次。`stop()`、从停止状态重新 `start()`、以新键 `start()` 都会使旧代次失效。每次读取得到的上下文包含 `key`、`force`、`signal` 和 `isCurrent()`；响应进入 `apply` 前，同时检查实例仍在运行、键仍相同、代次仍有效。

读取函数实际开始执行前也会检查运行代次，已排入 Promise 队列、但尚未开始的旧读取会直接结束。停止或切换时还会向读取的 `AbortSignal` 发出取消通知。读取函数可以把它传给网络请求；没有接入取消信号的请求可能继续完成，但其结果仍被代次检查挡住。新目标无需等待它结束。`destroy()` 进一步移除页面可见性监听，之后该实例不再启动。

默认情况下，标签页隐藏会取消自动轮询与校准计时器，保留已有事件订阅。隐藏期间收到的失效通知只留下待刷新标记；已经发出的普通读取返回时，结果暂存而不应用。恢复可见后，有变更通知就读最新内容，没有通知就应用暂存结果。新的读取开始时清除旧暂存结果，避免之后把旧内容重新应用。

对于直接推送结果的订阅，协调器逐条调用应用函数，并在每次调用前检查页面可见性。页面在异步应用期间隐藏时，已经开始的应用继续完成，尚未开始的更新留到恢复可见后处理。

`pauseWhenHidden: false` 用于确有后台读取需求的目标；`disconnectWhenHidden: true` 使隐藏时释放该实例的订阅。默认保留订阅的目标不会仅因切回前台就重新读取和重画。没有订阅、依赖轮询的目标恢复可见时恢复轮询。

## 事件匹配、轮询与校准

`portalSubscription(options)` 把四类窗口事件交给协调器：

- `portal:change`：先检查 `matches(detail)`，再检查 `domains`。要求完整快照、未设置域筛选，或变化域与筛选相交时，发出失效通知。
- `portal:events-open`：报告连接已经开放。
- `portal:events-ready`：报告开放；除非 `snapshot_required` 明确为 `false`，同时要求刷新。
- `portal:events-error`：报告连接错误，由协调器的重连预算决定是否继续尝试。

订阅到已连接的客户端时，默认报告开放并要求刷新；`refreshOnAttach: false` 可用于已有独立首读的目标。默认事件防抖为 100 毫秒，通过 `invalidate({delay})` 实现。匹配具体的数据变更时，页面可以只设置 `matches`；同一份数据的变更可能附在不同领域的事件上，过窄的域筛选会漏掉它。

没有订阅时，实例按 `interval` 轮询，默认 2,000 毫秒、下限 250 毫秒。`interval: false` 关闭周期读取，保留显式刷新和失效通知；`shouldRefresh()` 可限制普通轮询是否还需要继续。`initialDelay` 为首次轮询的延迟，默认 0。

订阅未在 `streamConnectTimeout` 内报告开放或更新时回到轮询；默认等待 3,000 毫秒，下限 250 毫秒。连接错误后的重订阅默认间隔 5,000 毫秒、下限 1,000 毫秒，最多尝试 3 次，可配置为 0 至 10 次。预算耗尽只报告一次 `onFatal`，轮询仍可继续。显式 `reconnect()` 重置预算。预算耗尽后保留轻量的 `portal:events-ready` 监听，连接恢复时重新接入事件订阅；实例销毁时释放该监听。

每次订阅还有独立的代次检查。订阅函数可能在返回清理函数之前立即报告失败，或使当前目标停止；协调器在接收返回值时再次检查该订阅是否仍有效，失效时立即调用清理函数，保留故障回调已经安排的轮询和重试。

连接正常时暂停周期轮询，默认每 300,000 毫秒进行一次普通校准读取，下限 120,000 毫秒。`repairInterval: false` 可关闭校准。它与 `nextDelay` 安排的后续读取不同：前者用于偶尔校准，后者用于明确知道尚未取得可用结果的情况。

## 服务端读取与浏览器协调的边界

协调器接受业务读取函数的结果，不要求各服务采用同一种缓存策略，也不把旧结果解释为最新业务状态。当前 Agent 状态摘要直接读取状态后端；定时与自动触发面板使用后台快照，首份快照未完成时可以返回 `loaded=false`；Conversation 的定向查询直接读取，一般列表的短时缓存过期后不返回旧快照。

Home 各区域的采集与展示职责见 decision_00546e28e1e0，Conversation 列表的查询与已读处理见 decision_15f7df737ed5。服务端缓存和失效由各业务提供方负责；浏览器的去重、代次检查、可见性和尾随读取统一遵循本 Design。

## 页面接入与职责范围

Home 的 Notice 和运行状态、会话索引、Resident 侧栏、Lineage 面板、Watchboard、文件 Preview 和 Article Git 均可按独立目标接入。用户名、对象 ID 或查询范围参与目标键时，页面先取得这些条件再启动；切换或离开对应视图时停止旧实例。

协调器是否发出读取，与页面是否改写 DOM 是不同的问题。列表和摘要可以比较参与显示的数据或渲染结果；内容相同时保留原节点，因此文字选中、焦点和滚动位置不会被无变化刷新打断。对象删除、筛选范围变化和真实新内容则由页面自己的应用函数处理。

终端字节流、按消息游标追赶的增量读取、编辑保存防抖和界面倒计时各有独立含义。它们不被改造成完整快照轮询；如果其中另有一份需要定期校准的摘要，可单独交给协调器。

## 主要调用方式

| 调用 | 行为 |
|---|---|
| `start()` | 启动当前目标；相同目标已有请求、计时器或订阅时复用现有工作。 |
| `refresh({force})` | 读取并等待结果应用。普通并发请求复用当前读取；强制请求可排一个尾随读取。 |
| `invalidate({delay})` | 标记内容可能过时，合并安排一次读取；隐藏时暂存。 |
| `isRefreshing()` | 返回是否正在读取或应用读取结果，可用于按钮状态。 |
| `stop()` | 使当前代次失效，取消计时器、释放订阅并发出取消信号；之后可重新启动。 |
| `destroy()` | 停止并释放可见性监听，结束实例生命周期。 |
| `reconnect()` | 重置重连预算并尝试重新订阅。 |

自定义订阅还可通过 `onUpdate(result)` 直接提供快照，或通过 `onInvalidate({delay})` 要求读取。直接推送的待应用快照只保留最新一份；事件适配器使用后者。页面通过 `onError(error)` 展示局部错误，显式 `refresh()` 也会把当前请求的错误返回调用方。

## 全站连接与共享读取

共享读取器的 `fetch` 还接受 `freshAfter`，表示调用方可接受的最早请求开始时间，单位为 Unix 毫秒。缓存时间早于它时会重新读取。由变更通知触发的会话索引读取使用本次读取的开始时间；同一 actor 的其他标签页在这一时间之后取得的结果仍可复用。

共享读取器统一按通道、当前 actor 和业务请求键隔离缓存与进行中请求。actor 由 `PortalIdentity.username()` 提供，业务调用者只描述对象和查询条件。身份尚未取得时只允许当前文档内去重，不发送或接收跨标签页结果。缓存隔离不替代服务端鉴权，业务读取仍须使用当前身份的正式接口。

身份变更通知同时使现有缓存、等待中的锁请求和进行中读取失效；同一个用户名收到新的身份或权限通知也建立新代次。旧读取可以在传输层继续结束，但不再调用尚未开始的取数函数、写入缓存、广播或返回可应用的结果。没有可用结果时返回 `undefined`，业务调用方继续使用所属协调器的目标检查，不能把旧结果重新归到新身份。


### 全站事件客户端

- 顶层页面自动连接 `/api/events?domains=execution,resource,resident,lineage,projection`。EventSource 的 open、`portal-ready` 和 `portal-change` 分别发布为 `portal:events-open`、`portal:events-ready` 和 `portal:change`；无效 ready 数据按空对象处理，重建连接后的 ready 带 `reconnected: true`。
- 心跳和业务消息都会刷新最后活动时间。连接 30 秒没有信号时发布原因 `stale_stream` 的错误；每 5 秒运行的看门狗关闭并重建静默连接。
- EventSource 原生错误会发布当前重试次数，同时保留浏览器自身重试。`retry()` 清零重试状态并重建；`close()` 或 `pagehide` 关闭连接并停止协调。
- 同时支持 `BroadcastChannel` 和 Web Locks 时，一个可见顶层标签页持有 EventSource。领导标签页向 `tfi-portal-events` 广播状态和事件；跟随标签页忽略自己的广播，领导标签页忽略回送，避免环路和重复分发。缺少共享能力时，每个顶层标签页独立连接。
- 同源 iframe 把 `connect()`、`close()`、`isConnected()`、`isLeader()`、`retry()` 和 `watchResident()` 委托给顶层窗口，并接收顶层转发的四类事件。frame 为自己登记的兴趣负责；真正卸载时释放，进入浏览器前进后退缓存时保留，并在恢复后继续使用。跨源访问失败时不代理。
- `watchResident(resident_id)` 要求非空 Resident ID，并返回幂等释放函数。同一文档对同一 Resident 的多个消费者按引用计数合并；默认 EventSource URL 不附带 `resident_ids`，只有当前可见文档的有效兴趣才加入该参数。
- 共享领导模式把各可见标签页发布的 Resident 兴趣求并集，由领导标签页重建唯一 EventSource。兴趣广播每 10 秒续租，45 秒没有续租的 peer 会被清除；隐藏页面立即发布空兴趣。兴趣变化以 150 毫秒合并，旧 EventSource 的迟到 open、ready、change、heartbeat 或 error 不得改变当前连接状态。

### 共享读取器

- `PortalRefreshCoordinator.createSharedFetcher(channelName)` 默认使用 `tfi-portal-refresh`。同一文档中的同名通道返回同一实例；空键直接调用读取函数，不使用缓存、锁或去重。
- 返回实例提供 `fetch(key, fetcher, options)`。同一标签页、同一 actor 和身份代次内的同键进行中请求共享一个 Promise；请求收尾只清理自己的记录，不能删除较新请求。
- `maxAgeMs` 默认 0，下限 0；缓存值为 `undefined` 时视为未命中。
- 浏览器支持 Web Locks 且已有 actor 时，锁名由通道、actor 和请求键的无歧义编码共同组成。取得锁后等待 25 毫秒，再检查运行代次和其他标签页广播的结果，以默认 1,500 毫秒且不小于 `maxAgeMs` 的窗口复用新结果。
- 缺少 Web Locks 时仍保留标签页内 Promise 去重，并可从 BroadcastChannel 机会性接收缓存。`refresh-result` 携带 actor、非空请求键、结果与有限数值的 `fetchedAt`；仅接受当前 actor 的结果。早于本地身份失效时刻或当前缓存时间的广播被丢弃，旧广播不能倒退缓存。成功且仍有效的读取才更新缓存并广播可克隆结果。`fetchedAt` 记录请求开始时间，变更发生前已开始的读取不会因完成较晚而被当作变更后的结果。
