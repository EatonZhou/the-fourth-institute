# Resident 聊天中的提问、审批与本轮修改卡片

Resident 工作时，除了用文字回复，还会遇到需要用户参与或值得单独展示的时刻：它想让用户在几个选项中做选择，Provider 需要用户批准一条命令或一次文件修改，或者这一轮它制定了计划、改了代码或知识库。Portal 在聊天消息中用**卡片**呈现这些内容，用户可以直接在卡片上回答、批准、查看改动或发起审查；等待回答的问题在提出它们的消息中逐题作答。

本 Design 说明有哪些卡片、它们怎样出现、用户的回答怎样回到正确的地方，以及卡片内容保存在哪里。聊天区域本身见 decision_f560803947c6；消息、输入与队列协议见 decision_c524c775e0be。

## 基本概念

- **Segment**：Resident 会话中不可修改的一段内容，如一条模型回复、一次工具调用或一次工具结果。卡片的内容保存在 Segment 中，刷新页面后从 Segment 重新显示。
- **Provider 适配器**：Portal 中负责和各 Provider 程序对话的部分。本篇的原生提问、审批与 MCP 请求由 Codex 适配器接入，并关联对应 Execution、线程和轮次；消息问题组及其他 Provider 的工具调用修改卡片按各自来源处理。
- **原生请求**：Provider 在一轮工作中途向用户发出、并等待回复的请求，如提问、审批和 MCP 补充信息。每个原生请求有 Provider 给出的请求 ID，答案必须通过原连接返回给这个请求。
- **阻塞与非阻塞**：阻塞请求让这一轮停下等待用户；非阻塞请求不暂停工作，Provider 在请求有效期内接受答案。
- **问题组**：一次一起回答的一组问题。Resident 一条回复中写出的全部问题是一组；Codex 的一个原生提问请求是一组。一组只提交一次，答案一起送达。

卡片分两类来源：

| 卡片 | 来源 | 用户操作 | 回答去向 |
| --- | --- | --- | --- |
| 消息中的提问卡片 | Resident 在回复中写出的问题 | 在提问的消息中逐题选择或填写，答完最后一题即提交 | 整组答案作为一条新的用户消息进入队列 |
| 原生提问卡片 | Codex 的 `item/tool/requestUserInput` | 在提问的消息中逐题作答，答完最后一题即提交 | 返回原请求 |
| 审批卡片 | Codex 的命令、文件修改和权限审批请求 | 本次允许、拒绝或取消 | 返回原请求 |
| MCP 补充信息卡片 | Codex 的 `mcpServer/elicitation/request` | 填写表单或打开链接后提交 | 返回原请求 |
| 本轮计划与修改卡片 | Codex 的计划和 Diff 通知；Claude、Kimi、DSH 的 Edit/Write 工具调用 | 查看计划和改动、发起审查 | 审查作为新输入进入队列 |
| 资源修改卡片 | Resident 通过 ResourceService 修改资源 | 查看改动、发起审查 | 审查作为新输入进入队列 |

## 设计点

### 消息中的提问卡片

- **Resident 一条回复中的全部问题组成一个问题组。** Codex 回复中的 `agentMessage.questions`，或回复正文中的 `portal-question` 代码块，由统一的内容解析器转成这条消息唯一的 `async_questions` 部分，和消息其他内容一起保存。代码块可以写一个问题对象，也可以写问题对象数组；每个问题有 `title` 和字符串 `options`。一条回复中有多个代码块时，问题按出现顺序编号，合进同一组，问题组放在第一个代码块的位置。Resident 不需要调用 Portal 接口来发问。
- **一组只接收一条回答消息。** 问题组的 `answer_message_id` 由 Resident 和来源消息推导，是这组唯一可用的回答消息 ID。回答消息带一个 `async_question_answer` 部分，写明来源消息和 `answers`（每个问题序号对应一个非空答案）。服务端要求答案恰好覆盖这组的每个问题，再生成发给 Resident 的正文：一题时写“关于你提出的问题「…」，我的回答是：…”，多题时按问题顺序编号列出。这条消息按普通输入进入 Resident 队列，只触发一轮工作；同一 ID 重试时不会覆盖已提交的不同答案。
- **问题组在回答前一直待回答，用户也可以关闭它。** 问题组的状态只由回答消息和回答位置决定，不另存状态：回答消息已经存在时为“已回答”；用户关闭了这组时为“已关闭”；否则为“待回答”。之后出现的消息都不会让它失效：Resident 同一轮后续的回复、其他 Resident 送来的汇报、用户自己改发的其他消息，以及之后新提出的问题组都一样。2026-10-12 TFI portal 确定这条规则：此前人发出的消息或新的问题组会结束旧问题组，一个协调者向他提出的四个问题在成员汇报到达 30 秒后失效，另一组五个问题被协调者随后提出的新一组取代，他都来不及回答。服务端接收回答时确认问题组存在于这个 Resident 的对话中、答案覆盖全部问题；同一问题组只接受一条回答消息，重复提交同一回答按原回答处理。聊天页用同一规则，从它显示的消息和回答状态推导卡片状态。
- **“不再回答”关闭问题组，不通知 Resident。** 用户已经用普通文字回答过、或不打算回答时，在作答卡片或摘要上点“不再回答”。页面调用 `AnswerResidentRequest`，`message_id` 是提出问题的消息，`answers` 为 `{"action": "cancel"}`；对消息中的问题组，这条指令只接受这个关闭动作，权限与回答相同。服务端把问题组的回答消息 ID 记为输入状态 `cancelled`，错误码 `question_set_closed`（`management_common.async_questions.QUESTION_SET_CLOSED`），不写回答消息，也不排队任何输入，Resident 不会收到消息。已回答的问题组不能关闭；已关闭的问题组再提交回答时拒绝，提示“这组问题已关闭，不再回答”。聊天页从对话快照的输入状态中读出这个错误码，各个浏览器看到同样的状态。Family 门面上显示的成员问题组不提供关闭。
- **提问后 Resident 结束这一轮，等待回答。** Portal 注入给 Resident 的提问说明要求把问题写在回复末尾、提问后结束本轮，不继续做依赖答案的工作。等待期间 Resident 处于空闲，Portal 不创建等待计时、催答或自动空答案；用户可以先发其他消息，Resident 按新消息继续；问题组仍然可以回答，回答到达时 Resident 再按回答继续。
- **Family 门面中显示的成员问题，回答回到提问的成员。** 门面对话显示成员的回复时，回复中的问题组仍属于成员：回答消息 ID 由成员和来源消息推导，状态按成员自己的对话判断。门面把成员问题组的“已回答”标在显示出的问题组上；成员对话已被清空、找不到来源消息时标为“已失效”。聊天页按这个状态显示卡片。用户在门面中提交回答时，服务端在门面对话中找不到来源消息，就通过转交记录找到写这条回复的成员，用成员的问题组检查答案和状态；成员对话中已有其他回答时拒绝。通过检查的回答保存在门面对话中，并自动引用被回答的成员回复，Family Router 因此不经模型直接把它交回这个成员。转交给成员的副本沿用问题组的回答消息 ID，成员对话据此把问题组记为已回答，副本同时引用成员自己的那条回复。嵌套 Family 中每一层门面都按同样方式转交。
- **成员经门面主动提出的问题，回答沿原转交链返回。** 原问题及其回答状态保存在实际发件门面对话；嵌套门面只持有已接受的回答副本时，接收端沿已保存且双向匹配的转交关系查找原问题。每层须保留同一回答 ID、作者、完整 content_parts 和 async_question_answer.source_message_id；按直接上游 Family 的当前归属核对原写信者对应的承接成员。仅有引用摘录、未接受的 business_ref、改写过的答案或不相关会话均不能取得问题来源。原问题的关闭、全组回答及唯一 answer_message_id 校验仍适用；重试复用同一回答，不复制问题、不移除结构或要求用户重答。失败恢复只继续尚未成功的转交，已接收层不重复执行业务。
- **待回答的问题组在提出它的消息中逐题作答。** 同一时刻只有一个问题组显示作答卡片：默认是已加载页面中最新的待回答问题组；其他待回答问题组的摘要带“回答”按钮，点击后作答卡片移到那一组，原来作答的一组改为摘要，已选答案保留。作答卡片显示在问题组原来的位置，提示“这组问题在回答前一直保留”，标题行有“不再回答”按钮，内容是“问题 n/总数”、当前问题、带数字键的选项和“其他回答”输入框。选中一个选项或在输入框按 Enter，就进入下一题；可以回到上一题修改；答完最后一题时立即提交整组。卡片留在对话原文中，不遮挡聊天内容，主输入框和其中的草稿始终不受影响。已选答案按用户和对话保存在浏览器中，切换对话或刷新后恢复；问题组变为已回答后丢弃。只有拥有发送权限的用户看到作答卡片。
- **所有 Provider 用同一条提问路径。** Claude、Codex、Kimi、DSH 的 Resident 都用 `portal-question` 代码块提问，问题组、回答和状态规则与 Provider 无关。Claude Code 的 AskUserQuestion、Kimi Code 的提问工具和 DSH 的 ask-user 工具不接入：它们会让一轮工作停在 Provider 内部等待，无人值守的运行会一直卡住。Claude 的允许工具不含 AskUserQuestion，调用会被拒绝；Kimi 的工具列表不含提问工具，它发出的待回答问题由 Portal 直接关闭；DSH 适配器不接入 ask-user。只有 Codex 的原生提问请求按下一节返回原请求。
- **其他问题组显示为摘要。** 不在作答的问题组在原位置显示问题列表和状态：待回答时显示“等待回答”、“回答”和“不再回答”按钮，已关闭时显示“已关闭，不再回答”，没有发送权限时提示只有拥有发送权限的用户可以回答，已回答时列出每题答案和送达状态；门面显示的成员问题组在成员对话已被清空时显示“已失效：原对话已清空”。摘要本身不提交答案。

### 原生提问卡片

- **Codex 调用用户输入工具时，聊天中出现原生提问卡片。** 适配器接收方法 `item/tool/requestUserInput`（也接受旧名 `tool/requestUserInput`）。一个请求是一个问题组，待回答时和消息中的问题组使用同一个逐题作答卡片，答完最后一题即提交；卡片另有“取消请求”。请求结束后显示同样的问题组摘要。原生问题组的状态由请求的结束结果决定，不受之后的用户消息影响。
- **阻塞请求显示“等待你的回答”，这一轮停下等待真实答案。** 等待期间，停止和其他控制照常响应；人工等待的时间不计入这一轮的恢复超时，也不会被当作“没有进展”而触发恢复。非阻塞请求不暂停工作。
- **答案返回原请求，不成为新的用户消息。** 一个请求的全部问题一起提交。Portal 检查提交者的发送权限、来源消息和 Segment 属于这个 Resident，再通过 Execution 的控制通道，把按问题 ID 组织的答案交给原请求。同一请求重试使用同一个控制 ID，首次提交的答案不会被覆盖。提交结果区分“已提交”和“Provider 已接收”。
- **请求结束后卡片不能再提交。** 用户取消时，Portal 向 Provider 返回明确的取消错误。Provider 清理请求、这一轮结束、线程卸载、连接断开或等待方退出后，Portal 记录结束结果并禁用提交。过期的答案不会转成普通消息补发。用户没有回答时，Portal 不会自动返回空答案。
- **秘密输入没有受保护通道时直接拒绝。** 请求标了 `isSecret` 时，Portal 拒绝该请求，秘密不会进入卡片草稿、控制队列或聊天历史。
- **从 Resident Fork 出的分支可以看到父节点的问题历史，但不能回答父节点的原生请求。**

### 审批与 MCP 补充信息卡片

- **命令执行、文件修改和权限审批请求显示为审批卡片。** 对应方法为 `item/commandExecution/requestApproval`、`item/fileChange/requestApproval` 和 `item/permissions/requestApproval`。卡片写明请求的操作和权限范围，提供本次允许、拒绝或取消，并只提供 Provider 允许的选项。批准的额外权限只用于原请求和当前这一轮，浏览器不能追加权限或把它扩大为整个会话的授权。
- **MCP 服务请求补充信息时显示表单卡片。** 卡片按请求中的 JSON Schema 收集字符串、布尔值、数字、单选和多选，浏览器和服务端在提交前后各校验一次。链接模式只显示安全的 HTTPS 链接，用户在新窗口完成操作后需要明确点击提交，只打开链接不算完成。机密字段、远程 Schema 引用和尚不支持的复杂字段直接拒绝并返回明确错误。
- **阻塞的审批显示“等待你的审批”。** 拒绝、取消、这一轮结束、Provider 断开或请求已被处理后，卡片不能再提交；已失效的请求不会重新授权，也不会显示为已回答。

### 本轮计划与修改卡片

- **Codex 在一轮中制定的计划和改动，在这一轮结束时保存为一张卡片。** 计划来自 `item/plan/delta` 和 `turn/plan/updated`，步骤保留 Codex 给出的 `pending`、`inProgress`、`completed` 状态；改动来自 `turn/diff/updated` 的最后一份 Diff。这一轮结束时，Portal 把计划正文、最后的步骤状态、说明和 Diff 保存为 `native_turn` 内容，并关联到这一轮的模型回复。未完成的步骤保持未完成。
- **卡片标题按实际内容显示：“本轮计划”、“本轮修改”或“本轮计划与修改”。** 计划、说明和 Diff 都为空时不生成卡片。最后一份 Diff 为空时，它覆盖之前的 Diff。卡片只展示 Codex 提供的 Diff；Resident 通过 shell 或脚本写的文件可能不在其中。
- **Claude、Kimi、DSH 没有原生的计划和 Diff 通知，它们的“本轮修改”由这一轮成功的文件工具调用生成。** 这些工具是 Claude Code 的 Edit/Write、Kimi Code 的 Edit/Write 和 DSH 的 edit/write。Portal 在一轮中记下这些调用的参数，在这一轮的 `turn/completed` 之前生成同样的 `native_turn` 内容，标记 `diff_source=tool_calls`，因此卡片、文件选择器、Preview 和审查都与 Codex 相同。Diff 按文件分块，同一文件的多次调用按调用顺序排列，相对路径按这一轮的工作目录展开。Edit 只提供被替换的片段，hunk 的行号从片段第一行起算，标注“Edit（行号从被替换片段起算）”；Write 只提供写入的内容，hunk 只列出写入的全文，标注“写入全文（写入前的内容未记录）”或“追加到文件末尾”。失败的调用、通过 shell 或脚本写的文件、子 agent 的修改都不在其中；这一轮中途由另一个 Worker 接手时，只包含接手后看到的调用。这一轮没有成功的文件工具调用时不生成卡片。
- **Diff 默认折叠，展开后用只读代码查看器显示。** 删除行用红色文字和底色，新增行用绿色，同时保留 `-`、`+` 符号；文件头和 hunk 标记单独区分，深浅主题都可读。短 Diff 按内容定高，长 Diff 在限定高度内滚动。
- **多文件 Diff 上方有文件选择器，默认“全部修改”。** 文件边界和名称从保存的 Diff 中解析，支持带引号或转义的中文和空格路径、重命名、删除和二进制文件；无法识别边界时只显示完整 Diff。选择单个文件只切换显示内容，折叠再展开保留选择。
- **“在 Preview 中打开当前文件”打开的是文件现在的内容。** 选中单个文件时可用；重命名的文件打开新路径，已删除的文件不可用。文件不存在或无权读取时，Preview 显示错误。
- **“审查这些修改”把审查排进 Resident 的正常队列，所有 Provider 都可以审查。** 执行时核对来源 Segment 属于这个 Resident，然后审查保存的完整 Diff，范围不随文件选择器缩小。Codex 用 `review/start` 审查；Claude、Kimi、DSH 没有原生审查模式，Portal 把同一份审查说明和完整 Diff 附在这条审查消息之后，作为普通一轮交给 Resident。由工具调用生成的 Diff，审查说明会写明它的行号从被替换片段起算、Write 只有写入后的内容。审查说明会提醒：共享工作目录可能已被他人改动，不能把他人的改动算作这一轮。Diff 超过展示上限时标记为截断，并禁用审查。这条审查消息只带被审查的那一轮（`turn_review` 分段），聊天中以发起人的名义显示为“请审查这一轮的修改”；Portal 给 agent 的说明文字不作为正文显示。

### 资源修改卡片

- **Resident 通过 ResourceService 修改知识条目、知识附件、Skill 文本或 Experiment 文档时，这一轮结束后聊天中出现资源修改卡片。** 卡片沿用“本轮修改”的 Diff 查看器、文件选择器、Preview 和审查入口，并显示资源地址和修改前后的版本。
- **每次写入都单独记录，只记录这个 Resident 这一轮的写入。** 知识条目用自身的版本号；没有版本号的文本用内容的 SHA-256 表示版本。其他 Resident 对同一资源的写入不会并入。
- **这一轮失败或被取消时，之前已经成功的写入仍然显示。**
- **正文已保存、但修改记录没能保存时，更新结果返回 `change_recording.status=unconfirmed`。** 这表示正文写入已成功、只是记录缺失，调用方不需要重复提交。Portal 不根据之后的文件内容补猜记录；过去没有记录的修改也不会补生成卡片。

## 实现

### 卡片内容保存在哪里

原生请求的问题和结束结果分别保存在对应的、不可修改的工具调用和工具结果 Segment 中，工具名为 `request_user_input`；聊天按 `tool_call`、`tool_result` 类型渲染它们。原生方法、请求 ID、问题参数、用户的决定和工具结果都在这些 Segment 中。卡片草稿和提交回执只是页面上的交互状态。

聊天显示卡片时，按 Segment ID 精确读取正文，并核对它属于哪个 Resident、Execution、请求、线程、轮次和调用。活动日志用于观察运行过程，可以隐去敏感文字，所以它不作为卡片正文的来源；重放旧活动事件时也走同一个读取流程。`isSecret` 的布尔值只是类型标记，隐去敏感内容时保留它。

刷新或加载更早的历史时，Portal 只读取这一页的消息，并按 Segment ID 查询这一页原生请求的结果，不扫描全部历史。问题组的状态从这一页的消息、回答和队列推导；来源消息不在已加载页面中的问题组不显示作答卡片，已选答案保留到它再次出现。


### 刷新时保留正在作答的输入

同一 Resident 会话内，消息内容、状态、历史分页或新消息的被动刷新，不得把仍有效的问题卡片输入节点移出页面再装回。消息渲染器只更新卡片宿主周围的内容；按问题请求 ID 识别的卡片宿主及其输入 DOM 由卡片组件维护。未确认的输入文字、焦点、选区和输入法组合状态随原节点连续保留，不靠刷新后重新 focus 补救，也不停止更新消息正文或状态。该规则同时覆盖异步问题组、原生 request_user_input 与 MCP 补充信息卡片。

默认展开最新可回答的问题组；用户把焦点放入某个问题组后，视为已选中该组，新问题到达只增加可选择的摘要，不替换正在填写的组。用户从摘要明确切换、问题关闭或失效、发送权限变化、来源消息移出已加载范围、会话切换仍按原有生命周期更新；被动刷新不得把焦点从其他控件拉回卡片。


### 答案怎样回到原请求

Provider 适配器只为尚未结束的请求保存连接内的关联信息：请求标识、线程、轮次、条目和原始 JSON-RPC 请求 ID。这些关联不跨连接复用。用户提交后，答案经 Execution 已有的 `user_input_response` 控制通道交给适配器，适配器用原 JSON-RPC 请求 ID 回复 Provider。审批和补充信息使用同一条路径。

### 卡片生成失败时

某条消息的卡片生成失败时，Portal 按 Execution 和消息标识隔离这条失败并记录错误，其他消息和停止操作不受影响，也不会无限重试。恢复只针对已识别的失败消息，用原消息 ID 和 Segment ID 重新生成；成功后解除隔离。原始 Segment 保持不变，已经取消或失效的请求不会重新打开。

### 资源修改怎样关联到这一轮

Codex 每一轮把当前 Execution ID 放进工具进程的环境变量，Resident 的资源客户端随写入请求带上它。ResourceService 在写正文前向 ExecutionService 核对这个 Execution 正在运行、并属于已认证的 Resident。这个关联只用于把修改归到这一轮，不授予读写权限：调用者身份、资源授权和版本冲突检查照常进行。业务 Job ID 和 Provider 的 turn ID 都不能代替 Execution ID。没有关联的普通编辑不归入任何会话。

写入方在自己的修改锁内取得修改前后的内容和版本，保存一条不可修改的修改记录。Execution 进入 `completed`、`failed` 或 `cancelled` 后，SocietyService 读取这次 Execution 的修改记录，生成一个 `resource_changes` Segment，按原 Job 的回复关系加入会话。平时轮询运行状态时不查询修改记录；已生成的 Segment 在重放时复用，不重复追加卡片。

完整文本保存在资源的修改记录中，聊天只保存可显示的 Diff、版本和摘要哈希。文件写入和修改记录是两个独立的存储，进程恰好在两次写入之间退出时，可能留下没有记录的修改。

### 验证

定向测试分别覆盖：消息提问卡片与分页；原生请求的等待、答案返回原请求、取消与失效、重复提交、权限与 Fork 限制、按 Segment 查询；计划步骤与审查；Claude、Kimi、DSH 由工具调用生成本轮修改与普通一轮审查；资源修改记录。浏览器测试用真实样式和编辑器检查逐题作答与整组提交、对话继续和新问题组出现后仍可回答、从摘要切换作答的问题组、从卡片和摘要关闭问题组、失败保留已选答案、提交回执、失效后禁用，以及无计划时的紧凑布局、窄面板、Diff 着色、折叠展开和截断后禁用审查；断言使用布局范围和语义，不比对截图。

真实 Provider 验收使用 Portal-test 身份，保存请求所属的 Resident、Execution、轮次和截图。只有 Provider 真的发出请求、Portal 显示卡片并把操作送回原请求，才算这条链路通过。Provider 没有提供对应能力时（如没有触发审批、没有可发起补充信息的 MCP 服务），明确记录为未覆盖，不用普通文本或人工构造的卡片代替。
