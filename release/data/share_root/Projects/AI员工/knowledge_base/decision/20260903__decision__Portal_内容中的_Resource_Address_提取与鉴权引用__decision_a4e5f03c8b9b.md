# Portal 内容中的 Resource Address 提取与鉴权引用

用户在 Portal 中写的很多内容是普通自然语言：发给 Resident 的消息、Knowledge 条目的 AI 对话、Review 的处理说明，以及知识归档对话。用户可以在这些文字里直接写一个资源地址，例如 `repo_a38c7d91e204` 或 `repo_a38c7d91e204/file/src/main.py`，让接收的页面和 Agent 知道这段话指的是哪个正式对象。

本 Design 说明 Portal 怎样从正文中找出这些地址，怎样以发送者的身份把它们转换成可以保存的引用，以及怎样把引用交给 Agent。资源地址本身的语法和解析规则见 `decision_4a9ba5dfada6`；本篇只负责“在正文中提及资源”这一层，它不判断资源是否存在，也不授予任何读取权限。

## 基本概念

- **资源地址**：一个资源的统一 ID，或统一 ID 后面接上内部路径。统一 ID 由资源类型和 12 位小写十六进制码组成，例如 `paper_1a2b3c4d5e6f`。
- **自然语言区域**：正文中用来表达意思的文字。代码块、行内代码、链接目标、部分 HTML 标签、文件路径和命令示例不属于自然语言区域，其中的地址不会被自动识别。
- **候选地址**：在自然语言区域中找到、形状符合资源地址语法的字符串。它还需要经过 ResourceService 验证。ResourceService 是 Portal 统一的资源服务，负责解析地址并检查访问权限（`decision_cf27d39e39cd`）。
- **显式引用**：调用方在正文之外单独提交的地址，例如用户在消息输入框里通过资源选择器添加的资源。
- **鉴权引用**：ResourceService 以发送者身份解析一个地址后返回的简短描述，包含身份、标题、摘要和打开地址，不包含资源正文。
- **引用快照**：业务记录（例如一条留言或一条消息）保存的鉴权引用。它记录的是发送那一刻的解析结果，之后打开或读取资源时仍重新检查权限。
- **上下文引用集合**：业务记录中保存引用快照的字段 `context_refs.resources`。每个业务模块在自己的记录里保存这个集合。
- **引用区块**：交给 Agent 时追加在消息后面的 `<resource_references>` 文本区块，列出本次消息的全部引用。

所有这些规则都由共享模块 `management_portal/resource_refs.py` 实现，各业务入口调用它，不各自编写识别规则。

## 设计点

### 自然语言中的正式地址会成为引用

- **只有完整、小写的规范地址会被识别。** 根部必须是“类型 + 下划线 + 12 位小写十六进制码”；后面可以接若干非空路径段，路径段中的 `%` 只有后面跟两位十六进制字符时才算作路径内容。
- **地址必须独立出现。** 地址左侧不能紧挨英文字母、数字、下划线、`.`、`/` 或 `\`，右侧不能紧接英文字母、数字或下划线。句末的中英文标点（`.,;:!?/，。；：！？`）不计入地址。
- **按首次出现的顺序保留，重复的地址只算一次。**
- **一条内容最多产生 20 个引用。** 达到 20 个后不再识别后面的地址。空正文得到空集合。

### 代码和示例中的地址保持原样

用户贴出的代码、命令和链接应该继续按原样显示，所以其中的地址不会变成引用：

- **代码块**：用三个或更多反引号、或三个或更多波浪号开始的 Markdown 代码块。结束标记必须使用相同字符，并且不短于开始标记。
- **行内代码**：一对相同长度的反引号之间的内容；前面带反斜杠的反引号不作为边界。
- **链接与图片**：Markdown 的行内链接、引用式链接和图片语法。
- **HTML 标签**：`a`、`code`、`kbd`、`pre`、`samp` 和 `var` 标签中的内容。
- **定位符**：文件路径、`http://`、`https://` 和 `file:` 地址中出现的统一 ID。
- **像代码或命令的整行**：以 `def`、`import`、`const`、`class` 等关键字开头的行，形如 `name = value` 的赋值，函数调用语句，JSON 键值行，以及带有路径、`--参数`、`变量=值` 或管道符号的命令行。

### 按发送者身份解析，单个地址失败不影响保存

- **每个候选地址都由 ResourceService 以发送者身份解析。** 发送者身份来自发送入口已经完成的认证，正文中的文字无法改变它。
- **解析失败的地址保存为失败状态，内容照常保存。** 失败状态分为四种：

  | 状态 | 含义 |
  | --- | --- |
  | `forbidden` | 发送者无权读取该资源 |
  | `not_found` | 资源或内部目标不存在 |
  | `invalid` | 地址格式错误，或资源类型的解析结果不符合规范 |
  | `unavailable` | 资源服务暂时不可用或出现其他故障 |

  失败项保留完整地址、状态和不超过 300 个字符的错误说明，标题使用地址本身，不补造资源标题或摘要。一个地址失败不影响其他地址的解析，也不会阻止留言、消息或说明本身保存。
- **引用不向读者扩散权限。** 一位读者在留言中看到别人引用的资源，打开时仍按这位读者自己的权限检查。

### 显式引用与正文引用合并为一个集合

- **先放显式引用，再追加正文中识别出的地址。** 显式引用可以是字符串形式的地址，也可以是对象；对象依次读取 `address`、`resource_id` 和 `id` 字段作为地址。空值被忽略。
- **合并后按地址去重，总数仍不超过 20 个。**
- **没有任何候选时直接返回空集合。** 这时不连接 ResourceService，所以不含引用的内容不受资源服务状态影响。

### Agent 收到一个经过转义的引用区块

- **有引用时，引用区块追加在消息正文之后；没有引用时不生成区块。**
- **区块开头说明三件事：** 这些条目已经按当前调用者解析；条目只描述资源，不包含正文，也不增加权限；需要读取正文时，Agent 应使用自己已有的资源读取能力，不借用其他身份，也不根据标题或路径猜测资源。
- **每个资源写成一个 `<resource>` 元素。** 地址、根 ID、类型和状态写在元素属性中，标题、摘要和 Portal 打开地址各占一行。
- **所有动态内容都先做 HTML 转义。** 资源标题、摘要和用户正文中的尖括号或引号不能关闭标签，也不能插入新的提示结构。

## 保存格式

一项引用快照包含以下字段：

| 字段 | 含义 |
| --- | --- |
| `address` | 完整的规范资源地址 |
| `resource_id` | 地址根部的统一 ID |
| `resource_type` | 根资源的类型 |
| `title` | 页面和 Agent 显示用的标题 |
| `summary` | 可选的简短说明 |
| `status` | `resolved`（解析成功）或上面四种失败状态之一 |
| `url` | Portal 中打开该资源的地址 |

读取已经保存的记录时，共享模块把每一项补全为上面的格式：缺少标题时依次使用 `name` 字段、根 ID 或地址；缺少根 ID 时取地址的第一段；缺少类型时从根 ID 前缀推出；缺少打开地址时使用通用入口 `/r/<百分号编码后的地址>`；保存的是纯字符串而不是对象时，这一项标为 `unresolved`。补全后再次按地址去重，最多保留 20 项，因此旧数据中的超长数组也不会突破上限。

## 谁在使用这套规则

| 使用方 | 在什么时候调用 |
| --- | --- |
| 发给 Resident 的消息 | 投递消息时解析用户选择的资源和正文中的地址，结果随消息保存；执行时把引用区块附在消息后交给模型 |
| Knowledge 条目的 AI 对话 | 发送对话消息时使用同一套上下文解析 |
| Review 中发给处理 Resident 的消息 | 用户选择的资源与正文中的地址合并解析，随消息保存，并附在交给 Resident 的内容中 |
| 知识归档对话 | 发送归档对话消息时解析正文中的地址 |
| Agent Harness 的统一资源读取工具 | 只使用识别规则：本轮消息正文中识别出的地址，才允许用该工具读取（`decision_5c62deb8253a`） |

一次处理的顺序如下：

```text
显式引用 + 用户正文
        ↓
屏蔽代码、链接、路径和命令区域
        ↓
按出现顺序识别、合并、去重，最多 20 项
        ↓
ResourceService 以发送者身份逐项生成鉴权引用
        ↓
业务模块把成功或失败的引用快照保存在自己的记录中
        ↓
交给 Agent 时追加转义后的引用区块
```

页面把引用显示成资源标签（Resource Chip）的方式由共享前端组件负责，不属于本篇。

## 状态归属与恢复

- 业务模块拥有自己保存的内容和 `context_refs`。
- ResourceService 拥有实时的地址解析和权限检查。
- 共享模块 `resource_refs.py` 拥有识别规则、20 项上限、失败状态和保存格式。

引用快照只反映发送时的结果。资源改名、移动或权限变化后，真正打开和读取资源时都会重新经过 ResourceService。资源服务暂时故障时，相应引用保存为 `unavailable`；业务模块可以之后重新解析，但不能把旧的成功快照当作长期有效的授权。将来要支持新的 Markdown 资源语法、更多地址字符或更多引用数量时，只修改 `resource_refs.py`，各业务入口不另外增加识别规则或数量上限。
