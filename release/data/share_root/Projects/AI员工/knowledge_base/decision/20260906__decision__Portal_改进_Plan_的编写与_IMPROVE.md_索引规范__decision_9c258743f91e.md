# Portal 改进 Plan 的编写与 IMPROVE.md 索引规范

Portal 的规范文档分两类：**Design** 说明系统现在是什么样（由 `SPEC.md` 索引，写法见 decision_ef80c6d3b5ee）；**Plan** 提出一个还没做、但值得做的改进（由 `IMPROVE.md` 索引）。本文说明 Plan 应该写什么、一份 Plan 应该多大、怎样登记到 `IMPROVE.md`，以及 WALL 怎样显示它。本文同时是 `SPEC.md` 规范管理部分的条目和 `IMPROVE.md` 的第一项。

## 基本概念

- **Plan**：一份提出单个改进的文档，保存在 AI员工项目知识库，资源类型为 `plan`，ID 形如 `plan_*`。改进持续完善时沿用同一个 ID。
- **`IMPROVE.md`**：Portal 工程根目录中的改进索引，列出当前值得审查的 Plan 的标题和 ID。
- **审查**：人阅读一份 Plan 后，决定这个改进做不做。一份 Plan 就是一次审查的单位。
- **`importance` 与 `metaness`**：知识库文档头部的两个评分。`importance` 表示有多重要；`metaness` 表示讨论的问题有多抽象，WALL 用它决定卡片面积。

## 设计点

- **一份 Plan 只讲一个改进，这个改进要大到值得人单独做一次决定。** 为了实现同一个收益、必须一起成立的多个步骤，写在同一份 Plan 中；两个主题可以分别判断、分别交付、各有明显价值时，才拆成两份。
- **Plan 的数量由真实的改进决定。** 不按领域或 Design 数量分配 Plan：多个 Design 可以支撑同一份 Plan，一份 Design 也可以没有 Plan。没有值得做的改进时就不写。
- **凑数的小调整不单独成为 Plan。** 常规开发步骤、没有独立收益的零碎修改，放进相关 Plan 的细节或普通任务中。
- **WALL 把一份 Plan 显示为一个改进卡片。** 卡片用 Plan 的标题和整体摘要，详情显示完整正文；Plan 中的列表、小节和实施步骤属于同一张卡片。Design 则按设计点分别显示。
- **`importance` 和 `metaness` 各管各的。** 一个表示重要程度，一个表示抽象程度，都不决定实施顺序或审核结论。

## Plan 写什么

读者读完一份 Plan，应该能回答“这个改进值不值得做”。通常按下面的顺序展开，章节名称和数量按内容自由安排，正文以一级标题开头：

1. **场景**：谁在什么情况下使用什么功能，现在要经历什么过程，困难或机会在哪里。关联的 Design 可以提供完整现状，但 Plan 自己要保留理解这个改进所需的背景。内部术语第一次出现时说明它是什么。
2. **价值**：做完之后，哪段工作、哪项能力或哪种维护成本会改变，为什么值得占用一次审查。好的价值是可辨认的结果，例如用户能完成以前做不到的事、一段流程明显省事、反复出现的障碍消失、服务获得确实需要的新能力。架构改造要说明职责、变化传播或维护负担怎样改善。“文件太长”“名字不统一”“可以加一层服务”只是线索，本身不构成价值。
3. **方案**：目标体验和实现机制。面向用户的改进，写清入口、操作、反馈、结果怎样找回、出错时怎样；内部改造，写清职责归谁、状态由谁维护、信息怎样流动、调用方怎样接入。多个 Plan 需要同一套规则时，由一个明确的负责方维护这套规则。图示和技术细节按需保留，标明哪些是现状、哪些是建议。
4. **边界与验收**：这次包括什么、保留什么、依赖什么、主要代价是什么，完成后能观察到什么结果。先后顺序只按依赖关系写，不编造排期。探索性的 Plan 写明要先验证哪些假设。

**证据要真实。** 事实来自实际检查过的 Design、代码或运行结果；说复现了故障就要有运行证据；没测量过的等待时间、节省比例和工期写“未知”。Design 没写某个功能，不代表系统里没有；旧证据在推进前要重新核实。正文解释证据为什么支持结论，`links.source` 列出来源文件。

**举例说明粒度。** “让刚完成的工作有持续可达的结果入口”是一份 Plan：它围绕一次完整的找回过程，解释完成记录、结果关联和不受筛选影响的详情访问；其中的字段、按钮和请求调整都是实现细节，不各自成为 Plan。

审查多个领域时，报告检查了哪些范围、依据是什么；没有明显改进的领域可以没有 Plan。某次任务明确排除的主题，只对那次任务有效。

## Plan、Design 与 WALL

Design 解释已经成立的结构和交互；Plan 解释一个提议的变化。Plan 的 `links.derived_from` 记录它真实推导自哪些文档，可以有多个；相关但不是来源的领域和相邻方案放在 `links.related`。

### metaness 怎样取值

`metaness` 写在知识库文档的 YAML 头部，可以省略。取值必须是 1 到 10 的整数；布尔值、字符串、小数、空值和超出范围的值都非法。省略时 WALL 按 1 显示，不改写文件；值非法时 WALL 报告出错的字段，后台不猜测、不转换、不截断，也不删除它。

按全文主要讨论的对象打分：

| 分数 | 讨论的对象 |
| --- | --- |
| 1 | 一项具体行为 |
| 2 | 一个子系统的模型 |
| 3 | 同一工程中跨子系统的机制 |
| 4–5 | 跨领域的设计原则或工作方式 |
| 6–7 | 规范、知识组织和设计方法本身 |
| 8–10 | 跨多个治理体系的元模型及其评价 |

普通工程文档通常是 1–3；讲未来具体功能的文档仍可以是低分，已经稳定的规范治理文档也可以是高分。本文讨论 Plan 的组织和审查规则，取 6。字段的通用约束见 `skill_577f37784184`。

评分要逐份判断，不按标题、目录或关键词批量生成。WALL 按 `metaness` 决定卡片面积，把大小不同的卡片紧密排列，除正常边框和间距外不留空洞。

## IMPROVE.md 的登记与维护

- **`IMPROVE.md` 开头的编写与审阅规则指向本文。** 其余条目按读者容易理解的改进主题排列，每项写标题、一句场景与价值、Plan ID，必要时注明关联的 Design。索引不复制正文，也不维护领域配额或一对一映射。
- **登记前先查有没有 Plan 已经在讲同一个改进。** 有就在原 Plan 上完善，保留原 ID；是全新的独立主题，才通过当前 Resident 的资源登记入口新建。
- **修改已有 Plan 时保留创建信息。** 保留创建日期、创建者和仍然有效的链接，递增版本号并记录本次修改者：人类用户无法确认时填空字符串，Agent 填实际写入者的 Resident ID。
- **整理已有 Plan 时先确认价值和关系。** 讲同一个改进的合并，保留背景和有效细节；没有独立价值的碎片删除；各有明显价值的分别保留。保留有效的来源和 ID，不为了维持数量而拆出新主题。删除要有用户授权，并遵守已有的快照安排。
- **实施后回头核对。** 已经成立的行为写进对应的 Design。改进还没做完时，Plan 更新剩余范围和当前状态；全部完成、失效或不再值得做时，从 `IMPROVE.md` 移出。实施记录保存在任务或成果入口中。

维护时检查三件事：每一项是否值得单独审查；读者能否从全文理解一个完整的改进；索引和资源是否准确、没有重复。后台可以报告碎片、重复、证据不足和非法元数据；调整主观评分和重组正文需要明确授权。
