# 知识库归档：把材料整理成项目知识

知识库归档是 Knowledge 页面中把外部材料整理进 Project 知识库的工作区。用户交给它一段文字、一个链接、一个本机路径或一组文件，负责归档的 Resident 先提出“建议归档哪些内容、写到哪里”的方案，用户审阅后再让它生成草稿；只有用户点击“Apply 到知识库”，内容才写入 Project。整理过程中产生的一切都放在暂存区，不会提前改动 Project。

本 Design 说明归档工作区的页面、一次归档作业从创建到写入的过程、后台服务与 Resident 的分工，以及出错后的恢复。写入 Project 之后的知识条目怎样登记、修改和讨论，由 Knowledge 资源相关的 Design 负责，见 decision_3ece26686464。

## 核心概念

- **归档作业**：一次归档的全部状态，ID 形如 `ka_` 加 16 位十六进制。作业按用户隔离，每位用户只能看到自己的作业。它保存在暂存区 `${staging_root}/shared/knowledge_archive_jobs/<用户>/<作业 ID>/`。作业 ID 只在归档过程中使用，不是知识条目的资源 ID。
- **候选**：方案中的一条计划，说明建议写入哪个 Project、知识类型、建议文件名、摘要和理由，以及用户的处理决定（批准或拒绝）。
- **草稿**：按一条已批准候选生成的完整文件，仍在作业目录中，等待用户检查。
- **Apply**：用户把选中的草稿写入 Project 知识库的操作。
- **知识类型**：`concept`、`idea`、`insight`、`question`、`decision`、`plan`、`thinking`、`information` 和 `material`（原始材料）。普通草稿写到 `<Project 目录>/knowledge_base/<类型>/<文件名>.md`，原始材料写到 `<Project 目录>/knowledge_base/material/<子目录>/<文件名>`，子目录默认为 `uploaded`。
- **归档策略**：告诉 Resident 按什么标准整理，共五种：

  | 页面标签 | 取值 | 含义 |
  | --- | --- | --- |
  | 高门槛精选 | `strict` | 只保留长期价值明确、与项目推进关系清楚、且与已有知识不重复的内容（默认） |
  | 尽量完整 | `complete` | 去重和去除无意义内容后，尽量覆盖材料中有长期参考价值的内容 |
  | 只归档 idea/insight | `idea_insight` | 只生成 idea 和 insight 类型 |
  | 只归档 decision | `decision` | 只生成 decision 类型 |
  | 直接保存文件 | `save_material` | 不拆分内容，把文件或目录原样保存为 material |

## 页面

Knowledge 页面工具栏上的归档按钮打开“知识库归档”窗口，窗口分为三栏：

| 区域 | 内容 |
| --- | --- |
| 输入 | 作业列表；标题（可留空）；Project 提示（例如 `RobotWorker`，可留空）；五个归档策略按钮；材料输入框（可以粘贴文本、链接或 `${share_root}` 路径，也可以拖放文件或图片）；添加附件；“生成方案”按钮 |
| 候选与草稿 | 候选列表（可以修改目标 Project、类型、文件名、摘要、补充要求和批准决定）；“生成/更新草稿”按钮；草稿列表（勾选要写入的草稿，可以预览和编辑）；“Apply 到知识库”按钮 |
| Chat | 与本作业的 Resident 对话，补充要求，查看运行状态 |

窗口顶部还有“清空”和关闭按钮。关闭窗口只是收起，作业保留，下次打开可以从作业列表中继续。

## 一次归档的过程

### 1. 创建作业

**用户提供材料并点击“生成方案”后，服务创建一个归档作业，并让 Resident 分析材料、提出候选方案。**

- 材料不能为空。服务判断输入类型：文本、URL、本机路径，或者多项材料组成的一组（bundle）。本机路径必须位于 `${share_root}`、`${staging_root}` 或 Portal 代码目录 `${code_root}` 之内。
- 附件单个最大 128 MiB，全部附件合计最大 512 MiB。
- 服务把材料复制或引用到作业目录，然后作业进入 `planning`（分析中）。Resident 分析完成后，作业进入 `plan_review`（候选待审阅）。
- 使用“直接保存文件”策略，并且 Project 提示能准确对应到一个 Project 时，服务直接为每个文件生成保存候选，不调用 Resident，作业立即进入 `plan_review`。这一步只形成计划，文件还没有写入。

### 2. 审阅候选

**用户逐条修改候选并决定批准或拒绝；修改在停止输入 0.6 秒后自动保存到作业中。**

- 保存候选时，整个候选列表替换作业中原有的列表，作业保持在 `plan_review`。这一步不调用 Resident，也不写入 Project。
- 候选中填写的 Project 和类型只是计划。生成草稿和 Apply 时，服务会再次检查它们。
- Resident 认为没有值得归档的内容时，候选列表为空，页面提示可以在 Chat 中追加要求让它重新分析。

### 3. 生成与编辑草稿

**用户点击“生成/更新草稿”后，Resident 为每条批准的候选写出完整草稿；没有批准的候选时，请求被拒绝。**

- 作业先进入 `drafting`（生成中），Resident 完成后进入 `draft_review`（草稿待审阅）。
- 草稿正文必须能脱离原材料独立阅读：Resident 把材料内容提炼或重述为自洽的事实、结论和条件，不写“第几页”“如上图”这类依赖原文件的说法。
- 用户可以在页面中修改草稿。单份草稿最多 500,000 个字符，路径必须位于本作业目录内。作业已经 Apply 后不能再修改草稿。
- 使用“直接保存文件”策略时，页面不显示“生成/更新草稿”按钮。用户审阅文件候选后直接 Apply，服务在 Apply 时根据批准的候选准备要复制的文件。

### 4. Apply 到知识库

**用户点击“Apply 到知识库”后，服务把选中的草稿写入各自目标 Project 的知识库；成功后页面刷新知识库索引，并删除这个归档作业。**

- **能登录 Portal 的用户都可以把草稿写进任意已登记 Project。** Apply 继续保留原有已登录写入规则，不读取已退役的 Project 角色。
- 普通草稿逐份写入。写入前服务检查目标 Project 已登记、类型属于上面列出的知识类型、文件名以 `.md` 结尾且不含路径、正文不为空。目标文件已经存在时，这份草稿写入失败，已有文件保持不变。
- material 草稿复制文件或目录；目标名称已被占用时自动改用下一个可用名称，已有材料保持不变。
- 多份草稿按顺序写入。某一份失败时，前面已经写入的文件保留，结果中列出每份的写入情况，用户修正后可以继续处理剩余草稿。
- 至少写入一份后，或“直接保存文件”策略执行完成后，作业进入 `applied`。Portal 随后通知资源索引收录新文件。
- 页面在 Apply 成功后自动删除这个作业并清空窗口。用户拒绝了全部候选、没有可写入的草稿时，点击 Apply 同样清空这个作业，写入数量为 0。

### 5. 清空作业

**用户点击“清空”并确认后，服务删除作业目录和其中的全部暂存文件；已经写入 Project 的文件保持不变。**

- 确认窗口提示“当前归档页面和后台暂存文件都会被删除”。取消后不发送任何请求。
- Resident 仍在处理这个作业时不能清空，页面提示等待完成；服务端同样拒绝删除有未完成对话的作业，避免 Resident 往已经删除的目录中写文件。

## 作业状态

| 状态 | 含义 | 用户接下来可以做什么 |
| --- | --- | --- |
| `planning` | Resident 正在分析材料 | 等待，或在 Chat 中查看进展 |
| `plan_review` | 候选方案可以审阅 | 修改候选，生成草稿 |
| `drafting` | Resident 正在生成草稿 | 等待 |
| `draft_review` | 草稿可以审阅 | 修改、勾选，然后 Apply |
| `material_ready` | “直接保存文件”的复制计划已准备好 | 核对后 Apply |
| `applied` | 至少一份内容已经写入 Project | 到 Knowledge 页面查看正式条目 |
| `failed` | Resident 这一轮工作失败 | 查看错误信息，修改输入或在 Chat 中重试 |

作业记录（格式版本 2）保存用户、标题、输入说明、策略、Resident ID、尚未完成的对话、状态、时间、最近的错误、候选方案、草稿和已写入结果。作业列表按更新时间从新到旧排列，每次最多返回 100 个。

## 组件与流程

| 组件 | 位置 | 职责 |
| --- | --- | --- |
| 归档窗口 | `knowledge_board_lan/knowledge_board.html` | 收集输入，显示候选、草稿和 Chat，提交操作 |
| Portal 转发层 | `management_portal/http_knowledge.py`、`knowledge_archive_backend.py` | 把当前登录用户和请求转发给本机归档服务，转换错误码；Apply 成功后通知资源索引 |
| 归档服务 | `${share_root}/Agents/KnowledgeArchiveAgent`，用户服务 `knowledge-archive-agent.service`，监听 `127.0.0.1:8767` | 管理作业目录、校验输入、启动 Resident 对话、保存方案和草稿、执行 Apply |
| 归档 Resident | Lineage “Knowledge Archive Agent” 中每个作业一个 Resident | 分析材料，写出候选方案和草稿 |
| 作业目录观察 | `management_portal/knowledge_archive_projection.py` | 作业目录中的文件变化后，通知打开的页面刷新；它只读不写 |

**Resident 的调用方式**：归档服务通过 Portal 的共享业务调用（decision_725dedbe89b2）为每个作业创建或复用一个 Resident，它们都属于同一个 Lineage。这个 Lineage 是 “Knowledge Archive Agent”，在服务配置 `agent_session.lineage_id` 中写明，每次调用都显式绑定到它；调用以提交作业的用户为请求方，Portal 服务名称不能代替用户在 Lineage 中创建或使用 Resident，缺少配置或请求方时作业直接失败。每次需要 Resident 工作时，服务投递一条消息，并把这条消息记为“未完成对话”；后台线程等待这条消息结束，再从作业目录读取 Resident 写出的方案或草稿，更新作业状态。

```text
用户提交材料与策略
        ↓
Portal 转发层（附上当前用户）→ 归档服务
        ↓
建立 ka_* 作业目录 → 投递消息给本作业的 Resident            planning
        ↓
Resident 写出候选方案 → 用户审阅、批准                    plan_review
        ↓
Resident 写出草稿 → 用户检查、勾选                        drafting → draft_review
        ↓
用户点击 Apply → 写入 Project 知识库 → 通知资源索引          applied
        ↓
页面删除作业
```

作业先放在暂存区，是为了让 Resident 的输出在用户确认之前不影响 Project；候选和草稿分两次审阅，把“理解材料”和“写成正式条目”分开；最终写入由用户点击 Apply 触发。

## 接口

页面通过以下 Portal 地址操作归档作业。Portal 在每个请求中附上当前登录用户，再转发给归档服务的同名 `/api/archive/...` 地址：

| 请求 | 作用 |
| --- | --- |
| `GET /knowledge/api/archive/jobs?limit=<n>` | 列出当前用户的作业 |
| `GET /knowledge/api/archive/job?id=<作业 ID>` | 读取一个作业 |
| `POST /knowledge/api/archive/create` | 创建作业，提交材料、策略、标题和 Project 提示 |
| `POST /knowledge/api/archive/chat` | 向本作业的 Resident 发送消息，参数为 `archive_id`、非空 `content` 和 `message_id` |
| `POST /knowledge/api/archive/candidates` | 用完整列表替换候选 |
| `POST /knowledge/api/archive/drafts` | 为批准的候选生成草稿 |
| `POST /knowledge/api/archive/draft/save` | 保存一份草稿的修改 |
| `POST /knowledge/api/archive/apply` | 写入选中的草稿；`draft_ids` 为空时写入全部草稿 |
| `POST /knowledge/api/archive/delete` | 删除没有未完成对话的作业 |

Portal 转发时最多等待 180 秒。归档服务返回的 400、403、404、503 分别对应请求不合法、无权操作、找不到和服务不可用；归档服务没有运行时返回 503 和“KnowledgeArchiveAgent 未运行，归档功能暂不可用”；其他错误返回 500。

**信任边界**：归档服务只监听本机地址，不做登录认证，直接把 Portal 附上的用户名当作作业分区。它的安全依赖两点：只有本机进程能访问它，以及所有外部请求都经过 Portal 的登录检查。Apply 的写入权限由“能登录 Portal”决定：归档服务和 Portal 转发层都不检查目标 Project 的角色；经 ISA 的写入由权限系统按当前模板判定（decision_b820faf42218）。

## 故障与恢复

- **服务或 Portal 重启**：作业保存在暂存区，重启后可以重新列出。读取作业时，服务为仍记录为“未完成”的对话重新启动等待，并从作业目录刷新方案或草稿。
- **Resident 工作失败**：服务清除“未完成对话”，把作业标为 `failed` 并记录错误，用户可以在 Chat 中重试。
- **Apply 部分成功**：已经写入的文件保留，结果中列出每份的情况；已存在的知识文件不会被覆盖。
- **删除作业**：只删除暂存内容。撤回已经写入 Project 的知识，使用对应知识条目自己的修改或删除方式。
