# Lineage 个性化前端投影：公共绑定、身份创建、生成提交恢复、有界资源读取与双向演化

一个 Lineage 是一组 Resident 和它们之间的协作结构（decision_6fc653d55c79）。直接在 HATG 画布上操作 Lineage 很灵活，但对于某一类固定的工作，例如审阅论文、管理设计点、运行测试，用户更需要一个专门的页面：只显示这项工作需要的内容，加上筛选、编辑、比较、草稿和确认步骤。**前端投影**（Portal 中称为工作台，Workbench）就是这样的页面：它把一个或多个普通 Lineage 的协作能力、领域资源和正式产物组织成适合某种工作方式的界面，页面与 Lineage 使用同一组 Resident、同一份执行记录和同一批业务数据。

**反向整理**（也称反投影）走相反的方向：工作台做好或改进之后，根据页面实际承担的工作，重新检查 Lineage 中的职责、入口和连接，提出一份可以审查的整理方案。它依据业务含义整理协作结构，不从截图机械地还原出图。

投影协议 v2（decision_7a5ae487e2e9）在本篇之上增加页面清单、侧栏多功能区、绑定 `facade` 角色的原生对话区、语义对象和变化通知；本篇的规则在 v2 中继续有效，v1 的单页面工作台按“只有一个功能区、没有对话区”的 v2 页面处理。

本篇规定所有工作台共同遵守的机制：页面怎样绑定 Lineage、怎样创建和使用 Resident、怎样调用 HATG 指令、页面的保存与发布，以及反向整理的流程。每个工作台具体有哪些功能、角色、流程入口和产物，由它自己的业务 Design 规定（见文末）；投影工坊的生成与反向整理功能见 decision_4bc03b20c30f。

## 基本概念

| 名称 | 含义 |
| --- | --- |
| 工作台 | 一个 `workbench_*` 资源，包含标题、说明、创建者（`created_by`）、所属项目、绑定、导航位置和页面源码（HTML）。内置工作台（例如 Portal 开发投影、WALL、Paper）登记固定的页面路径；自定义工作台由用户或投影工坊编写源码。内置身份描述 Portal 入口的归属，不限制页面采用原生组件或投影应用包。 |
| 绑定 | 工作台与 Lineage 的对应关系：`别名 → { lineage_id, residents: { 角色名: resident_id }, events: { 流程别名: Event Source ID } }`。别名 `main` 是主 Lineage。 |
| 角色 | 工作台中一项稳定的职责，对应绑定中的一个 Resident，例如“设计师”“评审员”。角色名由业务 Design 规定。 |
| 流程入口 | 绑定中登记的一个流程别名，指向 Lineage 中的一个事件源；页面通过它启动一段 Lineage 流程。 |
| 修订版本 | 工作台定义每保存一次得到一个新的修订版本（`revision`），已有版本不再改变；发布就是选定一个修订版本作为在线版本。 |
| Projection SDK | 页面脚本可以使用的一组方法，由宿主页面注入。 |

## 页面与 Lineage 怎样连接

### 绑定

绑定中的 `resident_id` 标识唯一的 Resident；服务返回的 `lineage_id` 表示它的当前归属。绑定校验核对这个归属与目标 Lineage，一名 Resident 恰好属于一个 Lineage。Lineage 自身的 `formal/personal` 分类与工作台的角色、布局、显示偏好分别由各自的领域维护，Resident 归属不附加恒定的分类字段。

- **页面通过绑定取得普通 Lineage。** 内置工作台从当前启用的工作台解析绑定；资源类型和项目的讨论页面从 Portal 范围的职责登记解析（decision_6591e7793116）。两种来源由公共解析层处理，页面只声明功能或已授权的资源类型。解析只读取已有的配置；缺少绑定或目标不可访问时失败，不因用户、条目或运行次数新建团队。
- **设置页与实际调用使用同一绑定检查。** 已绑定 Lineage 被删除或无访问权限时，SDK 调用在转发业务指令前返回 `projection.lineage_unbound` 或 `projection.lineage_forbidden`，明确提示检查工作台绑定与权限，并说明刷新页面无法修复此绑定；不得将其显示为可以靠不断重试恢复的任务。503 等暂时性服务错误保留原错误码和可重试性质，不改判为绑定失效。
- **所有被投影的 Lineage 都是普通 Lineage。** 投影定义和业务绑定保存在各自的领域中，Lineage 上没有投影标志、工作台字段或专用类型。一个工作台可以关联多个 Lineage（最多 256 个，每个绑定最多 200 个流程入口），同一个 Lineage 也可以被多个页面使用；数量上限不决定业务怎样划分团队。
- **页面登记、安装或显示前，从业务领域的真实登记同步必需的绑定。** 不按访问者自动创建同名空团队，也不要求普通用户点击“连接团队”来补齐交付缺口。已登记的必需成员被删除、移出或解除绑定后，依赖它的功能明确报错，刷新时不会悄悄创建替身；其他功能不受影响。
- **局部更新绑定只检查这次改动的身份。** 修改绑定时只验证本次新增或改写的 Resident 和事件源；已有且没有改动的失效绑定继续作为 `binding_issues` 显示，但不阻止无关角色的创建和投递。首次创建、启用内置工作台和发布时仍完整检查全部绑定。
- **工作台自己按需创建的角色失效后，下次需要时重新创建。** 已发布的工作台创建一个角色之前，先从绑定中移除由它自己按需创建、而对应 Resident 已不在该 Lineage 中的其他角色，新绑定保存后再忘掉这些角色的创建请求；之后用到这些角色时按普通流程重新创建。只有创建请求记录的 Resident 与绑定中的完全相同时才算“自己创建的”；人手动绑定的角色失效时仍作为 `binding_issues` 报告，不被替换。这样，一个被删除的按需角色（例如 WALL 为某个工程创建的任务角色）不会让之后所有角色的创建都因绑定检查失败（`projection.resident_unbound`）。

### 页面功能与 Lineage 的对应方式

| 页面行为 | 怎样连接 Lineage | 边界 |
| --- | --- | --- |
| 筛选、选择、草稿、布局与比较 | 在页面本地处理，需要时读取真实数据 | 本地选择和进度不写成团队状态，也不需要每次操作都执行 HATG 指令。 |
| 确定性的业务操作 | 调用所属领域的已授权接口 | 不为它另建 AI Resident 或调度器。 |
| 固定职责的 AI 功能 | 通过流程入口触发：事件源 → Effect → 承担这项职责的 Resident | Effect 保存固定的功能提示词，本次输入单独传入（decision_4adcc1ff2f2c）；具体角色和连线由业务 Design 规定。 |
| 持续对话 | Chat Workspace 直接显示、读写绑定的 Resident 的同一个对话 | 首次创建或初始化可以由流程完成，之后的普通消息不需要每轮都经过专门的事件和 Effect。 |
| 多阶段 AI 工作 | 用事件源、Effect 和 Function Block 组合 | 下一阶段只根据本次输入、对应的回复和正式产物继续，不监听共享成员的任意一次完成。 |
| 公共基础能力 | 引用已登记的能力及其原来的团队 | 页面复用能力，不复制基础 Resident，也不因调用能力而获得管理原团队的权限。 |
| 按上下文出现的目标 | 业务领域按明确的业务键解析，首次真正使用时创建 | 页面组件不自己决定身份范围，之后复用同一身份；绑定失效与从未创建是不同的状态。 |

一个角色对应一项稳定职责，一个 Effect 对应一项明确操作，一个成员可以服务多个入口。页面可以依赖其他团队中已授权的成员，绑定如实反映它的归属，不为了让页面看起来完整而创建空团队或复制对话。

固定流程已完整登记、功能提示词未改变时，复用绑定只读取一次当前 Lineage，核对成员、Event、Effect 和连线仍然存在，不获取整个团队的流程安装锁。不同成员的正常调用因此可以并行准备。首次安装、补完未完成的安装和功能提示词更新继续串行提交；被删除的成员或连线明确报错，不自动重建。

### 创建 Resident 与首次发送

- **打开、刷新、读取历史和空消息都不创建 Resident。** Paper、WALL、资源讨论和项目讨论共用同一个“首次发送准备”：页面负责授权目标和提供上下文，公共层在用户第一次真正发送时读取或创建身份。同一用户和同一业务目标复用已有的身份；WALL 的页面缓存只用于显示，不能绕过绑定解析。
- **工作台角色和普通讨论使用同一个 Resident 创建流程。** 角色的逻辑身份由工作台、Lineage 和角色名决定，标题或配置改变不会分配新身份。创建请求在发出前固定下来；结果未知时重发同一请求，只有明确未提交的首次版本冲突才重新准备。创建完成后再次确认成员仍在目标团队中，才保存页面绑定；被删除或移走的成员不会被悄悄替换。
- **角色登记成功前，公共创建流程确保同 ID 的 Agent 与主 trace 已建立。** AgentData 保存该身份的消息和执行历史，主 trace 可以为空；取得成功结果后，工作台再保存角色绑定并发送首条消息。页面不用首条模型回复判断身份是否创建完成，也不在打开或读取历史时补建 trace。登记、首次执行和删除后的历史保留规则见 decision_d19b9909a674 与 decision_b1ab45c4b3ec。
- **普通创建、Fork 和迁移分别使用对应的 HATG 指令。** 角色需要全新上下文时调用 `CreateResident`；需要继承来源上下文时调用 `ForkResident`；调整已有 Resident 的团队归属时调用 `MoveResident`（decision_6591e7793116）。页面按每条指令的接受结果更新绑定，部分失败时保留已经建立的身份和已接受的动作。

### 专属投影的生命周期

资源的专属投影随资源一起结束。每个专属 Resident 的关联明确登记资源根 ID；工作台角色另登记工作台 ID 和精确角色名，流程绑定登记专属 Event、Effect 与连线。一个资源可以有多个用户的讨论 Resident，删除范围覆盖这些已登记的专属身份。标题相似、同处一个团队、曾经参与同一次运行，都不能单独证明归属。

资源提供者先完成删除权限、资源根和业务前置条件检查，再调用投影生命周期服务，成功后删除业务资源。Knowledge 的各类条目（包括 Skill、Plan）、Paper 和 Review 使用同一清理入口；Paper 同时结束被删除的 Review 的专属投影。业务领域只提供资源根与删除时机，不各自实现图清理。WALL 删除条目、取消工程登记以及 TAU 更换执行槽位也复用同一个专属身份与流程释放过程。

清理按当前成员归属读取 Lineage，通过现有 HATG 图编辑一次移除已登记的专属 Event、Effect、连线和 Resident，并完成普通 Resident 删除的后续处理。工作台解除精确角色绑定后同步发布，最后移除调用关联与创建请求。固定 Lineage、Leader、公共功能成员以及被其他条目或角色共同引用的对象保留；专属流程被接入其他消费者时明确报冲突，不能连带删除。

工作仍在运行、队列未空、权限不足或存在无关的未发布工作台修改时，清理失败，资源删除不报告成功。多成员释放可能已完成一部分；剩余关联保留以便重试。图编辑已提交但回执丢失时继续完成同一删除，工作台发布失败时保留资源归属，重试先完成绑定发布，再忘掉关联。清理不会靠重新创建成员补偿失败。

### 调用 HATG 指令

- **页面通过宿主调用 HATG 指令，调用绑定在页面自己的 Lineage 上。** 页面脚本调用 SDK 的 `hatg`，宿主把请求交给 `POST /api/workbenches/isa`。服务端按页面的绑定补上参数：指令需要 `lineage_id` 时填入绑定的 Lineage；给出流程别名时，只允许 `TriggerEvent`，并填入绑定的事件源 ID；给出角色名时，填入绑定的 Resident ID。参数中出现的 Resident 都必须是绑定 Lineage 的成员，否则返回“Resident 未绑定”。
- **改变状态的指令要先由用户确认。** 宿主在 Portal 自己的界面中显示指令、目标和参数，用户确认后才提交；没有确认的请求返回 `projection.confirmation_required`。页面不能订阅流式指令，只能读取一次。
- **SDK 的 90 秒请求预算只计算宿主活动处理时间。** 宿主明确进入人工确认时，以原 `channel` 和 `requestId` 通知 `pending`，SDK 扣除已消耗的活动时间并暂停计时；确认结束的 `resolved` 通知使同一请求继续剩余预算，不重新获得 90 秒。通知必须来自该 iframe 的 `parent`，并匹配当前通道及仍在等待的请求；重复通知不延长预算。
- **确认结果沿原请求返回。** 用户拒绝时不执行变更；确认通过时沿用原业务参数、请求关联和幂等键，一次提交获确认的操作。成功回执交还原来的 Promise，不因人工等待超过 90 秒而丢弃。此保证限于页面和 iframe 仍打开的明确确认流程，不承诺销毁 iframe 或离开页面后恢复待确认请求。
- **活动处理超时表示结果待核实。** 原 90 秒活动预算用完时，SDK 返回 `projection.request_timeout`，提示核实结果并避免重复提交；超时不代表业务确定未执行，也不触发自动重发输入或自动确认。
- **页面不能指定调用身份。** 调用者始终是当前登录用户；页面不能提供 actor、principal 或内部资源配置，也不能用提示词中自称的身份取得权限。调用格式中的 `idempotency_key` 和可选的 `expected_version` 按 HATG ISA 的规则处理（decision_898b8911a2ff）。
- **流程入口按页面版本解析。** 宿主按当前页面版本的绑定把流程别名解析成事件源，确认它仍然存在后执行 `TriggerEvent`；流程别名不是新的指令参数。入口或成员的连接被解除时报错，不自动创建替身。

### 运行结果与产物

- **执行进度以正式的消息 ID 和输入状态为准。** 页面的 AI 请求记录事件、Effect 调用和 Resident 的消息 ID，用 `GetInputState`、输入状态中的 `reply_message_ids` 和对话消息追踪结果；SDK 的 `inputResult` 读取并核对这条输入的全部回复。投递成功、Resident 开始、Resident 结束和正式产物提交是四件不同的事，页面不把按钮回调、请求发出或最后一条回复当成任务成功。完成事件先到、回复还读不到时继续观察，不把暂缺的回复当作空结果；观察时间用完时保留同一输入，只有真正失败或明确取消才结束这条输入。
- **取得成功回执后保存输入 ID，再读取真实回复。** 页面可以用 SDK 的 `state` 持久保存回执中的业务输入消息 ID；`inputResult` 通过 `GetInputState` 取得该输入关联的回复 ID，再用 `GetMessage` 读取并核对回复。人工确认结束和成功投递回执不代替输入完成或真实回复，不能按最后一条聊天消息猜测结果。
- **共享成员同时处理多个请求时，只沿当前请求的因果链继续。** 重试使用原来的幂等键，不改写共享 Effect 中的“当前任务”。
- **生成、优化与反向整理先保存提交身份，再发送一次。** 任务使用既有 `receipt` JSON 字段完整保存 WorkflowBindings 的提交/恢复句柄，保留 request_id、idempotency_key、instruction、instruction_id、Event/Trigger Path、submission_state 和原因等返回事实，不把这些字段直接并入严格的任务进度记录。`save_receipt`、`plan_receipt` 仍只代表 Resident 提交的业务产物。提交结果不明或连接中断时保持 submitting；只有明确未受理才进入 failed。由原提交者恢复时，仅观察原请求，不能再次 TriggerEvent；读取暂缺执行记录不等于未提交。旧的 submitting 记录没有句柄时，按其原 job ID 和绑定重建同一定位键并持久保存，再进行只读观察。取得输入 ID 后沿同一输入继续，完成条件仍要求相应业务资源动作回执。
- **产物按领域对象查询。** 页面显示的长期内容来自领域对象和正式产物，与是不是当前浏览器发起的无关：来自页面、Lineage、定时流程或授权工具的有效产物使用同一套登记、查询和访问规则。已打开的页面在领域数据变化后重新查询，刷新或重新打开也能恢复。任意聊天回复或工作区文件不会自动成为正式产物；产物的归属、类型、来源和提交方式由业务领域规定，投影不通过文件名猜测、扫描无权访问的目录或读取其他任务的最后回复来补齐结果。
- **业务结果由业务领域判断。** 例如投影工坊要求保存页面或反向整理计划的资源动作成功才算完成，输入状态变为完成不能代替业务提交。反向整理和直接编辑画布一样执行普通的 HATG 指令；投影只解析页面中的别名和用户确认，不直接改图，也不增加专用的资源类型或指令。

## 身份与权限

- **正式业务检查验证当前绑定和功能流程。** 工作台管理、Lineage 读取及各项业务操作使用各自的现行授权入口。

- **页面访问、团队操作和领域资源的权限分别由各自的负责方判断。** 公共或项目型页面按相应的资源策略开放；通用框架不把某一种页面的规则推广为所有页面的规则。页面授权不会扩大 Lineage、成员或源资源的权限。
- **工作台不保存所有者列表。** `workbenches.owners` 表和 `owner_ids` 字段已于 2026-10-17 删除；`created_by` 只记录创建者，历史任务和操作保留原来的 `created_by`。谁能改变工作台只由权限系统判定（decision_b820faf42218）。
- **任何 User 和 Resident 都可以打开工作台，能改变它的人由权限系统决定。** 打开包括运行页、设置页和统一资源解析；页面里的数据仍按各自领域的权限读取。保存、发布、删除、启用内置入口、发起 AI 生成和反投影要求操作者是有效的 User 或 Resident，并且权限系统给它这个工作台至少 contributor 级（`Store.authorized` → `_changeable`）。权限系统关闭时，所有有效登录身份都满足这一条；开启时按当前模板判定，判断只看操作者自身，Resident 不因执行别人交来的工作而取得对方的权限。设计师 Resident 保存生成页面时按发起这次生成的人的修改权校验，发起生成时也先检查这项权利。用户拥有某个 Resident，并不让 Resident 的调用身份变成这个用户。
- **目录按 Project 列出工作台。** `/workbenches` 目录列出三类工作台：当前用户能修改的、内置入口，以及当前用户对所属 Project 至少有 viewer 的（由权限系统判定）。草稿只列给能修改它的人，因为其他人既不能运行它，也不能编辑它。权限系统关闭时，所有工作台都列给所有有效登录身份。每个目录条目带 `can_manage`，详情接口也返回它：无修改权的卡片不显示“设置”入口，也不显示版本、发布状态、更新时间和未发布修改；设置页显示“权限系统没有给你修改这个工作台的权限。”，所有编辑控件只读。目录条目还带 `native`（该工作台当前承担内置入口）和 `favorite`；响应中的 `favorites` 按收藏先后列出当前用户收藏、且目录中可见的工作台。工作台收藏与 Resident 收藏同存于 presentation_store 的 favorites（surface `workbench`），通过 `POST /api/workbenches/favorite` 修改：只影响当前用户的目录排列，不授予任何权限；收藏前须能读取该工作台，工作台删除时从所有人的收藏中移除。
- **能管理与默认使用是两回事。** 用户默认使用自己的内置工坊、个人页面状态和最近的请求；有权管理别人的对象，不会自动切换到对方的设计师或使用对方的请求身份。目录和显式操作都遵守统一权限，不能用个人默认筛选掩盖权限拒绝。按用户默认选择的动态目标不代表额外的私有权限；历史消息、任务和产物保留发生时的真实身份。

## 工作台页面的保存与发布

`workbenches.apps` 保存身份、当前版本、发布指针、导航位置与时间；`versions` 保存每个版本的标题、说明、HTML 和源码路径。版本关联的项目、Lineage 绑定与 Resident/Event 目标分别保存到 `projects`、`bindings`、`binding_targets`。读取接口组装页面定义，不再存 `apps.data` 与整份版本 JSON 的重复对象，也不保存旧 owner 观察容器。所有版本及当前/发布指针在迁移中保留。

工作台由 Portal Web 的工作台领域管理，通过 `/api/workbenches/*` HTTP 接口创建、修改、发布和删除；这些接口再调用 ResourceService 的登记、修改和撤销登记，由工作台的资源提供者校验并保存数据。提供者内部不再调用同一资源的公共修改入口。

- **每次保存得到一个新的修订版本。** 新建时保存第一个草稿版本（`POST /api/workbenches/create`）；修改（`update`）时必须提交读到的修订版本 `expected_revision`，版本已经变化时返回 `projection.conflict`（“工作台已被更新，请刷新后重试”）。
- **生成和反向整理的结果只形成草稿。** 生成结果只取可编辑的定义，以任务开始时的 `base_revision` 为基础；模型给出的版本或发布字段不写入。发生冲突时保留生成的内容供合并。用户预览后显式发布。
- **发布只选定一个已保存的版本。** 发布请求只包含 `expected_revision` 和 `published_revision`，两者必须相同，不能与内容修改一起提交，也不产生新的修订版本；发布前完整检查绑定。在线页面的源码、名称和团队绑定取自发布的版本，编辑草稿不影响在线页面；访问授权和导航位置则立即生效。
- **删除工作台只删除页面本身。** 页面、它的版本和用户偏好被删除；绑定的 Lineage 和 Resident 不删除、不停止，已经接受的任务也不撤销。没有成员的 Lineage 仍可以通过卡片或链接打开 HATG；导航中的占位键 `lineage:<ID>` 不能用作 Resident 身份或对话目标。
- **工作台数据保存在 PostgreSQL 的 `workbenches` schema 中。** 工作台领域负责页面定义、发布指针、源码版本、生成记录和用户状态的表结构、查询和事务，不写其他领域的表；数据库连接使用公共入口 `management_common.portal_database.portal_database`（decision_86aed2f0e8c7），事务回滚不会撤销其他服务的动作。用户状态按页面和账号分开保存，每份最多 64 KB，修改它不产生新的修订版本。
- **生成任务保存当前工作流回执。** `workbenches.generations` 用 `event_id`、`trigger_path_id` 和 `message_id` 关联触发事件、Trigger Path 与设计师输入；设计师的实际执行统一由 `agent.executions` 记录。生成表不保留旧 `run_id` 或 `invocation_id` 字段。相同生成请求重试读取原任务和已接受输入，不重复触发；取得工作流回执后必须能够完整持久化，刷新后仍能观察同一任务。历史关联按原事件身份转换为对应 Trigger Path，不能把旧 Run ID 直接当作新路径 ID。

## 内置应用包工作台

Portal 开发投影是 Portal 的共享内置工作台，入口为 `/development`，逻辑入口名为 `development`。入口登记指向一个已发布的 `workbench_*` 身份；页面、SDK、Chat 和功能区继续复用通用投影宿主，不另建运行器。它出现在全站固定导航和工作台目录的内置组，不占个人顶部扩展名额，也不依赖 TFI portal 或其他账号的个人目录配置。不同用户访问同一已启用身份，数据和操作仍按当前用户授权，本地页面状态及草稿仍按用户隔离。

Portal 开发投影和投影工坊是核心内置工作台。Paper、WALL、Test 等业务内置工作台由所属功能登记（`workbench.builtin`，decision_15aab18c0ab3），Portal 不带该功能时没有这个内置入口；页面从 Web 写入的前端清单读取当前安装的内置工作台及其地址，打开功能工作台的地址时初始化它的权威登记。

工作台是不是 Portal 内置入口由独立的启用操作决定。将已有应用包登记为内置工作台时，保留资源 ID、修订、发布指针、构建产物和团队绑定，不复制页面或创建替代团队。通过独立的启用操作指定已登记的 builtin 名、expected_revision 和 previous_app_id；当前修订须已发布，绑定与领域前置条件须通过，入口比较交换与 builtin 归属变更在同一事务提交。冲突或校验失败不留下半迁移身份；已启用入口不能直接删除，也不能改作另一逻辑入口。

旧的 `/workbenches/view?id=…` 地址继续打开同一资源并选中内置导航项。内置入口及旧资源地址都支持已有 region 深链接；在本页使用 SDK 导航时原地聚焦功能区或门面对话，不刷新已装配 iframe。缺少入口登记或无权读取时明确失败，不回落到个人工作台、空团队或新建页面。

## 页面外壳、导航与宿主

- **工作台使用 Portal 公共的页面外壳。** 包括使用当前站点配置名称的公共顶栏、账号菜单、主题和基础控件；页面源码只提供业务部分，不另做顶栏、品牌栏或 Workbench 框架。业务分区、图表、选择和草稿可以自定义。
- **顶部导航中的入口名为 Workbenches。** `/workbenches` 是独立目录，与 Resource、Project 等集合页使用同一套集合看板（`portal_collection_board.css`、`portal_board_toolbar.css/.js`）：页面不设标题区，顶部是共享看板工具栏，包含搜索框、“筛选”下拉中的全部／已发布／草稿单选、刷新、创建工作台和结果数；下方按分组列出工作台卡片。分组依次为“收藏”、各 Project（按组内最近更新时间排列）、“未归属 Project”和“Portal 内置”；内置组放在最后，因为顶部导航已经提供这些入口。收藏组按收藏先后排列，其余组内按更新时间倒序；分组可以折叠，刷新后保留搜索词、筛选和折叠状态。卡片右上角的星标（与 Resident 收藏相同的图标和文案）加入或取消收藏，收藏的工作台只出现在收藏组；写入失败时卡片回到原处并提示，星标保持键盘焦点。每张卡片显示名称、星标、发布状态（已发布 vN／草稿 vN，内置项不显示）、更新时间、未发布修改与顶部导航等标记、说明，以及主绑定 Lineage 的团队行；发布状态、更新时间和未发布修改只对能修改该工作台的人显示：Leader 头像、Lineage 名称（链接到 Society 页）、成员数和当前工作／排队数。一个工作台可以绑定多个 Lineage：团队行以 `main` 绑定（没有时取第一个绑定）为主，其余绑定的团队显示为“+N 个团队”，悬停时列出团队名称。工作数和排队数优先取 Leader 的 Family 活动汇总，没有时取 Lineage 的运行状态计数。卡片先显示，团队信息随后用一次 Lineage 列表读取加上 Leader 状态和头像补齐；读取失败只在团队行显示“团队信息暂不可读取”，目录照常可用。搜索覆盖名称、说明、Project，以及全部绑定团队的名称和 Lineage ID；数量和空态由完整加载后的当前可见数据计算。目录只读取一次工作台列表就显示卡片：内置入口按服务端标记的 `native` 列出，打开目录时不逐个检查内置入口的团队绑定，这项检查留在各内置页面自己的入口。目录列表读取失败时，目录整体进入明确的不可用状态，提供重新加载入口和可展开的错误详情，不把部分结果计作完整目录；重试成功后恢复目录与搜索焦点。已发布项打开运行页，草稿继续编辑，点击卡片空白处等同主操作，每项均可进入页面设置。目录不挂载创建表单或预览宿主。投影工坊（`studio`）是“创建工作台”背后的设计模块，打开它就是 `?panel=studio`，目录不再单列它的卡片；能修改它的人在 `?panel=studio` 页标题栏看到“投影工坊设置”入口。`?panel=studio` 聚焦团队与需求，`?panel=settings&id=…` 聚焦名称、导航、保存与发布，高级源码／授权绑定及反投影按需展开，均可返回目录。这两个编辑页与 Society 页使用同样的面板工作区：满宽满高，顶部一条紧凑标题栏（“← 所有工作台”、工作台名称和一句用途说明），下方左侧是设置面板，右侧是撑满剩余高度的预览面板。两个面板沿用 Portal 面板的边框、圆角和灰底面板标题栏；设置面板内的各节以分隔线堆叠，折叠项是带箭头的标题行，内容超出时只在设置面板内滚动。预览面板标题栏在页面已发布时提供“打开工作台”。窄屏时两个面板上下排列，整页滚动。`/workbenches/view` 保留原有运行宿主与 Chat。目录展示和本地筛选由 `portal_workbench_catalog.js/.css` 唯一负责，数据加载、编辑与运行路由由 `workbench_studio.js` 负责，模板统一声明脚本依赖。桌面和窄屏均须支持键盘导航、长标题与搜索空态。每个页面的导航位置为 `menu`（菜单中）、`top`（顶部）或 `hidden`（隐藏），修改后立即保存并刷新导航，不受发布版本影响；顶部最多显示 4 个已发布的自定义页面，其余在菜单中；隐藏只是不在导航菜单中显示，`/workbenches` 目录仍列出该页面以便进入设置，不撤销访问权。
- **Society 页面可以把工作台作为一种编辑器打开。** Society 页面按当前团队找到相关的工作台，把它们与 Chat、HATG、Preview 并列加入公共组件选择器（Workbench 的 `setEditorTypes`）；关闭组件只关闭视图。绑定配置和团队链接集中在“页面与绑定设置”中。投影身份 `projectionId` 与公共容器上下文 `workbenchId` 是两个不同的值。
- **自定义页面运行在隔离的 iframe 中。** iframe 设置 `sandbox="allow-scripts allow-forms"`，没有同源权限；内容安全策略禁止网络连接、外部脚本、表单提交目标、子 frame 和 `base` 地址，页面不能 `fetch`、读取 cookie 或本地存储。宿主在页面脚本之前注入 SDK，并校验消息来自这个 iframe 和独立的通信通道。宿主负责身份、绑定和确认，页面负责业务布局和本地交互。
- **Projection SDK 提供**：`context()`（页面与绑定的上下文）、`hatg(...)`（调用 HATG 指令，见上文）、`eventInputIds(receipt)`（从事件回执中提取已执行 Effect 投递的输入消息 ID，并去重）、`inputResult(...)`（读取一条输入的回复）、`resource("query" | "read" | "resolve" | "read_many" | "resolve_many", …)`（查询资源、读取资源内容，或解析一个或一组资源地址；只支持这五种只读操作。`resolve` 只返回当前用户能否读取该地址、地址指向的资源类型、标题和页面链接，不返回正文，供页面核对对象引用和证据地址）、`state(value)`（读写当前用户在这个页面上的状态）和 `openLineage(binding)`（打开绑定的 Lineage）。

投影宿主的资源正文入口为一次完整快照设置固定的 16 MiB 预算，并显式传给 ResourceService；该预算独立于应用包资产大小，也不改变 ResourceService 的通用 4 MiB 默认值。页面不能提高预算或指定调用者。每次读取仍先校验工作台访问，再以当前用户解析和鉴权目标资源；返回完整原始字节的 SHA-256，供应用与其固定来源描述符核对。超过预算明确失败，不返回截断正文，不改读其他版本。结构化 YAML 读取采用同一预算与原始字节哈希。

批量资源操作用于在保留逐来源授权的前提下减少宿主 HTTP 往返。每批接受 1–128 个完整地址，按输入顺序逐项执行；重复地址仍分别授权，不用根资源授权、先前解析结果或其他条目的成功替代当前地址权限。调用者始终由宿主当前身份决定，工作台访问在批次开始及返回前复核；末次复核失败丢弃本批结果。批次不构成跨资源事务或统一授权快照，逐项读取时的权限与状态可能不同。

`resolve_many` 的成功项与单项解析一样只含可读性、资源类型、标题和页面链接；拒绝、不存在、暂不可用等失败按地址保留错误码及状态，不伪装成可读或静默遗漏。`read_many` 直接调用带完整地址鉴权的正文读取，避免额外解析往返；整个批次的原始正文累计预算固定为 16 MiB，每项使用剩余预算，完整正文及其 SHA-256/字节数同时返回。已读字节即使解析失败也消耗预算，超限不截断，预算用尽后不再发起读取并为后续条目返回明确错误。调用方不能扩大预算。

批次结果按顺序给出每地址成功值或失败状态及错误对象，同时报告已读字节数和预算；HTTP 成功只代表批次封装成功，不代表全部地址成功。无效参数及工作台权限失败使整个请求失败。应用仍逐项核对固定来源描述符、完整字节数与哈希，限制批次并发并处理部分失败。销毁、失活或取消时应用停止提交后续批次并丢弃过期响应；已发出的宿主 HTTP/资源读取可能完成，不能把本地取消表述为服务器已中止读取。

## 从页面反向整理 Lineage

通用分析可以记录职责调整建议；工坊当前可应用的结构化计划仅支持新增 Resident、受限组件和连线，具体操作白名单、步骤限制、确认与恢复合同由 decision_4bc03b20c30f 定义。移除、迁移归属、授权或停止任务等建议不进入这一计划的执行序列，需要作为独立工作使用对应正式能力完成。

用户把自己的 Lineage 做成页面后，可以在页面初次成型、功能增减或流程迭代时请求反向整理。只改样式、布局或筛选时通常只影响页面；只有职责、AI 动作、对话目标、结果约定或协作依赖发生变化时，才需要调整 Lineage。

| 阶段 | 输入与产出 |
| --- | --- |
| 读取基线 | 读取有权访问的页面源码与版本、业务 Design、当前绑定、Lineage 版本和相关运行记录；明确分析的是草稿还是已发布的页面。 |
| 整理操作 | 依据页面的实际功能和调用链，区分本地交互、确定性业务、AI 功能、持续对话、创建与初始化、产物展示；截图和按钮名称只作为线索。 |
| 对照已有团队 | 找出可以复用的成员、事件源、Effect、Function Block 和领域能力，保留稳定的身份和历史，标出缺失、重复或放错位置的职责。 |
| 生成差异方案 | 同时列出页面、绑定、Lineage 和所属业务 Design 的修改；说明新增、复用、移除、权限影响，以及需要能修改该工作台的人决定的问题。 |
| 确认并应用 | 能修改该工作台的人审查后，核对页面版本、绑定和 Lineage 版本，再通过 ResourceService、HATG 指令和领域接口分步应用；出现冲突时保留方案并重新核对。 |
| 验证两个方向 | 确认页面和 Lineage 能执行相同的业务能力、持续对话复用同一身份、不同入口的产物都能找到、本地交互没有多余的副作用，并检查旧页面和进行中的任务。 |

- **只提出与本次工作相关的改变。** 反向整理优先复用已有结构，不按按钮数量创建 Resident，不把每个前端回调翻译成节点，也不重建整个团队。新增或移除成员、改变共享的提示词、迁移归属、修改权限、停止进行中的任务和产生外部影响的操作都要在方案中逐项列出，不能借页面优化顺带执行。
- **使用现有的 HATG 原语和公共流程。** 缺少通用能力时单独提出 ISA 改进建议，不把业务字段或页面特例放进指令内核。绑定关系和产物约定写回页面的业务 Design，本篇只维护通用规则。
- **页面与 Lineage 之间没有跨服务的原子事务。** 应用过程保存每一步的接受回执、版本和验证结果；部分失败时保留已有的身份和已经接受的动作，再有控制地修复。回滚页面不能撤销已经投递的任务。代码发布、权限变更和真实业务运行是独立的动作，分析或生成方案时不会自动发生。
- **多个页面使用同一个 Lineage 时，方案列出对其他页面和进行中任务的影响。** 未确认或未验证的方案保留为草稿。对整理后的同一基线再分析一次，应当得到没有实质差异的结果；页面以后更新时可以再次整理，形成持续的演化。
