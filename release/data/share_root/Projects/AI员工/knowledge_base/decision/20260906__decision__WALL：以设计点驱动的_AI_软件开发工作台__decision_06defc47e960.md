# WALL：以设计点驱动的 AI 软件开发工作台与条目身份生命周期

WALL 把软件工程中的设计、改进建议和当前进展铺成一面可以浏览、讨论和操作的墙。开发者主要决定软件往哪里发展，并体验开发结果；Resident 持续维护设计、实现代码、验证功能和推进发布。

## 设计理念

AI 可以持续工作，人的时间和注意力有限。WALL 希望让人用少量操作表达清楚的意图，让 AI 自主完成具体工作。页面优先展示值得关注的方向、改进、冲突和可体验的结果，日常纠错由已获授权的 Resident 处理。

Markdown 是人与 Agent 共同使用的内容来源。墙上的卡片来自工程索引引用的文档；用户修改卡片，也是在修改这些文档。工作可以从直接修改设计、提出新功能、发现错误或认可演化方向开始。

## 基本概念

- **工程**是接入 WALL 的软件源码目录，包含设计和改进文档的索引。Portal 是首个接入工程，后续可以注册其他工程的根目录。
- **设计规范与设计点**分别是说明软件如何工作的 Markdown 文档，以及其中一项可独立理解的设计说明。Portal 的规范登记为 `decision_*` 知识库资源，由 `SPEC.md` 索引。
- **改进计划与改进点**指同一个值得独立审查的显著变化。每份 Plan 完整叙述一个改进，包含理解它所需的背景、问题后果、预期体验、方案边界与成功检验；内部细节继续属于该改进。Portal 的计划登记为 `plan_*` 资源，由 `IMPROVE.md` 索引。Design 可以包含多个设计点，Plan 与 Design 不设数量配额或一对一映射。
- **不一致点**指出当前实现和规范描述的差异，供人或 Resident 判断修改哪一方。
- **演化方向**说明希望软件如何发展，可以关联多个设计点、改进点和不一致点。
- **Block**是墙上的矩形卡片，显示上述内容。颜色表示内容类别或进展，深浅表示重要性，面积表示来源文档的 `metaness`。该可选字段为 1–10 的整数，数值越大越偏向定义、组织或治理其他对象的规则；它与重要度、紧急程度及实现时间分别评价。
- **Resident**是保留身份、对话和工作知识的 AI 协作者。**Lineage**是一组共同工作的 Resident；成员关系不局限于 fork。
- **Which Resident**根据工作内容推荐合适的 Resident。**HATG Instruction**是 Portal 提供的协作指令，可用于创建成员、连接工作并启动执行。
- **Dev**是正在开发、可以体验当前改动的版本；**Release**是正式使用的版本。**TAU**让 Agent 从真实用户入口使用软件，记录结果并发现问题。

## 设计点

### 软件开发工作区

- **WALL 与 Test 位于 Portal 开发投影中。**页面左侧复用共享 Activity Rail，依次提供开发投影、WALL 窗图标和 Test 盾牌图标。墙面组织设计、改进与演化方向，Test 提供测试目录、用例、运行、TAU、门禁组合和覆盖审查；测试面板的内部行为由 `decision_f2a6a5dd4646` 说明。Portal 主导航使用开发投影入口，WALL 不再拥有独立文档页面。
- **切换保留当前工作。**三种工作区在同一页面内切换可见性，WALL/Test 首次选中才加载其原生组件；返回开发投影保留区域 iframe、Chat 和草稿，返回墙面或 Test 保留筛选、选择和未启动计划。隐藏的工作台工具与面板生命周期同步停用，墙面轮询在返回时恢复。切换不会创建测试 Run 或重新投递已有任务。页面组合不迁移业务数据：WALL/Test 保留原 workbench 身份、修订、功能入口、绑定和所属 Lineage，各自按当前用户进行业务鉴权。
- **入口可直接定位内容。**`/development?view=wall` 打开墙面，`/development?view=test` 打开 Test；未指定 view 的 `/development` 打开开发投影。旧 `/wall` 和 `/wall/` 作为兼容入口以 302 转到新地址，只保留 view/project/block/semantic/case/run 参数；有效 view 优先，没有有效 view 的 case/run 链接进入 Test，其他进入 WALL。浏览器前进后退同步视图选择。兼容入口服务于既有资源链接，只有调用者和已有外部链接完成迁移后才能删除。领域 API 保持 `/api/wall/*` 与 `/test/api/*`。

### 浏览与注意力

- **工程以目录注册。**用户输入软件工程根目录接入 WALL。首期只预先登记 Portal，沿其现有索引读取全部文档，实际数量随内容变化。 跨工程查找设计点时，已登记但目录已删除或不再是目录的工程不阻断其他工程的解析；没有找到可访问的绑定目标时返回不可用状态。
- **点来自文档正文。**绿色卡片显示 Design 中的设计点，橙色卡片显示完整 Plan，紫色显示实现与规范的不一致。Plan 内的章节、清单、证据和表格共同构成同一张卡片的完整内容，打开后可以连贯审查前因后果。设计点无需另建代码文件或测试用例文件。
- **索引条目区分主目标与证据。**普通列表或段落条目只把第一个 Markdown 目标交给统一候选验证器，后续链接只提供说明、报告和证据。验证器优先服从 frontmatter／`wall` 元数据和专用 `.wall` 文档类型，并排除文件名或一级标题明确表示报告、审查、审阅、审计或证据的辅助文档；这些辅助文档即使作为独立首链接，也不生成改进 Block。表格按单元格识别各自第一个目标，使同行 Design 与 Plan 可以建立模块关联。用于稳定地址但不承载正文的空 HTML 锚点可以位于前导元数据两侧或一级标题之后；WALL 保留来源文件，但不把锚点字面量显示在正文和预览中。
- **墙面向右延展。**不同宽高与面积的矩形在可用高度内紧密铺排，整个内容流从左向右延展。布局按 `metaness` 分配面积，避免将不同层次强制放入整齐的等大网格；相邻矩形共享边界，以细线分界，不产生内部空洞。阶段标签、聚类标题和点数合并在同一标题行。横向滚动、触控滑动和鼠标滚轮用于浏览后续内容；较小的视窗保持正文和操作可达。
- **面积与分组共用同一几何规则。**在相同视窗和缩放下，一张 M1 卡片的面积 A 等于基础宽度乘以最小高度；元层级 m 的卡片面积为 `A × (m + 1) / 2`，M10 为 5.5A。重要度和类别不改变面积。分组内部按原有排序切成连续加权条带，以有界动态规划选择宽高比例，保持最小可读尺寸。相同阶段的连续稀疏分组可上下共用列，各自保留标题；分组数量较少或视窗过矮时，优先保证面积、顺序与可读性，外缘允许余白。卡片之间不插入填充块，也不逐卡测量 DOM 反复试排。
- **阶段从左向右排列。**改进、Dev 已完成、设计、不一致依次展示，形成从建议到实现、再到现状核对的阅读方向。领域、文档和关联方向的聚类，以及重要度排序，都在各阶段内部进行；演化方向与改进放在同一阶段。
- **卡片紧凑并可直接打开。**标题、正文摘录和重要度共同利用卡片空间；摘录按卡片可用高度展开，去除重复的首标题，较大的块能展示更多背景，不受固定短摘要长度限制。来源与常用操作紧跟正文排在底部同一行，卡片最小宽度同时容纳可辨认的来源名称与当前语言的操作文字，不能把来源挤成单字加省略号。基础面积随最小可读宽度同步调整，保留加权面积比例、条带填充与阅读锚点，不逐卡测量 DOM。正文与操作之间、操作下方均不保留额外空白层。有关联 Resident 时，在卡片顶部显示 Resident ID 链接，详细任务状态放在详情中，不另占一行运行说明。点击卡片正文或空白处展开详情，点击 Resident、来源、操作按钮或选择文字时分别保留对应行为。
- **工程选择与搜索放在同一行。**顶部集中展示工程选择、搜索和工作操作，工程选择框与搜索框等高对齐；下一行提供类别、SPEC 模块、重要度、阅读状态和审核状态筛选，以及聚类、排序与缩放，墙面保留更多可用空间。
- **蓝色显示 Dev 中的成果。**蓝色表示当前 Dev 已实现、尚待发布的工作，用户可在体验后直接选择发布。WALL 不给每项功能附加独立构建或代码版本绑定。
- **重要性由语义判断。**Resident 根据每个点的影响范围、必要性和预期价值建议 1–10 分，并说明理由。同一文档中的点可以有不同分数，人可以修改分数且手动值优先。同类卡片使用可明显区分的颜色深浅表达重要程度，分数越高底色越深；明暗主题下均保持文字和操作可读。重要度筛选支持全部或指定最低分，与其他筛选共同生效。
- **Meta 层次由来源文档继承。**普通功能、界面和直接工程协议通常为 1–3；描述其他设计或知识如何被生成、组织、评价与治理的规则可使用更高分。未来方向只有内容确实更 meta 时才提高评分。Design 中的所有点继承同一文件评分，Plan 整文使用自身评分；缺省合法，墙面按 1 展示。显式非法值显示诊断并暂按默认尺寸展示，保留正文，不自动猜测或改写文件。
- **元层级可以独立筛选。**筛选栏提供“全部”和 M1–M10，选择一个层级后仅保留该层级的点，并与模块、类别、重要度、阅读状态、审核状态及搜索条件共同生效。缺省 `metaness` 按 M1 参与筛选；显式非法值只在“全部”中显示并保留诊断。筛选只改变已加载卡片，不触发模型任务或文档修改；选择通过共享 Page State 保存，重新进入和刷新后恢复有效值。
- **用户可以查找内容、缩小范围或调整阅读尺度。**墙面支持关键词与语义搜索、筛选、聚类、排序和语义缩放。缩放改变阅读尺度，语义搜索按自然语言问题查找相关点，两者各自独立。

  模块筛选按索引中的二级标题（`##`）列出一级模块，按三级标题（`###`）列出其下的二级模块。选择一级模块时包含其全部子模块，也可以只选择一个二级模块；选项顺序跟随索引。改进 Plan 同行关联的 Design 归属唯一模块时沿用该模块；其他 Plan 使用自身在 `IMPROVE.md` 中的章节归属，无需为分组创建一一对应的 Design。

  模块选项来自用户可读的点，与类别、重要度、阅读状态、审核状态和搜索结果共同生效。选择模块只筛选已加载的数据，不启动 AI 或重新扫描文档。文档还在读取时先保留选择，确认模块已消失后恢复全部模块；切换工程时也从全部模块开始。
- **排序由用户选择。**排序只提供“重要”“标题”和“最近打开”，默认按重要度从高到低排列，同分时按标题排序；不提供“推荐”项。“最近打开”让当前用户最近成功打开详情的点排在前面，再次打开会前移，尚无打开记录的点接在后面并按重要度、标题排列。排序在既有阶段与聚类内部生效，保持墙面从改进到不一致的阶段方向。
- **离开后保留显示配置。**模块、重要度、元层级、阅读状态、审核状态、聚类、排序和缩放通过共享 Page State 保存，下次在同一浏览器以同一用户进入时恢复有效选项。模块选择同时关联当前工程，其他显示选项在切换工程时继续沿用；失效值回退当前默认值。刷新墙面不重置这些选择。
- **阅读状态可以筛选。**阅读筛选提供“全部”和“未读”，未读判断与卡片小圆点一致，并与模块、重要度、类别及当前搜索结果叠加。成功确认当前内容已读后，该点从未读墙面移除，已打开的详情继续保留；读取或确认失败时继续显示，后续内容变化可再次进入未读集合。
- **用户可以标记已审核。**所有类别的卡片和详情都提供“已审核”复选框，用户可勾选或撤销，表示自己已检查当前内容。记录按用户和工程独立保存；打开详情与审核分别记录，审核不改变实现、发布或自动推进的权限。
- **审核状态可以筛选。**审核筛选提供“全部”“未审核”和“已审核”，与模块、重要度、阅读状态、类别及搜索结果共同生效。保存成功后，卡片按新状态进入或离开当前筛选结果，已打开的详情继续保留；新点和内容变化后的点显示为未审核。
- **语义搜索复用 Resource 体验。**输入文字时保留即时关键词筛选；点击语义搜索按钮或按 Enter 才发起后台语义任务。任务面板复用 Resource 页的共享实现和样式，显示运行状态、结果数及刷新、删除操作。用户选择有结果的已完成任务后，墙面展示其匹配点，并继续应用现有筛选和所选排序；零结果或失败任务保留反馈但不可选。继续输入关键词会退出当前语义结果，切换工程后只显示新工程的任务。
- **方向关联具体工作。**方向和其他内容都按文档 `metaness` 获得面积，类别不替代层次评分。缩放和展开让用户在整体目标和细节之间切换；关联点较多时，列表在卡片内滚动，底部操作保持可达。
- **未变化的文档复用已有结果。**进入墙面先显示已有缓存，后台按索引和来源文件的变化更新内容；首次没有缓存时显示加载状态。手动刷新提前检查文档变化，卡片操作后的数据刷新继续使用未变化的文档缓存。
- **布局缓存与卡片元素的生命周期分开。**工程切换、重新选择工程或刷新登记列表后，即使条目 ID、分组和面积权重相同，也必须把已有布局应用到重新创建的卡片元素，保证卡片互不遮叠、操作按钮可点击；可以继续复用几何计算结果。
- **新增和变化的点提示未读。**新加入、标题或正文变化、转换类别或进入 Dev 已完成阶段的点，在右上角显示小圆点；一项工作产生多个结果时，各结果分别提示。小圆点沿用 Lineage 的未读视觉样式，卡片底色继续表达类别与重要度，阅读记录由 WALL 按用户和工程独立保存。

  打开详情、成功读取当前正文并保存已读记录后，清除该版本的提示。首次建立记录时，以一次完成且没有读取错误的扫描结果为基线，后续新增和变化再提示未读。单纯浏览墙面、调整重要度或更新工作运行状态保持原有阅读状态；重新进入页面或更换设备后继续使用服务端记录，读取或保存失败时保留提示。

### 讨论与工作

- **常用操作直接放在卡片上。**改进点提供“请实现”，蓝色成果提供“发布”，不一致点提供“改规范”和“改实现”。用户可以连续选择多个不同的点开展并行工作。
- **运行中的卡片有轻量动画。**WALL 工作或该点已关联的 Chat Resident 实际运行时，卡片底部的一小段主题色状态线持续横向移动，底色、文字和边框保持原有样式。仅在详情对话中发送消息也会触发动效，无需点击“请实现”；关闭详情、重新进入墙面后继续按实际状态显示。两种工作同时运行时共用一条线，其中一项结束后，另一项仍在运行就继续移动。没有实际运行、只有排队、准备或停止过程时显示静态状态线，全部结束后移除提示。动效遵循用户与系统的动画偏好，减少动画时使用静态线条，卡片点击、文字选择和操作按钮继续可用。

  纯讨论只影响卡片的活动提示，保留原类别、重要度、已读状态和 WALL 任务结果，不生成 Dev 成果或额外的 WALL 任务。讨论的停止操作继续由 Chat Workspace 提供，卡片上的工作按钮仍按原有 WALL 任务状态与权限展示。
- **每个点直接展示对话框。**打开详情即可看到原文、出处和 Chat Workspace。已有 Resident 时读取其对话；尚未关联时先显示可输入的空对话框，首次发送消息后再创建 Resident 并初始化会话。后续消息复用该成员，附件、引用、快捷发送、队列与工作活动沿用 Portal 已有对话能力。

  同一用户围绕同一工程、同一个点的讨论复用已关联的 Resident；这里复用的是对话组件和当前用户的工作关系。文档标注的工作成员在打开详情时由 SocietyService 检查当前用户的访问权限；用户没有可访问的关联对话时，先显示空对话框，首次发送再准备自己的讨论成员。墙面轮询只读取当前用户已有的讨论与工作关联，任务分配不会把原讨论切换到实现成员。

  实现任务已投递并取得 `message_id` 后，对话区显示“讨论”和“实现中”两个标签：前者保留原 Chat Workspace，后者连接任务对应的 Chat Workspace。默认继续显示讨论，首次选择实现标签才加载该成员的对话；选择标签不创建 Resident 或重复发起实现任务。两个面板复用共享 Chat 组件，消息、草稿和附件各自保留，发送只针对当前面板的真实 Resident，键盘方向键也可切换标签。完整正文编辑和对话切换各自独立。

  尚未投递的任务只保留原讨论；即使已分配 Resident，排队、路由、准备中及投递前失败或取消均不显示实现标签。历史记录只有 Resident ID、没有任务消息记录时也不显示“实现记录”，不主动加载该实现对话。

  任务结束后保留“实现记录”标签，方便继续查看结果；正在查看实现对话时不因任务结束跳回讨论。任务更换 Resident 时连接新成员，旧草稿留在原成员的工作区，不自动带入新成员。实现对话读取失败或不可访问时只在该面板显示错误，原讨论及草稿继续可用。既有历史记录中两种角色指向同一个 Resident 时按真实身份展示，页面不伪造两份独立会话。
- **阅读和输入保持连续。**相同数据返回时，卡片和状态区保留现有元素，选中文字不会因轮询消失。草稿按工程和点分别保存；发送失败或准备会话期间关闭详情时，已输入的内容继续保留。
- **出处在当前页面展开。**点击卡片或详情中的 Design、Plan 来源，打开已有的资源详情面板，显示完整文档和原有操作。关闭资源详情后继续浏览原来的 Block，墙面位置和对话草稿保持不变。 工程内 Markdown 来源也可点击，按当前工程索引与路径边界重新读取完整正文，在共享详情浮层中展示。未登记来源、越界路径和无权读取时显示错误，不回退读取任意文件；关闭原文后保留原点的编辑草稿。
- **人和 AI 都能提出内容。**用户可手动新增、修改设计、改进、方向和不一致点；WALL 的 Resident 也持续维护这些内容。具有维护权限的用户点击 Block 后，在详情左侧直接编辑标题、Markdown 正文、重要度和关联点，右侧保留 Chat Workspace；编辑直接在详情中进行，没有单独的编辑按钮或弹窗。只有完整正文读取成功后才启用表单，只读用户继续查看渲染后的原文。

  保存 Design 正文时只修改当前点，保存 Plan 时修改完整文档；修改 `metaness` 属于来源文档属性变更，该 Design 的其他点同步继承新值。成功后停留在详情并显示服务端返回的内容，失败保留输入与错误提示。墙面轮询和工作状态刷新不覆盖编辑草稿；关闭、取消或切换到其他点时，存在未保存的修改就使用共享 Dialog 提醒。保存期间避免重复提交或关闭；权限变化后停止写入并保留当前输入。新增点、登记工程和自动推进设置继续使用各自的表单入口。
- **实现交给合适的 Resident。**Which Resident 提供领域推荐；任务由对应成员或为该任务创建的成员推进，HATG 可进一步组织协作。不同卡片可以由不同 Resident 并行工作。
- **Resident 协调共享代码修改。**现阶段工作直接发生在当前工程工作树，成员通过上下文、代码现状和协作能力处理交叉修改。专门的分支与并发管理可在实际出现需求后再引入。
- **完成或否定改进后整份 Plan 退出候选。**实现完成或用户否定、删除改进后，WALL 把原文标为 `obsolete` 并移出 `IMPROVE.md`。原文保留完整上下文以供追溯，其他独立 Plan 不受影响；不在一份 Plan 中逐条删改建议。Dev 中的完成说明仍以 Markdown 保存。
- **最近完成的工作可以直接找回。**顶部“最近完成”入口显示当前用户在当前工程中最近完成的 20 项工作，按完成时间倒序排列，保留原工作标题、完成时间、结果摘要和可用的成果、Resident 或 TAU 报告入口。查看成果直接复用 Block 详情，即使该成果被当前墙面筛选隐藏，也可以打开。关闭详情后返回完成列表，墙面的筛选、搜索和阅读位置保持不变。

  完成列表来自服务端已有工作记录，原 Plan 退出候选、审核状态变化或用户刷新页面后，完成记录继续保留。没有独立结果 Block 的工作仍展示摘要及可用的其他入口；结果后来被移除或访问权限变化时，详情说明读取失败，完成记录继续提供工作上下文。列表按现有墙面刷新节奏更新，工作完成不会自动打开弹层或移动墙面。
- **当前规范可以编排为发布文档。** 顶部“生成发布文档”提供当前工程规范的预览与 Markdown 下载；来源、权限与失败边界见下文“当前索引生成发布文档”。

- **改进与设计不是一对一关系。**一次改进可以新增多个设计点、更新现有描述，也可以只修正代码而不增加设计点。Resident 根据实际结果决定文档改动。
- **设计可以被抛弃。**用户选择抛弃设计点后，Resident 删除对应功能实现并更新规范；工作结果和未解决问题回到该点的对话。
- **重写、拆分或合并后，由 Resident 判断哪些点继续保留。**Resident 根据内容含义区分原有点与新内容，并维护相应联系。程序提供正文与来源，不用文字哈希替代语义判断。

WALL 工作记录保存原 Resident、输入消息、事件及 `trigger_path_id`，用于继续观察已受理的同一任务和查看触发过程。工作结果与错误保存在 WALL 自己的业务记录中，Resident 的执行正文由 Agent 保存。历史记录迁移按所属 Lineage 和实际事件精确关联 Trigger Path；已无法找到对应路径时保留原事件、输入和工作结果，不伪造路径，也不重复投递任务。

### 自主演进

- **人控制方向。**用户认可或调整方向后，Resident 自主拆解、实现和验证已授权的相关工作。目标冲突、重大代价或超出授权的事项再请求人判断。
- **结果反过来改进方向。**实施和使用中的发现可以修正方向，产生新的建议或更新已有设计；方向及其关联内容继续保存在 Markdown 中。
- **后台持续发现和维护。**工程可启用周期性分析，Resident 阅读设计、计划和实现，仅将能明显改善实际任务或系统能力的变化写成独立 Plan；无足够价值或证据时不创建条目。实现细节、轻微文案或单纯文件拆分不能用于凑数。周期可调整，后台分析不随页面轮询反复启动。分析的成果是 WALL 文档：发现的不一致或缺陷如实记录后分析即为完成，未修复的问题写入结果说明，不因被分析工程本身未通过验证而返回 blocked；只有分析本身未能完成时才是 blocked。
- **无发现的说明放在结果摘要。**没有值得登记的改进、不一致或方向时，无须生成卡片或点来源文件；补充验证报告可以从实际点的正文引用，只有“未发现问题”说明的报告不加入 WALL 点来源索引，避免被当成格式错误的工作文档。
- **TAU 验证真实使用。**Resident 根据设计点组织实际使用测试，记录问题并继续修复。已获授权的日常错误可以自动修正，页面聚焦需要关注的结果，详细工作仍可查询。
- **发布也是 Resident 工作。**点击发布后，发布 Resident 围绕所选成果及必要依赖确定实际文件范围，调用工程的小批量同步入口。Portal 遵循 `decision_08bb2d9141f9`，不要求工作区干净、全功能完成或全量测试。成功结果给出完整 publication_commit，WALL 校验它已进入 Release 分支后，只处理当前任务对应的成果。

## 当前索引生成发布文档

发布文档是按工程 SPEC 索引编排的 Design 正文集合，用于阅读、交付前检查和保存设计快照。WALL 拥有生成入口和预览，知识库继续拥有 Design 正文。下载文件包含目录、设计章节和来源清单；生成不调用模型改写设计，也不把未确认的取舍变成当前规则。

- **用户可以在工程工具栏生成、预览和下载文档。** 预览按纯文本显示 Markdown，下载内容与该次预览一致；关闭预览或切换工程会丢弃页面中的结果。
- **生成继续使用当前登录账号的读取权限。** 服务先检查登记工程的 viewer 权限，再以相同 actor 读取每份资源；任何来源缺失或不可读时整次失败，不静默跳过，也不把之前成功生成的结果用于此次失败下载。
- **生成范围仅由登记工程的当前 SPEC 索引决定。** Design 按索引顺序和模块归属编排，同一来源去重；未列入索引的文件、改进 Plan、索引之间的互链和 thinking 补充材料不自动加入。
- **每份生成物必须能追溯实际读取的索引和正文。** 来源清单记录 SPEC 名称及原字节 SHA256、各 Design 稳定地址、版本号与原字节 SHA256，另提供生成时间、来源集合指纹和整个下载文档的 SHA256。未声明数字版本的工程本地正文以内容摘要标识。
- **来源清单表达逐份读取的版本快照。** 多资源读取不声称具有数据库式全局原子性；生成前后 SPEC 字节变化时拒绝输出并要求重试。只有重新生成才能反映后续 Design 变化。
- **生成文档不产生发布或代码变更。** 服务只返回当前请求的预览内容，页面按用户操作下载，不写共享产物、不改变权限表项、不触发 Release、git commit 或服务重启。

工程选择只能指向已登记的工程，客户端不能提供任意读取目录或服务端输出路径。索引解释复用 WALL 的 Markdown 解析和工程内路径校验，资源正文由 ResourceService 按 actor 读取。单次最多处理512份正文，索引与正文合计最多8 MiB；超过边界时报告失败，不截断成看似完整的文档。页面展示失败原因并保持下载禁用，用户处理权限、索引或大小问题后重新生成。

## 文档到墙面的组织

WALL 读取工程中的 `SPEC.md` 和 `IMPROVE.md`，沿其中的资源 ID 或工程内 Markdown 链接取得正文。知识库内容通过 ResourceService 按当前访问者权限读取与修改，工程内文件在已登记目录内读取。Design 解析器识别设计点列表、分节和表格；Plan 解析器把有实质正文的完整文件作为一项改进，不按内部结构拆分。无法解析的来源显示诊断，其他可读内容仍可浏览。

`SPEC.md`、`IMPROVE.md` 和 `.wall/WALL.md` 负责导航，可以互相链接。 分析产物中的实际点写入工作文档，再由索引链接；导航索引中带显式 wall 点注释的正文仍不能成为卡片。分析完成校验必须报告本轮写进索引而无法投影的点，即使同轮已有其他有效 Plan 也不能掩盖该缺口。任务说明明确实际点的文件位置和关联地址，并要求完成前核对墙面成果。同一份正文只生成一组卡片，三个索引自身的导航项保持为导航，正文识别提示也只针对工作文档。`.wall/directions.md` 等专用文档使用各自的默认内容类型，出现在改进索引中的方向或不一致点仍保留其类别。

设计点带有来源地址和文档内的局部标记，组合成 `来源地址#局部标记`，供详情、关联与任务定位。Plan 使用固定地址 `来源地址#plan`，标题、章节或内部细节变化不会改变身份。正文中的 WALL 注释可保存点的标记、类别、状态、重要度和关联；文档级 `metaness` 只来自 YAML 头部。Resident 合并或拆分独立改进时，按实际语义维护资源身份和关联。

方向、不一致点以及 Dev 完成说明也使用 Markdown。界面新建改进时，在 `.wall/plans/` 下创建独立文件并链接 `IMPROVE.md`；知识库 Plan 继续使用正式 `plan_*` 资源。工程内 `.wall/design.md`、`.wall/directions.md` 和 `.wall/inconsistencies.md` 接收对应的点，`.wall/dev.md` 保存可包含多项成果的完成记录；其他 WALL 文档由 `.wall/WALL.md` 组织。

卡片内的操作按钮随可用宽度换行，英文等较长文案也必须完整留在卡片内；正文预览可以收缩。创建表单将长字段区独立滚动，保存错误提示与取消、保存按钮始终留在可见区域，缩短视口或出现错误不能裁掉操作入口。

文档章节边界只由顶层标题建立。条目正文中的列表或引用可以包含 ATX 和 Setext 标题，这些标题继续属于该条目的说明，不改变后续条目的类型、识别范围或来源标题。带独立 WALL 注释的顶层列表建立新的点边界；它位于分节形式的点之后时，结束前一个点，注释归属新点。界面向同一文档新增点时，既有条目的正文与身份保持不变，新点仍可单独读取和编辑。

Design 点编辑写回原文档，保留其列表、分节或表格形式；Plan 编辑写回整份正文，保留 YAML、资源身份和创建审计。知识库写入递增版本并更新修改审计。WALL 界面对同一文档的新增、编辑和退出索引操作依次完成读取与写入，避免不同操作覆盖彼此；Resident 对工程代码的并行工作仍沿用已有协作方式。

### 增量读取与墙面刷新

程序按工程与访问者缓存来源文件的修改信息、解析结果和诊断，索引自身也按文件变化复用解析结果。每次后台检查先确认当前索引与资源访问权限，再比较来源文件的路径、文件标识、大小和修改时间；来源信息与文件都未变化时，直接复用已解析的点。文件修改信息变化但正文相同时也复用解析结果；索引调整后重新计算文档所属模块，来源删除或失去访问权限后从墙面移除。

当前文档检查间隔为一分钟，手动刷新可提前执行检查。已有内容在后台检查期间继续显示；首次没有缓存时显示加载状态。可见页面约每五秒检查墙面数据是否变化，后台返回内容标记相同时，前端保留当前显示。这些检查只读取文件和已有资源信息，不启动 Resident 分析；服务重启后的首次读取重新建立内存中的文档缓存。

每次墙面读取还通过 SocietyService 的批量状态接口检查当前用户已关联的讨论或工作成员，按 Resident ID 去重并遵守成员访问权限。Resident 会话协议拥有运行状态，WALL 只读取其 `work_state` 投影；每个点的状态与当前用户的关联一起参与响应签名。对话开始、结束、排队或停止时，即使文档与 WALL 任务都未变化，也会更新卡片；只增加会话事件游标而运行状态不变时，仍复用原响应。发送对话消息成功后，页面使墙面数据失效并交给已有刷新协调器重新读取，不为每张卡片添加请求或定时器。

读取对话状态失败时，墙面保留文档及原有任务展示，提示“对话运行状态暂不可用”，后续轮询自动重试；缺失或当前用户无权读取的成员不提供运行状态。状态查询不创建 Resident、不初始化会话，也不发送模型请求。

Resident 的批量重要度建议保存在 `.wall/importance.md`，以 Markdown 表格记录点的地址、分数和理由。原点明确设置的分数优先，尚未评估的点暂时使用文档默认值。后台扫描和点详情读取同一份建议，浏览页面只读取已保存的结果；自动维护任务可以继续评估新增或修改的点。

重要度建议同样按文件变化读取，评分应用在解析结果的副本上。建议被移除后，点恢复使用文档或自身设置的分数；原有文档解析结果继续保留。

### 已读记录

已读记录保存每个用户在各工程中查看过的点及其内容标记。内容标记由点的地址、类别、内容阶段、正文和标题生成；这里的内容阶段包括 Dev 已完成，与任务的排队、运行或停止状态分别处理。这个标记表示当前地址对应的内容版本，点在重写、拆分和合并后如何延续，仍由 Resident 根据语义维护。

首次完整读取工程且没有来源读取错误时，服务端将当时可见的点及其内容标记保存为该用户的初始记录。之后，当前标记与已读记录不同，或记录中尚未包含该点时，墙面返回未读状态。用户打开详情后，客户端提交实际展示版本的标记；服务端确认仍是当前正文后保存，后续墙面响应同步该用户的已读结果。查看旧正文期间发生的新变化继续保持未读，其他用户的阅读记录独立保存。

### 审核记录

审核记录由 WALL 服务端保存每个用户在各工程中确认过的点及其内容标记，默认均为未审核。同一用户在不同浏览器或设备中读取同一工程时，可以取得自己的审核记录；其他用户的记录分别保存。

审核沿用已读记录的内容标记。标题、正文、类别或 Dev 等内容阶段变化后，原有记录不再代表当前内容，点重新显示为未审核；仅调整重要度、`metaness` 或任务运行状态时，保留原审核结果。Plan 的审核覆盖整份改进，内部任一正文变化都会使该版本的审核失效。用户撤销审核时移除该点的审核记录。

卡片和详情提交实际展示内容的标记，服务端核对后保存。详情存在未保存的编辑时，先保存再勾选审核；保存失败时恢复原状态并说明原因。审核记录与来源 Markdown 分别保存，勾选只更新个人记录，不启动 Resident 或整墙文档扫描。

### 页面偏好与最近打开

WALL 使用 `PortalPageState.create("wall", {user: ...})`，由 `PortalIdentity.username()` 提供当前用户。模块及显示配置按字段补丁保存，读取时校验值的类型和当前控件可选项。页面偏好保存在当前浏览器的 `localStorage`，不承诺跨设备同步。

最近打开记录也属于该用户的 WALL 页面状态。记录键组合工程与 Block ID，保存最近成功打开的顺序，去重并最多保留 1,000 个点。详情完整读取成功且仍对应本次选择后才记录；打开失败、过期响应或后台轮询均不计入访问。每次写入先读取已保存记录，再把本次点移到最前。此前没有记录的历史访问不补推。

最近打开记录用于排序，服务端已读记录用于判断当前内容版本是否读过，两者独立。打开已读的点仍更新最近顺序，已读确认失败不抹去一次成功读取详情的访问。

### 语义搜索的共享实现

前端复用 `portal_semantic_search.js` 的 `PortalSemanticSearch` 控制器与 Resource/Board 的共享样式。关键词筛选在本地执行；显式语义提交才调用搜索接口，任务完成后由用户选择结果集。活动搜索使用 `search_*` 身份，页面地址携带工程与 `semantic` 参数。切换工程时销毁旧控制器，清除旧选择，并忽略旧工程的迟到响应。

后端复用 Board Semantic Search 的任务存储、Resident 检索、结果校验及 Search Identity，使用 `surface=wall` 和工程范围。候选由 WALL 后端按创建者权限生成，包含点的 ID、标题、类别、状态、重要度、模块、领域、出处及正文摘录；目录尚在加载时返回可展示错误，不能把未就绪当作零匹配。模型只从候选中返回点 ID，查询和目录内容作为检索数据处理；搜索不修改代码或文档。页面把结果与当前可读墙面取交集，再执行当前筛选和排序，不用模型结果替代点的正文或权限判断。

## WALL 功能与 Lineage 绑定

WALL 工作请求在领域层声明流程名称与固定工作协议，绑定到已经解析的真实工作成员；通用投影层只安装并调用 HATG 图，不拥有工程动作表。单次请求把工程、设计点、动作和用户补充组织到 prompt；工作目录、附件和任务上下文沿规范消息内容部件传递，不丢弃图片或改写共享 Effect。已有 `wall:<工程>` 团队、外部指派成员与历史会话保留原身份。

每个 WALL 工作 Resident 共用一条 `WALL · 任务` Event → DeliverMessage Effect → Resident 连接，绑定名为 `wall:work`。分析、实现、实现/设计对齐、方向推进、抛弃、按项发布、全量发布和全面回归均向该成员的同一入口提交任务；动作、工程、设计点与本次要求写入规范输入。固定协议相同且目标成员相同时，不按按钮或每次运行重复创建图结构。全面回归由固定测试修复 Resident 调用测试框架、分析失败并复测；确定性的拒绝和状态查询归 WALL，测试运行与报告归测试领域。调用恢复继续等待原规范输入，`WALL_RESULT` 的解释及正式 Dev/Design/Plan 提交仍由 WALL 负责。

WALL 的业务绑定由本篇定义。内置投影从 WALL 的真实工程、讨论与工作身份登记发现团队和成员，安装记录或访问账号不决定团队身份。工程团队发现范围使用 `wall:<project>`，复用已登记的普通 Lineage，不创建按访问者命名的空团队。显式指定的实现成员可以来自其他获授权团队，继续遵守本文的实际 Resident 绑定与读取发送协议；显示工作成员不要求先把它移动到工程团队。

| WALL 功能 | 流程与成员对应 | 结果归属 |
| --- | --- | --- |
| 工程和卡片浏览、筛选、布局、已读 | 页面本地状态与 WALL 资源查询 | 原文、索引和用户偏好按各自协议保存，不创建 Resident |
| 语义搜索 | 公共语义搜索能力及其登记团队 | 当前 actor 与工程范围受控，搜索成员不由 WALL 投影复制 |
| 围绕一个点讨论 | 首次发言解析讨论身份，必要时创建并初始化；已有目标由 Chat Workspace 直接展示与发送 | 复用该用户、工程和点已有的讨论成员；普通聊天只影响对话和活动事实，不自动生成实现任务或 Dev |
| 请实现、改实现 | 操作请求 Event → 成员共用任务入口的消息 Effect → WALL 工作关联指定的实现 Resident | 规范输入、工作状态与 `WALL_RESULT` 关联；完成后按 WALL 协议提交或复用 Dev 成果 |
| 改规范、否定建议、抛弃设计 | 已确认的卡片操作 Event → 成员共用任务入口的消息 Effect → 本次工作关联的 Resident | 按操作含义更新 Design、Plan、索引和成果，不能把任意回复当作资源变更完成 |
| 发布已有 Dev | 用户确认的发布请求 → 成员共用任务 Event → 消息 Effect → 该任务负责 Resident | 沿工程既有发布协议保存结果，不能从页面生成或普通讨论隐含启动发布 |
| 文档分析与自动推进 | 手动或周期任务请求 → 成员共用任务 Event → 消息 Effect → WALL 登记的相应工作成员 | 返回有来源的分析与资源修改；授权、周期、暂停和工作范围由 WALL 领域控制 |
| 查看实现对话与继续讨论 | Chat Workspace 直接打开规范任务 Resident | 复用同一会话，不创建新成员、重发原实现任务或切走独立的讨论目标 |

表中任务入口使用 `manual.triggered`；自动推进调度复用相同任务入口，消息由调用 `DeliverMessage` 的 Effect 投递。操作名及工程、点、文档、发布要求属于 WALL 领域内容，由 prompt 和业务记录表达，不增加 WALL 专属 HATG 参数。讨论与实现的具体 scope、历史复用和外部成员规则由后续服务分工章节统一说明。

WALL 卡片操作和直接在 Lineage 中使用相应能力应遵守同一领域产物协议。通过受授权资源入口提交的 Design、Plan 和 Dev 变更，由现有文档读取与索引更新显示到墙面，不要求浏览器先创建一个任务；特定工作进度和完成回执仍按本次规范输入关联。私有草稿、普通聊天和未登记文件不能冒充正式成果。

跨工程绑定保持各工程的实际团队身份与权限，单个团队不可访问不阻断其他工程；已经接受的工作和历史证据保持原身份，不通过重装页面改写。

打开讨论后，每次发送都读取该点的当前完整正文，将点 ID、来源、正文和读取版本附在本条输入中。复用已有讨论也执行这一步；正文读取失败或期间切换条目时保留草稿并停止本次发送。已完成工作对应的源点退出墙面后，继续使用详情保留的工作上下文。

## 后台工作与服务分工

讨论身份与任务身份分别由 WALL 的 `discussions` 和 `jobs` 关联维护，墙面与详情通过 `discussion` 和 `job` 分别返回，兼容的 `resident_id` 展示字段不承担两个标签的身份区分。新讨论使用 `wall-discussion:<工程>:<点摘要>:<用户>` 的 Invocation scope，新任务使用 `wall-work:<工程>:<点或操作摘要>`；全面回归固定使用 `wall-work:<工程>:regression`，避免实现任务占用原讨论。已有讨论沿用原 Resident；任务记录保存其 scope，已经分配身份的历史任务和重试继续使用原关联。创建、读取和发送仍沿用当前 actor 的工程、任务 owner 与 Lineage 权限。任务 Resident 被删除后，它在 WALL 工作台绑定中的任务角色随之失效；工作台下一次创建任务角色时，丢弃这些由它自己按需创建、成员已不存在的角色，需要时重新创建，单个失效角色不阻断其他工程的任务。人工绑定的成员被删除时仍报告未绑定。

实现成员可以来自任意 Lineage，包括其他团队或个人入口的 Resident。WALL 只按规范 Resident ID 链接、加载对话和发送消息，不要求成员归属于 WALL 的 Lineage，也不按 formal/personal 类型或是否出现在团队画布中限制展示。Portal 直接复用 Resident 协议既有的读取与发送权限校验，不额外检查 Lineage 所有权或图内成员资格。协议内部需要的 Lineage 信封由服务端从 Resident 登记身份解析，客户端无需提供或匹配，任务记录中缺失或过时的 Lineage 信息不影响对话。未登记或无权访问的 Resident 仍由既有协议拒绝；Resident 工具和团队图操作继续遵守各自的权限与作用范围。

ResourceService 提供知识库资源的读取和修改。SocietyService 管理工作成员、对话和协作关系。ExecutionService 执行真正的 Agent 任务。WALL 的后台代码负责连接这些已有能力、组织卡片操作和返回进展。

卡片操作保存负责 Resident 和本次输入的关联。Portal 重启后可以继续读取这次工作的结果；模型执行沿用现有后台任务机制。实现、讨论、文档分析和发布使用不同的工作范围，工程不另设专用模型执行进程。

任务执行遇到 Lineage 服务暂时不可用时，沿用原任务等待恢复。结构化故障只有同时明确 owner 为 lineage、错误为 instruction.owner_unavailable、允许重试且本次操作未提交时才重新排队；已有规范输入继续观察原 message_id，尚未投递的准备工作沿用原任务关联。用户已停止任务时优先进入取消状态。已提交或提交状态未知的结构化故障保留阻塞回执，不自动重新提交。

后台分析根据工程的授权和周期开展。它可以读取最近变化，建议重要度和关联，维护方向与计划，发起必要测试和日常修复。用户可暂停自动推进，也可在具体 Resident 对话中调整工作。

历史任务保留原有状态、错误与 Resident 身份。WALL 在读取时批量查询当前调用者可访问的 Resident 状态；任务目标已删除或不可访问时，界面显示原 Resident 不可用及重新发起任务的入口说明，不继续提供失效的“查看 Resident”链接。查询失败时提示状态暂不可用，不把暂时故障写成永久失效，也不自动重启旧任务。

### 操作如何推进

点击工作按钮后，WALL 先记录任务，再通过 Which Resident 推荐与现有成员创建能力准备执行者。已有关联讨论时可以复用成员；独立的新任务可以派生自己的 Resident。任务先后显示排队、寻找成员、准备工作区和执行中的进展，用户可以停止自己发起的工作。

Resident 在回复中用 `WALL_RESULT` 返回完成情况和结果说明。已完成的实现、代码对齐、功能抛弃或方向推进会生成蓝色 Dev 成果；Resident 已写好对应成果时可以返回其地址供 WALL 复用。需要判断或尚未完成的工作显示原因，并保留继续讨论的入口。

工作完成时，WALL 在已有任务记录中保存 `completed_at`（完成时间）和 `result_block_ids`（本次生成或复用的成果地址）。这些记录用于找回工作结果，成果正文继续来自 Markdown。旧工作缺少完成时间时使用已有更新时间，其次使用创建时间；按任务 ID 生成且仍可见的旧 Dev 成果也可以关联到完成记录，其他旧记录保留原有摘要和 Resident 入口。

不同操作按各自含义维护文档：

| 操作 | 代码与文档的结果 |
| --- | --- |
| 请实现 | Resident 完整实现并验证该 Plan，更新相关规范，完成后整份 Plan 退出候选并展示 Dev 成果。 |
| 改实现 | Resident 让实现与规范一致，完成后移除不一致点并展示 Dev 成果。 |
| 改规范 | Resident 根据确认的实际设计修改规范，完成后移除不一致点。 |
| 否定或删除建议 | 原 Plan 标记 obsolete 并移出 IMPROVE 索引，保留完整原文和其他独立 Plan。 |
| 抛弃设计 | Resident 删除相关功能并调整规范，完成后移除原设计点，记录 Dev 中的结果。 |
| 发布 | Resident 使用工程更新工具同步所选成果的实际范围；WALL 校验返回的 commit 已进入 Release 分支后处理当前任务的成果，并保存 commit 与任务结果。 |

### 条目与 Resident 的生命周期

WALL 的执行身份按工程与条目分配，讨论身份按工程、条目与用户分配。通过 WALL 操作移除条目后，WALL 持久记录并清理不再被有效条目引用的执行和讨论 Resident；工程固定的分析、回归与发布 Resident 保留到取消工程登记；操作沿用普通 Resident 删除语义，同时移除按需角色绑定、创建回执及该身份专用的流程组件和连线。

Plan 转为 Dev 成果后，成果可以继续引用原执行 Resident。删除原 Plan 时保留这个身份，直到最后一个有效成果退出墙面。历史任务中的身份引用只用于读取历史，不阻止回收，也不因读取历史重新创建身份。删除条目保留产品原有的 Markdown 归档语义。

取消工程登记须先等待或停止该工程的工作，再清理工程级分析、回归、发布及全部条目和讨论角色，最后撤销登记及其运行关联。工程源文件与固定 WALL 团队保留。清理期间阻止该工程产生新工作，失败时保留待清理关系，重复请求继续清理；重新登记后，新条目的首次实际使用重新分配普通 Resident。

尚有活动任务、排队消息、有效成果引用，或无法读取来源确认引用关系时，不把身份当作无主对象删除。条目移除与身份清理之间的待办状态必须持久保存；自动完成导致的条目移除，在工作终态后重试清理。文档移除失败返回失败；文档已移除而身份暂不可清理时返回成功和 `cleanup: pending`，按退避间隔重试。只检查待回收身份自身是否忙碌；其他条目的工作不阻止清理。取消登记进入清理阶段后失败，保留 `deleting` 状态和未完成的角色关系，返回 HTTP 503、`wall.unregister_pending`、`retryable=true`、`commit_state=unknown`，避免把已经部分执行的清理误报为未提交。前端立即刷新该工程，以只读状态展示并保留再次取消登记入口；重试只清理尚存关系，来源目录和固定 Portal 团队保持不变。


## 页面与后台接口

页面通过 `/api/wall/projects` 读取可见工程，通过 `/api/wall/board` 读取点、模块、工作进展和操作权限，通过 `/api/wall/block` 取得单个点的完整正文。创建、编辑、任务操作和自动推进设置分别提交到 `/api/wall/create`、`edit`、`action` 和 `automation`。

`POST /api/wall/documentation/preview` 接收当前工程标识，按上述只读规则返回 `manifest`、`markdown`、文件名和 `document_sha256`。服务端每次请求重新读取并校验来源，不把旧预览缓存当作当前规范；浏览器只在成功响应后开放下载。

`/api/wall/board` 同时返回 `recent_completed`，从当前工程中由登录用户发起的已完成工作中取最近 20 项，与墙面筛选及运行任务列表的条数分别处理。每项包含原工作标题、动作、摘要、完成时间、可用的 Resident 与 TAU 报告地址标识，以及 `result_blocks` 中的成果引用。成果尚未出现在墙面缓存中时，已有引用仍可通过 `/api/wall/block` 按当前用户权限读取；完整正文读取期间或读取失败时，详情里的修改操作暂不可用。打开完成列表使用已取得的墙面数据，不额外请求历史列表、不启动 Resident，也不触发文档扫描。

墙面与详情中的点通过 `resident_work_state` 返回已关联对话成员的状态；该字段与 WALL 工作的 `job.status` 分别保留，页面合并两者的活动提示。未关联、不可读取或暂时无法取得状态时，该字段为空；批量状态服务故障同时返回告警。页面使用实际运行优先于静态等待的合并规则，工作进展、完成结果和操作权限继续由原有任务字段决定。

墙面与详情中的点还返回 `unread` 和 `read_revision`，分别表示是否未读和当前阅读内容的标记。客户端通过 `POST /api/wall/read` 提交 `project`（工程标识）、`block`（点地址）和 `read_revision`。服务端使用登录用户身份检查阅读权限，并只更新该用户的记录；登录用户也可以记录自己的已读状态。

提交的标记仍对应当前内容时，接口返回 `read: true`、`block` 和 `read_revision`。内容已变化时返回 `read: false` 和 `block`，新内容保留未读提示；读取或保存失败时，界面保留提示并显示失败原因。

墙面与详情中的点通过布尔字段 `reviewed` 表示当前用户是否已审核该版本。客户端通过 `POST /api/wall/review` 提交 `project`、`block`、`read_revision` 和布尔值 `reviewed`，分别设置或撤销审核；登录用户也可以维护自己的记录。接口使用登录用户身份检查该点的阅读权限，保存后返回 `block`、`reviewed` 和 `read_revision`；内容标记已过期时返回错误，请用户查看最新内容后再次操作。

有效登录用户可以浏览、维护内容、发起工作、登记与取消登记工程。经 ISA 的操作由权限系统按当前模板判定（decision_b820faf42218）。知识库来源另按 ResourceService 的权限处理，Portal 工程的 TAU 执行沿用 Test Lab 权限。返回的工作记录和讨论关联按当前用户选择，页面据此展示可用操作。

语义搜索接口复用共享任务协议：

| 请求 | 参数与作用 |
| --- | --- |
| `GET /api/wall/semantic-searches` | `project`，读取当前用户可见的该工程搜索任务 |
| `POST /api/wall/semantic-search/start` | `{project, query}`，创建后台搜索 |
| `POST /api/wall/semantic-search/refresh` | `{project, search_id}`，重跑搜索 |
| `POST /api/wall/semantic-search/delete` | `{project, search_id}`，软删除搜索 |

搜索要求当前 actor 可读该工程，并按任务 owner 与工程范围校验管理动作；登录用户可使用自己的搜索，不需要内容维护权限。工程、surface 或搜索身份不匹配时不操作其他任务。

## 交互与结果

进入页面先显示墙面框架和可用的缓存内容；尚无缓存时显示加载状态，后台检查已有文档时保留当前卡片、阅读位置和输入。卡片操作立即反馈已接收和当前工作状态，失败时保留错误及重试入口。阅读、讨论和创建权限沿用工程与资源已有权限。

实现完成后，Resident 更新相关规范和计划，墙面展示可在 Dev 体验的成果。测试发现可以形成不一致点或改进点；常规修复不增加逐项审批。发布完成后，墙面更新 Dev 完成说明，并展示发布结果。

## 发布入口与实际结果

WALL 的发布任务交给 Resident 按普通工作流执行，实际的同步和 Git 提交由发布工具完成。发布成功时结果中带有 `publication_commit`；Portal 工程的 WALL 校验完整 commit ID 确实是 `release` 分支 HEAD 或其祖先，校验通过后保存 commit 并移除当前任务对应的成果。无效 commit、尚未进入 Release 的提交或分支读取失败时，任务失败且成果保留。成果地址取自任务记录，Resident 返回的额外成果列表不参与处理。后续发布快进后，原 commit 仍可用于恢复任务；成果已移除时重复完成保持幂等。其他待发布成果保持不变。开发者不经过 WALL 直接发布，同样有效。WALL 接口既接受人类登录会话，也接受 Resident 的认证请求，都按实际调用者检查工程权限；Resident 调用时不会因此获得 owner 权限。

## 工程级全量发布与 Resident 全面回归

WALL 提供三个并行的交付与验证入口：成果卡片按功能发布、当前 Dev 源码全量发布、全面回归。全量发布补齐漏发的新增、修改和删除；它不等待全面回归，不要求工作区干净或其他工作完成，也不自动删除或标记任何功能卡片。Resident 按全量发布命令执行并检查标准输出、健康与推送结果；Portal 的 WALL 接收 `WALL_RESULT.publication_commit`，校验该 commit 已进入 Release 分支后完成任务。发布工具的独立单元日志用于查询运行结果，WALL 不读取发布报告。

全面回归按钮直接调用 WALL 所绑定 Lineage 中的固定回归测试与修复 Resident。同一工程连续调用复用同一成员及其聊天上下文；绑定由 Workbench 保存，任务通过既有 Event → 消息 Effect → Resident 工作流投递。页面和 WALL 后台不先运行测试再决定是否调用模型。

测试 Resident 读取工程测试规范和目录，通过既有测试能力组织后端、浏览器和 TAU 等适用回归。它观察真实终态，区分产品错误、错误或过时的测试断言和环境故障，依据当前 Design 修复，并重跑失败和受影响的测试；不能删掉有效用例、跳过失败或弱化正确断言制造通过。本次明确指定用例时只检查指定范围。报告记录实际范围、证据、修复和未解决项，框架 Run 关联为可打开的测试报告。

全面回归与全量发布各有独立任务、手动按钮和可选周期。默认不开启周期执行，用户分别选择开关和间隔；关闭自动分析不会关闭已单独启用的回归或发布计划。周期与执行回执保存在后台，页面刷新不影响执行；重启后恢复原 message 的观察，不重新投递。用户可以按具体任务停止，停止回归不会取消全量发布。

只运行回归不隐式发布代码。回归 Resident 完成实际修复并通过定向验证后，按开发交付规范发布相关修改；全面回归本身不成为发布门槛。WALL 展示进度、Resident、测试报告、发布 commit 和失败原因，测试执行与代码发布分别由既有测试框架和发布工具负责。

## WALL 运行事实

工程、任务、讨论绑定、自动化设置以及用户阅读与审核状态由 PostgreSQL 的 `portal_state` schema 中 `wall` 命名空间唯一保存，包括 `projects`、`jobs`、`discussions`、`reads`、`reviews` 和 `resident_cleanup` 集合。项目、任务、讨论与用户状态分记录保存；读改写在同一事务内进行，只更新变化行。文档正文保持由其知识资源 owner 管理，扫描缓存可重建。运行时不读取或重建 `state.json`。

## 工作区、Plan 与执行入口

WALL 以共享 Activity Rail 提供墙面和 Test 两个工作区，测试目录、运行、TAU、门禁与审查在 WALL 内使用；全局导航只保留 WALL，测试功能内部协议由测试工作台规范说明。

### WALL 怎样从索引中识别 Plan

WALL 从工程的改进索引（如 `IMPROVE.md`）中找出可以实施的 Plan 文档，规则如下：

- **列表项或段落中只有第一个 Markdown 链接是候选。** 后面的链接是说明和证据。表格中每个单元格各取自己的第一个链接，所以同一行的 Design 和 Plan 可以建立模块关联。
- **文档自己的声明优先。** front matter、`wall` 元数据和专用的 `.wall` 文档类型决定一个候选是不是 Plan。文件名或一级标题表明是报告、审查、审阅、审计或证据的文档不是 Plan，即使它在索引中单独成项。
- **资源锚点可以放在开头的 `wall` 元数据之前，也可以放在一级标题之后。** 这些不含正文的 HTML 锚点和元数据不会出现在卡片正文和预览中；元数据中的重要度、关联资源和负责 Resident 照常生效。

WALL 手动工作可在投递前选择 Codex 账号；选择按当前用户保存，任务受理时冻结为 `backend_route_id`，恢复与重复点击沿用原任务的账号和消息身份。首次讨论在首次发送时带入选择，已有讨论通过普通 Session 入口切换。周期任务在自动推进设置中单独保存账号。账号必须来自现有注册表，由通用 Resident 创建与 Session 迁移流程落实；空选择沿用既有配置，不改全局默认值、API Provider 或其他用户的成员。

WALL 的 Design 模块归属优先使用 SPEC 正式目录表；前文的正文交叉引用不覆盖目录归属。

## 索引与并发保存

索引读取和写入共同使用磁盘上实际存在的文件名，根索引按大小写不敏感匹配；不同时创建大小写不同的副本。索引链接可以缓存，链接目标是否存在和是否为 Plan 在每次解析时检查。WALL 修改知识资源时携带读取正文中的版本号，版本冲突要求刷新后重试。任务按创建时间排序后截取最近记录。SocietyService 暂时不可用时保留正文详情，成员状态显示暂不可用。

工程登记和取消登记分别使用 `POST /api/wall/register`、`POST /api/wall/unregister`；`GET /api/wall/test-binding` 读取设计点的测试关联。
