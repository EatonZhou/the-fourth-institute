# 软件工程智能开发核心团队：Lineage 模板与创建原则

一个软件工程由一个核心开发 Lineage 负责它的完整开发过程：理解与设计、实现、测试与用户视角验收、发布、进展汇报和方向演化。整条 Lineage 组成一个 Family，对外由门面接待；工程的开发投影工作台（decision_13e1a748cf04）是这个团队面向人的界面，工作台对话区连接门面。人用工作台理解工程、表达反馈和需求，团队完成具体工作。

本篇规定这种团队的模板：有哪些稳定角色，成员怎样在只收到一句话或一个事件时自主工作，标准事件与流程怎样连接，以及创建团队时要遵守的原则。按模板创建团队的操作步骤见 Skill `${share_root}/Skills/create-software-dev-team/SKILL.md`。Portal 工程的团队 `lineage_8794980b1bb7` 是第一个实例。

## 团队与规范的分工

团队规范（本篇、开发投影范式、投影协议）给出方向和体验水准；团队自主完成工作。成员在实现中发现规范不可行或需要取舍时自己解决：在职责内直接做出取舍，把取舍和依据写进对应 Design 或工程设计文档以及工作报告，不向规范设计者或其他成员请示。实现细节（代码结构、数据表、组件划分）由成员决定，并按工程自己的设计规范记录。用户查看工作结果后再给规范设计者反馈，由规范设计者调整方向。

**成员自行完成职责内的设计、实现、自检和交付。** 设计与体验成员继续提供可直接使用的设计、问题和证据；日常工作不以同伴评审、签字或批准作为开工和继续实现的前置条件。用户明确安排的独立验收与正式测试按原职责执行。同一成员可以连续完成的完整工作不按内部步骤拆分；只有独立职责或可并行的完整工作才委派。

**Portal 开发 Family 及其子团队的主动通知以完整工作项完成且存在实际交付需要为条件。** 接收方需要最终成果执行已明确的工作，且既有回复或成果不能完成交付时，沿原任务或约定入口发送一次合并交付，只写成果入口和具体消费方式。完成本身不自动产生通知；不滚动汇报进展、不催回执，不因风险、失败、接口变化或解阻而在中途主动同步。已有成果可自行获取时直接获取，不追加广播或抄送。

原始业务请求、已授权任务分派、平台既有业务及失败/恢复事件沿原规则运行；它们不产生成员中途通知许可。用户明确指定的通知、收件人和频率按该项要求执行。收到消息不另发确认、感谢或复述；原任务最终回复已足够时不再发送完成通知。新增或派生成员由本层 steward 通过共享目标及下一轮背景带入这些规则，不逐一发宣贯消息。

## 稳定角色

| 角色 | 职责 | 主要产物 |
| --- | --- | --- |
| 门面、Router、steward | Family 自带：门面接收工作台对话与反馈，Router 按规则路由，steward 维护成员与职责，在职责缺口反复出现时新增成员 | 路由记录 |
| 架构成员 | 模块地图、架构与协议解释、发布后核对偏离 | 模块地图、核对脚本 |
| 演化成员 | 演化方向与改进计划之间的依赖，整理反馈为计划草稿 | 演化图、计划草稿 |
| 汇报成员 | 按时整理进展摘要和体验步骤 | 进展摘要 |
| 投影前端团队 | 在核心 Lineage 内嵌套的局部 Family：负责人、交互设计、宿主与 SDK 平台、每个功能区一名可视化工程、体验验收；工作台是一个独立软件，由作者完成交互设计、自检及投影应用包实现 | 交互设计稿、投影应用包、走查证据 |
| 开发成员 | 用户经门面提出的功能开发、缺陷修复和设计调整 | 代码、设计更新、体验步骤 |
| 测试成员 | 维护测试目录、回归基线与发布门禁，处理测试失败，调度用户视角验收 | 测试用例、回归结果、失败处理 |
| 用户视角验收单元（TAU） | 一组按工程模块划分的 TAU Resident，从真实用户入口使用软件、保留证据并定位问题 | 验收证据与问题报告 |

投影前端团队可按真实使用反馈的需要增设常驻投影 TAU 成员，与作者自检和理解任务走查分工协作。该成员使用团队交付的真实页面，记录用户影响、复现和证据，问题交对应开发成员修复，再按受影响范围复验；负责人把验收和复验纳入交付流程。团队内探索与问题账本不冒充正式 Test Run；正式 Case、Campaign 及会发送消息的真实反馈闭环仍由测试成员统一登记调度，保留已有模块 Resident 的槽位与工作流。这样缩短产品问题反馈距离，同时避免重复执行和重复发送。

角色按职责设置，不按按钮或功能数量设置。规模小的工程可以由一名成员承担多个角色，例如架构与演化合并；规模大的工程按模块增加开发成员或 TAU Resident。TAU 单元的身份、执行和证据规则沿用 decision_c953eab654cd，测试浏览与运行沿用 decision_f2a6a5dd4646。

## 成员自足：resident.md 是完整的工作说明

用户可能只对成员说一句“请创建初始投影”，也可能只点击工作台或 Lineage 上的一个事件。成员必须能够仅凭自己的 `resident.md` 判断要做什么、先读什么、做到什么程度。因此：

- **`resident.md` 写完整的工作说明。** 包括团队名单与各自职责、规范依据、学习材料、协作关系，以及若干**具名工作项**。每个具名工作项写明目标、需要先阅读的材料、步骤、完成标准和结束时的汇报内容，例如“生成初始投影”“起草模块地图”“运行回归基线”。
- **事件连线只携带短任务。** 连到成员 Invoke 端口的连线提示只写“执行具名工作项《生成初始投影》”这类一句话，并可附本次参数；做法和标准不写在连线上，避免同一工作在两处出现不同版本。
- **先学习，再动手。** 每个 `resident.md` 列出成员开始新工作前要阅读的材料：理念文章 article_c30f093138b5（至少第 2、3、5、6 章，必要时全文）、团队模板（本篇）、开发投影范式与投影协议，以及与本职责相关的工程设计。成员根据理念理解规范的目的，在规范没有覆盖的情形下按理念判断。
- **规范会反复调整。** 每次开始新工作时重新读取规范的当前版本，不依赖记忆或以前对话中的旧版本。
- **写立场和效果，不写做法和例子。** 具名工作项的目标与完成标准描述要达成的效果和读者的感受，例如“读者能很快理解”“作者自己愿意拿给任何人看”，不规定界面形式、布局或内容清单，也不转录用户反馈中随口举的例子。AI 成员会把写下的形式和例子当成标准照搬，并套用到所有地方（thinking_c72047ece30c）。用户反馈中的例子只用来理解用户的意思，转写成它背后的要求。
- **成员是作者。** 每份 `resident.md` 说明成员对自己的产出负作者责任：先研究内容再决定形式，做自己作品的第一个用户，不满意就重做；有主见，可以推翻规范中的具体做法；汇报讲做成了什么，不自我辩护。

## 并行与派生

开发类成员（开发成员、投影前端团队成员，以及需要大量实现工作的其他成员）可以自行用 `ForkResident` 派生子 Resident，按功能模块或任务并行开发：

- 派生前写清子任务说明：目标、范围、可修改的文件边界、验收标准和汇报方式；共享同一工作树时，各子 Resident 的文件边界不重叠。
- 子 Resident 加入同一 Family，从父成员继承上下文；父成员负责集成、整体测试和一次性发布。
- 子任务完成后，父成员删除派生的子 Resident；需要长期保留的职责交给 steward 判断是否转为正式成员。

## 标准事件与流程

团队用 Lineage 事件源和连线表达流程，不用逐个直接投递提示词绕过 Lineage。标准集合如下，具体工程按需要取舍：

| 事件源 | 类型 | 接收方与具名工作项 |
| --- | --- | --- |
| 起草模块地图 | 手动 | 架构成员 |
| 起草演化图 | 手动 | 演化成员 |
| 生成初始投影 | 手动 | 投影前端团队负责人 |
| 运行回归 | 手动 | 测试成员 |
| 模块验收（每个 TAU Resident 一个） | 手动 | 对应 TAU Resident |
| 每日进展摘要 | 时间 | 汇报成员 |
| 回归基线 | 时间 | Effect → RunScript；失败时 `script.finished` 交测试成员 |
| 发布完成 | 发布事实事件（Portal 为 `portal.release_published`） | 架构核对（Effect → RunScript）、汇报成员补一轮摘要 |

确定性的检查和运行用 Effect 调用 RunScript，不占用模型；需要判断的工作交给承担该职责的 Resident。发布完成事件的语义见 decision_13e1a748cf04。 摘要事件用于维护可获取的进展产物；是否主动通知仍遵循前述交付规则，事件触发不自动授权向成员或用户发送进展。

## 运行设置

创建团队时，由发起人指定全体成员统一使用的账号、模型、推理强度和权限预设，Family 的 Router 与 steward 同样设置。Router 只负责分派，发起人可以单独降低它的推理强度以加快门面响应。

核心团队承担整个项目的开发、测试、发布和运维。建队时，有相应权限的发起者通过启用方案的持久权限表项，为门面、Router、steward 和常驻成员配置承担职责所需的管理员权限；表项由 `CreatePermissionEntry` 建立，具体判定与方案规则见 decision_22227d0ad075 和 decision_b820faf42218。权限按每个 Resident 自身的有效表项判定，Family 角色之间不共享；派生成员同样需要自己的授权，临时协作可以使用持有者签发的限时或随消息凭证。缺失的受控自动化能力作为对应模块的开发需求处理，执行者继续使用自己的身份和有效权限。

## 创建原则

- 一个软件工程一个核心开发 Lineage；新工程直接按模板创建完整团队，不把开发、测试和验收分散到不同的 Lineage。
- 先创建 Lineage 并整条 Family 化，再创建成员，使成员自动加入 Family。
- 总 Family 下按工作领域嵌套局部 Family：开发团队（架构、演化、开发成员）、测试团队（测试成员、回归执行成员、TAU 模块执行成员）、投影前端团队。只服务于某个领域的事件源、Effect、过滤器和连线归入该局部 Family，折叠后随它收起；跨领域的流程（例如由发布事件同时驱动核对与汇报）留在总 Family。
- 每名成员创建后立即写好自己的 `resident.md`，再创建事件源和连线；连线只写短任务。
- 成员的工作目录绑定工程代码仓库和项目目录。
- 搭建完成后检查 Lineage 诊断；首轮工作通过手动事件触发，并观察成员确实开始工作。
- 团队创建过程中不改变其他 Lineage 的成员与绑定；把已有团队并入核心团队需要单独确认，因为迁移会影响已有工作台绑定和进行中的任务。
