# 更新现有 Portal 实例

本指引用于 AMA、Resident 和开发入口执行用户已要求的实例更新。操作前读取当前代码的 `docs/instance-updates.md`，核对安装器与实例控制器的 `--help`；使用部署所属的 Python 环境。规则和工具升级随代码发行，不从历史对话推断当前参数。

## 识别目标与准备

- 从实际实例清单、`PORTAL_INSTANCE_ROOT` 或本机正式登记确定目标名称、instance_id、代码目录与部署。目标不明确时询问；不得把来源开发站或另一个实例当作更新目标。
- 核对代码来源、当前提交、发布分支与本机改动，按该部署已有的 Git 或安装包更新流程取得正式代码。保留本机修改，冲突先报告，不执行强制覆盖或重建实例。更新器处理已取得的代码，不负责选择任意远端或分支。
- 检查本机服务适配。需要保留的 launch-agents 目录和组件 PATH 前缀通过 `tfi_release_install.py configure-services --instance <名称> --settings <JSON文件>` 保存；字段为 `launch_agents_directory`、`path_prefixes`。核实实际已有目录，不凭示例路径搬动已加载任务。
- 在代码稳定后，可用 `tfi_release_install.py update-code --instance <名称> --plan` 检查领域要求、缺失服务与冲突。规划可能临时启动数据库并执行领域原有的增量结构准备，不称为纯只读检查。

## 执行与等待

AMA 若在被更新实例内运行，使用独立原生控制作业：

```sh
python scripts/tfi_instance_manager.py update-code --name <已登记实例名称>
```

需要离线时加 `--offline`，依赖不齐就报告，不悄悄联网。独立作业调用正式更新器，停服不会随当前 AMA 的 Provider 一起终止更新。不要从当前 AMA 内直接拼接 stop、复制文件和 start。

外部终端或独立部署工具可直接调用 `tfi_release_install.py update-code --instance <名称>`。依赖准备、代码切换、启动项生成都只是更新的一部分；不要以它们替代正式更新器。

提交后记录作业 ID。读取目标实例 `runtime/portal-control.json` 和 `runtime/update-code.json`，按同一作业、实例与代码身份核对终态。`queued`、`running` 不是完成，不重复投递。服务停止造成聊天断开时，在重连后的下一轮继续读取原作业；不得声称已自动给用户发送完成通知。

失败时报告具体阶段和回执中的阻塞项。依原更新合同修复冲突后重试；停服后的中断必须遵循同一代码恢复要求，不能删回执、伪改状态或更换来源强行通过。

## 完成标准与数据边界

- 核对作业完成、更新回执为 `updated`、全部要求的领域检查和服务检查通过。说明实际提交、补齐内容、保留的用户修改、未完成项与回执位置。
- 已安装面板、工作台构建和本地桥接均按所有者声明处理；未知缺失文件不猜造。用户修改冲突保留，显式停止功能保持停止。
- 不重导示例 SQL，不整体覆盖实例数据，不复制来源站点联系人、绑定或凭据；保留数据库、账号、草稿及本机配置。
- PostgreSQL 大版本、破坏性迁移和可选工具仍走各自流程；不能用空迁移或仅更新代码推断兼容。
- 自动文件/服务检查与真实业务验收分开。微信需真实消息进入 AMA 并回复到微信才能称往返通过；仅扫码成功、进程存活或首页正常都不够。没有目标访问或消息验收条件时明确保留限制。

## 已有会话

新会话通过共用核心规则取得本入口。旧会话已送达的规则不会被代码发布改写；通过 Prompt 注入的任务 Skill“连同核心规则重发”或新的正常会话取得新入口，也可在原会话明确要求读取本指引后继续。核对 `PreviewPromptInjection` 的实际发送时机，不为文档同步强制重启任务，不全局改成每轮重发，不把源码已发布声称为所有 AMA 已收到。
