# 解释页的创作与独立检查

解释页帮助读者形成可操作的理解：能说清关键关系，能预测改变一个条件之后会发生什么，也能查到支撑结论的材料。页面的复杂度由理解任务决定。一个清楚的图、一张简洁的表或一段短文足以回答问题时，应当停在那里。

## 主动性与本次质量

先消费 Portal 为本次输入提供的有效 `reporting` 策略，Home 提交时的设置快照只提供入口上下文，不能覆盖服务端策略。`initiative=off` 不主动另做汇报，仍完成用户明确要求的成果；low 只在重要成果、风险或决策需要时考虑，medium 按信息增量与理解收益判断，high 更积极判断机会，仍不要求每轮生成。普通回答和业务最终交付不自动变成额外汇报。设置读取失败须保留失败，不能声称用户配置了默认值。

报告质量 low 使用清晰的 Markdown，medium 使用现有交互网页模板，high 按下述参考标准创作并交另一名 Resident 实际审查。low/medium 不强制独立审核。简单任务仍可用简单表达，高质量不以页面复杂或动画数量衡量。首次生成显式记录质量，质量与成果固定版本绑定；更改质量或内容产生新版本，原消息和历史继续读取原版。视频按钮单独选择质量：low 自由选择表达方式，medium 加强 3Blue1Brown 风格的讲解指导，high 还必须完成独立成片审查与修改后复审。不同质量不能复用同一个 ready 结果。

## 三个参照，学习表达方法

high 解释页必须在清单记录 `quality: "high"`，通过构建入口送独立检查；手写清单同样要送检。不能把设置读到的 high 留在提示里而把产物保存为默认 medium。检查未通过时向用户交代具体意见、受影响的固定版本和接下来的修改，继续创作复审；只完成页面或收到 submitted 均不表示质量达标。

medium/high 解释页即使尚未编写 `video_plan` 也保留“生成讲解视频”入口。点击后先请求负责 Resident 准备真实分镜与固定音轨；初次打开、恢复历史不生成配音、不启动视频任务。没有语音工具时说明具体缺口，保留图文和按钮。页面质量检查与视频检查分别显示；用户能查看修改意见与证据，普通读取不重复送审。

| 参照 | 值得迁移的表达方法 | 适用的理解任务 |
|---|---|---|
| [Transformer Circuits：Global Workspace](https://transformer-circuits.pub/2026/workspace/index.html) | 把观察对象、实验干预、读出结果放在同一解释路径中，正文与图像共同承担论证 | 内部过程、实验现象、系统机制 |
| [Distill：Paths Perspective on Value Learning](https://distill.pub/2019/paths-perspective-on-value-learning/) | 在同一组路径上比较方法，让差别随过程显现，再用公式解释差别 | 算法比较、传播过程、策略取舍 |
| [Distill：Handwriting](https://distill.pub/2016/handwriting/) | 让读者提供输入、调整参数，看到样本变化；把输出与内部表示联动 | 生成过程、不确定性、表示与输出之间的关系 |

这些作品提供质量参照，不规定固定配色、图表类型或模块数量。不得复制整页内容或把其中的研究结论移植为自己的实验结果。D3 是实现数据驱动图形的工具；是否使用它不决定作品质量。

## 先定义读者要弄懂什么

动手前用三句话写清：读者当前困惑；他读完后能做出的判断；怎样用一个具体例子验证这种理解。随后选取能揭示该关系的表达。

| 用户任务 | 有效的图形或操作 | 应避免的空操作 |
|---|---|---|
| 理解“为什么会这样” | 改一个输入，过程与输出一起更新；同时显示保持不变的条件 | 按钮只换颜色或弹出同一句话 |
| 比较多个方案 | 统一尺度并列比较；同一个案例作用于各方案；明确代价 | 各方案使用不同尺度让差异失真 |
| 理解时间过程 | 拖动时间、逐步执行、暂停在关键转折，标明先后与持续时间 | 无法暂停的装饰性动效 |
| 理解结构与依赖 | 在图中选择一个对象，高亮相关路径并显示依据；适时提供局部视图 | 给任何问题都画大量卡片和箭头 |
| 理解分布与不确定性 | 调参数看多个样本或区间；显示分布、典型情况和例外 | 只展示一条漂亮曲线却暗示普遍成立 |
| 阅读事实或简短说明 | 清晰正文、必要的表格和来源；可不使用视频与交互 | 为凑模板而增加操作和长视频 |

读者不需要使用“直观解释”“做交互”之类关键词。Resident 应主动判断何种呈现更有帮助。

## 图文怎样成为一个整体

先展示一个具体对象，让读者看见问题；再开放少量有意义的操作；最后提供可展开的推导与边界。每张图应有一句解释它要回答的问题，坐标、颜色、大小和线条均有明确含义。

文字、图形、参数和结果使用同一份状态与计算。点击文字中的例子可以定位图中的对应对象；点图中的对象可以查看具体数值和依据。互相联动要保留读者的阅读位置，不能突然跳走或重置设置。复杂细节按需展开，不用巨大的仪表盘淹没主线。

交互必须改变有解释意义的变量。结果应来自真实计算或明确标注的演示数据。一次操作后，读者应能看到改变了什么、什么保持不变、差异从哪里产生。支持重置和几个有代表性的预设，帮助读者从无目的滑动进入有意义的比较。

## 视频按需生成

初次打开先呈现已有解释内容。视频区域提供“生成讲解视频”按钮，由读者决定是否生成。生成完成后持久保存视频、字幕、讲稿和章节，重开直接恢复。状态、失败与重试由宿主管理，不把一个空播放器当作已完成视频。

视频适合需要连续观察的过程：连接怎样变化、量怎样积累、物体怎样运动、一个推导怎样展开。视频画面应承载推理，不能只把字幕按页播放。配音、字幕与画面按实际音轨时间对齐；按钮、字幕和播放器提供可用的无声阅读路径。生成失败不阻断已有图文与交互。

视频参照 [3Blue1Brown：Attention in transformers](https://www.3blue1brown.com/lessons/attention/) 的解释质量。先确定每个镜头要让读者理解的一步关系，再选择向量、矩阵、路径、空间变换或其他合适图形。符号、颜色与对象跨镜头保持含义；由具体对象逐步建立抽象表示，用连续变换交代“从哪里来、为何改变、得到什么”。高亮和镜头移动跟随正在解释的对象，给关键推导留出阅读时间。不能让所有主题都套成固定节点图加移动粒子，也不能把增加对象数量当作精细制作。复杂度以解释所需为准。

每个镜头写明读者的问题、当前状态、新增操作、图形含义和对应旁白。画面应显示操作本身：相乘与相加展示来源和部分和，归一化展示共同分母，比较实验明确改变的一个条件及保持的条件。结果随推导完成后揭示；无贡献的量不能继续用运动暗示贡献。中间插值若不是真实计算值，应标为过渡或暂不显示读数。讲解复杂系统时，先让读者理解一个局部，再把熟悉的局部接回整体。

图形、算式、字幕与旁白共用可复算的事实源。对象跨镜头保留名称与含义；长度、面积、正负和零值采用可解释的尺度。高亮绑定正在说到的对象和真实字幕时间，不按计时器轮流点亮。切换案例或重置条件须在画面上交代，避免读者把多处同时变化误认为单一原因。教学数据、简化假设与实测结果需要清楚区分。

先完成一段可播放样稿，再展开全片。分镜估时仅用于创作；拿到真实音轨后再确定字幕、语义事件与阅读停顿。暂停时仍能看清当前输入、操作与结果。时长超出上限时缩减不必要内容或拆章，不机械加速旁白。视频在右侧窄栏和全屏都应能读清关键关系；密集细节使用局部放大，并在图文区域提供可核对的数值或推导。

音色、语言与节奏依题材选择，制作方法遵守用户要求。按真实音轨编排镜头、留出阅读与呼吸空间、检查响度和字幕同步，不机械套固定语速。

保存音轨文件及摘要，旧成果保留原始版本。

high 质量的成片由独立视频检查 Resident 检查，页面检查结论不能替代视频质量结论。检查完整解释路径与关键帧、数值和视觉含义、镜头连续性、字幕与旁白时序，并在具备听辨能力时实际听声音。无法听辨时应写清音质未验。检查要绑定成片及字幕的实际 SHA；可播放、编码完成或任务已受理均不表示内容质量通过。low/medium 不自动送独立审查，作者仍须检查实际成果。

内容包只提供经验证的声明式生成计划与资源引用。服务端不可执行生成页面中的任意 Python、Shell 或 JavaScript。

## 内容与运行边界

每页说明数据来源、核对时间和适用范围。真实测量、估计、手工教学数字和假设要分清；图形中不能让人工设定的数据看起来像模型实测。引用原始论文、官方文档或用户允许访问的材料；无法验证的内容明确保留不确定性。

页面使用独立成果目录、正式资源地址和字节 SHA256。修改产生新版本，历史入口仍绑定原版本。解释交互在无业务权限的隔离页面中执行；不读父页面、凭据或本地存储，不发外网请求。确需 D3 等库时使用宿主提供的固定版本或打包经审查的本地副本，保留许可。

先保证合理字体下可读，再考虑视觉密度。窄屏不压缩成无法触摸的桌面缩略图；复杂图可转为局部细节或补充直接可操作的列表。键盘、触屏、减少动态效果和暗色主题都需要实际检查。使用有界数据、增量更新和事件驱动计算；隐藏后停止播放和无用动画。不要用持续轮询或整页重绘来维持一张静态图。

## 独立 Resident 的检查方式

high 质量的独立检查在生成内容完成后读取固定版本、实际打开页面并操作，检查者不能是作者本人。检查范围按理解任务确定；若只有一段短说明，检验其准确、清楚、完整即可。视频未被用户要求生成时，不把缺少视频判为失败。

检查者要回答：

1. **解释是否成立？** 核对来源、关键数字和因果描述。读者能否用该页面预测一个新例子的结果？
2. **形式是否有用？** 图像或交互是否揭示了正文难以表达的关系？若删除某个控件没有损失理解，应建议删除。
3. **操作是否可信？** 用正常点击、触摸和键盘操作，确认联动、重置、错误提示与状态恢复。视觉变化必须与计算一致。
4. **体验是否完整？** 检查初始状态、窄屏与大字体、对比度、焦点、加载、空数据与失败状态，不只看截图。
5. **复杂度是否合适？** 是否用最清楚的方式完整解释了问题？简单页面可以通过；装饰很多、操作很多但读者仍不明白的页面应退回。

检查输出记录固定成果地址与 SHA、适用范围、实际操作、发现的问题和结论。结论分为“通过”“需修改”“缺少验证条件”。报告不得把未操作的功能写成通过；修复后只复验受影响项。独立检查服务的调用、合法测试身份、版本匹配、重试和结果回写属于宿主工作流，本指南不冒充已部署的自动流程。

## 一个可复用的生成顺序

1. 研究内容和理解任务，选择一个有代表性的例子。
2. 确定图形的语义和最有价值的操作，先把计算与数据核对正确。
3. 制作正文与互动图，让同一对象在不同视图中保持一致。
4. 保存固定成果；视频按用户点击后的请求生成。
5. high 质量由独立检查者真实操作并给出修改意见；作者修复成新固定版后再审，并回读匹配当前版本的结论。修改使旧版的通过结论对新版失效。缺权限、取消、生成失败或验证条件不足如实保留，不自动降级、不用无限重试掩盖阻塞。

本目录的注意力模型、视频渲染脚本和交互页演示了这个顺序。它们不是其他主题的固定界面：面对地理、流程、设计比较、财务估计或日程，作者应重新选择适合对象的图形、计算和操作。
## 固定解释包与实际生成入口

作者先读取自身 Resident 的正式 Workspace 绑定，在有写权限的目录创作。每版保存为独立目录；不要覆盖已被历史引用的文件。生产入口为同源 `/static/home_explanation_authoring.md`，本指南同时由 Home 每次发送上下文指向。

清单格式：

```json
{
  "schema": "portal-explanation/v1",
  "title": "解释主题",
  "summary": "读者将理解的关系",
  "revision": 1,
  "quality": "medium",
  "interaction": {"address": "workspace_ID/file/包目录/interaction.html", "sha256": "实际64位SHA256", "title": "互动图解"},
  "supplement": {"address": "workspace_ID/file/包目录/supplement.md", "sha256": "实际64位SHA256"},
  "video_plan": {"address": "workspace_ID/file/包目录/generation-plan.json", "sha256": "实际64位SHA256"},
  "sources": [{"label": "原始材料", "url": "https://原始材料页面"}]
}
```

只保留实际有用的模块。`quality` 为 low、medium 或 high，构建命令必须显式传入当前有效档位，不提供省略后的默认值；low 包只保留 Markdown supplement，直接文件也可用 Preview 打开。引用也可包含已生成的 `video`，其中 `address/sha256` 指向 MP4，`captions` 与 `transcript` 各带地址和摘要，`chapters` 为 `[{time:秒,title}]`。普通 HTML 文件在 Preview 中仍是代码；解释包的 interaction 才进入隔离宿主。自包含 HTML 内联样式、脚本、数据和所需库，禁止远程依赖及父页面访问。大型图按需更新，不维持无用动画。

视频计划使用 `portal-explanation-video/v1`，包含 title、scenes、audio、cues；不执行作者脚本。新计算画面使用 scene.visual 的封闭操作，支持点积、归一化、逐项贡献、单条件对比、矩阵、投影、多头管线和步骤索引；数据与事件完整字段见[声明式计算画面合同](/static/home_explanation_video_contract.md)。旧节点图计划仍支持 nodes、edges 和 values。每个 scene 按真实音轨声明 start/end 秒；cues 为实际逐句时间及 text，visual.events 按真实cue安排绝对秒动作，不得按字数猜测配音时长。

视频 low 可采用已有节点图计划。所有新生成的 medium/high 视频都需要正式作者任务及其完成证明，即使旧计划已有合法 `visual.events` 也不能直接跳过。没有本次质量对应的 `authoring_proof` 时，显式生成操作先派发带质量指导的创作任务，不开始渲染。作者须按任务中的固定来源实际修改分镜，每段提供与真实字幕对应的 `visual.events`，保存新固定版并完成正式回填；只改标题、JSON排版或质量标签均不算修改。medium 按 3Blue1Brown 式概念递进、连续图形与音画同步要求创作；high 还须实际独立审片。结构检查和创作回填成功均不代表审核通过。已 ready 的旧视频仍可只读恢复，不因重开自动生成或投递任务。

audio 为同包固定 MP3 或 PCM16 WAV 的正式 address/sha256。Portal检查当前主体的读取权限、固定摘要和媒体格式。计划顶层的创作注释不参与渲染，也不会由Portal读取或执行。原始MP3可逐字节复制，转码/混音须另记派生关系，不能借用源SHA。已有音轨、附件与 ready 视频保持原件，继续按普通资源权限读取。

句内有多个因果动作时，依据固定音轨实际内容安排事件与字幕时间。没有真实对齐依据时保留未对齐，不按字符比例、旧音轨或估时编造新时序。可读停顿和音质仍需连续观看及具备能力时的听辨；求和、缩放等不同推理步骤应各有清楚的语言和阅读时间。

计划与音轨必须与 manifest 处于同一 Workspace、同一包目录。生成服务逐次重新鉴权各来源，检查摘要、音轨绑定和目标写权限；medium 结果持久保存在 `包目录/explanation-media/<manifestSHA>/`，low/high 使用 `<manifestSHA>-<quality>/`，遵循同一 Workspace 的访问与删除规则。媒体读取、生成和重试均显式带视频 quality，不能把其他质量的成片当成本次结果。

high 视频保存完成后，服务按实际生成 actor 查找唯一、可投递的“讲解视频独立检查” Resident，并发送固定 manifest、视频、字幕、讲稿及来源引用。检查员使用自身权限。`submitted` 表示任务已投递，只有固定版本的正式审核记录为 `passed` 才表示通过。`changes_requested` 要求作者另存修订后重审；`blocked`、`cancelled`、`submission_failed` 保留真实原因，不自动降级。low/medium 不要求独立送审。页面的独立检查重试对应 `POST /api/home-explanation/media/review`，提交 `{address,sha256,quality}`，按原请求 actor 重试，保留播放器、不重编码；送检重试有上限。GET、刷新和重开不自动投递。

常用构建入口（占位值需替换为自己正式绑定与文件）：

```bash
python3 scripts/build_explanation_package.py '<包目录>' \
  --address 'workspace_ID/file/<包目录>' --title '<主题>' \
  --interaction interaction.html --supplement supplement.md \
  --video-plan generation-plan.json --resident-id '<自己的ResidentID>' \
  --quality high --task '<读者当前困惑、读完能判断什么>'
```

构建命令必须显式填写 `--quality`，采用本次有效质量要求；省略时在写入前报错，避免遗漏参数把 high 默认为 medium 并跳过审查。构建器核对文件、生成固定摘要清单，再经当前作者身份的 HATG ReadResource 回读；选择 high 时触发独立检查，low/medium 不强制送审。它用 SearchResidents 发现唯一可投递的“解释页独立检查”；也可用 `--reviewer` 指定已正式查得的检查 Resident。检查者不能是作者本人。不直接读取别人的凭据，也不代签通过。

完成视频创作任务时，负责 Resident 本人在上述构建命令中增加 `--authoring-id '<正式任务ID>'`，并使用任务规定的 `--quality medium` 或 `--quality high`、新包目录与修订。构建器先保存并回读新清单，再回填创作任务；选择 high 时，回填成功后才送独立检查。回填失败须保留失败，不把已保存的包视为已完成任务，也不继续送审。

正式回填是 `POST /api/home-explanation/media/authoring`，请求为 `{address,sha256,quality,authoring_id}`，其中 address/sha256 指新 manifest。服务核验原任务来源、质量、实际负责 Resident 身份、未取消状态，以及新旧计划的实际语义变化；不能在客户端自行添加证明。回填后对新固定清单显式请求生成视频，生成前与产物发布前再次核验任务状态。证明不能跨质量档复用；取消或核验失败不能借旧证明继续生成。

已有作者工具生成的清单，或提交中断后的同版重试，使用：

```bash
python3 scripts/submit_explanation_review.py --resident-id '<自己的ResidentID>' \
  --address 'workspace_ID/file/<包目录>/manifest.json' --sha256 '<实际摘要>' \
  --task '<理解任务>'
```

相同作者、检查者、清单地址和 SHA 使用同一幂等提交键，不重复投递检查。回执 `submitted` 仅表明受理；检查者以自己的权限读取并真实操作，报告保存其 Workspace。作者读取该报告，核对清单地址和 SHA，再修复被指出的问题、生成新固定版并只复验受影响路径。检查者无法读取或打开时记录 blocked 及精确缺口，不改 ACL 来冒充通过。未完成检查的页面可以明确作为待检查预览，不得称已经验收。

用同一脚本 `--read '<review_id>'` 回读正式结论，原请求者可用 `--cancel '<review_id>'` 取消。独立审核者以自己的 `--resident-id` 加 `--verdict-file '<结论JSON路径>'` 提交：JSON 含 `review_id`、当前固定 `digest`、`status`（passed/changes_requested/blocked）、`evidence:[{address,sha256}]` 和可操作的 `feedback`。服务验证实际鉴权主体必须为该请求的审核者，不能是作者或请求者；通过必须有真实检查证据。该脚本通过同源 `/api/home-explanation/reviews` 读取或提交，`/verdict` 记录结论，`/cancel` 取消。请求已受理和作者写的通过声明均不替代此记录。

正式结论保存后，服务向真实作者投递固定版本的反馈；投递失败另存 `feedback_delivery`，不把通知失败改写为审核通过。作者收到 changes_requested 后按意见生成新固定版，以 `--previous-review-id '<原review_id>'` 关联上次审核并再提交。质量修订不设固定轮数上限，每轮须有实际修改的新摘要和可检查证据；相同版不会凭重试获得新结论。传输重试仍有限，权限缺失、取消和无法继续的真实原因须如实保留，不能无限忙重试或自动降级通过。只读回结果不会触发通知或新审核。

high 质量生成链路须完成上述独立检查，手写 high 清单也要送检。不要在打开历史、刷新页面或普通读取时重复触发检查。独立检查与产品正式 User TAU 分开，不能代替真实门面对话验证。

打开动作仍使用本次 Home request_id 的 `portal-home-display/v1`，`view:explanation` 与 `target:{address,sha256}`。正文只展示读者需要的结论、页面入口和真实检查状态；不把内部协议当作品。固定展示、未保存草稿、手动选择和迟到保护仍由 Home 宿主管理。

来源汇报由 User 点击聊天按钮保存时，创建者仍是该 User。Home 附带对话 Resident、真实消息 ID 和代码围栏序号作为待核对的出处；服务须以当前身份回读正式消息，验证展示意图后绑定负责修订的 Resident，不能信任客户端 `author` 或按名称猜测个人门面。审核反馈和 medium 视频分镜修改任务发给该已核验的负责者。作者要据固定报告与具体反馈实际修改图形、讲稿和分镜，保存新版本后再生成或送审；修改质量标签或收到任务均不等于完成。手动来源没有可核验回复时应明确待指定负责者，保留可读报告，不把通知 User 算作 Resident 修订闭环。

创作任务与质量审核是两种不同的记录。收到 `portal-quality-authoring/v1` 后，作者可用 `scripts/submit_explanation_review.py --resident-id '<自己的ResidentID>' --read-authoring '<authoring_id>'` 读取正式任务；开始和提交成果前都核对未取消。报告分支沿正式 UpdateResource 的 `content={authoring_id,presentation}` 提交实际修订，由报告域核验负责者和内容变化，再生成新revision的媒体；不把解释页的 visual 计划字段套给报告 presentation。创作任务的 `submitted` 只表示已通知作者，不能称为已完成修改或审核通过。GET任务、打开报告或恢复旧视频不会自动再派任务。
