# macOS 桌面安装与数据归属

测试构建与公开发布分开授权。“重新打包”“给我试用”仅生成测试文件，保存到
Workspace 后通过 Portal 直接交付；用户明确要求“发布到 GitHub”才创建公开 Release。
普通源码提交和版本号更新均不触发打包或发布。用户要求测试包时，可更新
`code/scripts/macos/test-build.json` 的请求编号并推送到 main，触发双架构测试构建；
这一入口不能创建 Release。手动工作流默认只构建，临时归档保留一天；
公开发布须显式开启 publish_to_github，发布脚本也要求 --publish-to-github。
已交付的 20261022.2 包仍需独立目录复测；兼容升级实现须经过原生构建检查后才随后续测试包交付。

macOS 桌面发行沿用共享安装器的实例隔离、数据库迁移、可选案例筛选和健康检查契约。
两种架构分别构建，DMG 内提供应用包与 Applications 快捷入口。应用包携带固定摘要的
Python、PostgreSQL、NATS、Node.js，以及构建时安装并验证的核心 Python 包及完整间接依赖。
两种芯片分别维护 `scripts/macos/requirements-core-{arm64,x86_64}.lock`；离线 wheel 文件、
版本、摘要、Python ABI、芯片与目标系统依赖条件均在构建时校验。Windows 与 macOS
复用同一依赖闭包校验器；Intel 缺少新版官方 wheel 的组件及配套 WebAuthn 版本显式锁定，
普通构建不解析新版本，不将源码编译交给用户。
准备基础平台不依赖用户的全局 Python，也不安装 TeX 等可选工具。Provider 工具及在线 AI 仍需联网。
每包携带 `dependencies/python-wheels/` 与锁文件，回执记录架构、摘要与文件清单。
预装环境优先复用；缺件时只从包内 wheelhouse 安装到托管虚拟环境，使用 `--no-index`、
`--require-hashes` 与二进制包限制，缺失或损坏即报错，不联网回退。环境标识纳入实际架构锁文件。
原生构建先做 `pip check`，再在全新虚拟环境验证离线安装、核心依赖检查和 WebAuthn/CBOR 调用。
发布回执必须同时包含这组验证结果和正确架构的离线材料信息。
欢迎页使用“欢迎安装 The Fourth Institute”标题，正文仅保留产品说明及 macOS 15+
试用版、基础安装无需联网的信息，提供 Lenia 选项与进入按钮。
欢迎页显示现有 TFI Logo；构建时用同一 PNG 生成完整尺寸的 ICNS，并在 Info.plist
声明应用图标，全部资源组装后再签名。
首次安装的进度页直接从只读应用包加载 Logo，避免依赖尚未复制的目标目录；
欢迎页与进度页都显式设置 Tk 图标。Dock 的实际展示仍由 macOS 原生验证确认。

只读应用包首次复制到用户的 `~/Library/TFI` 后运行；代码和依赖共享，实例数据放在
`instance/desktop`。核心 RPC 与登录 IPC 按地址编码后的字节数选择本地传输；当地址
超过 macOS Unix Socket 容量时，使用仅监听 loopback 的临时 TCP 端口和私有发现文件。
服务端与客户端在发送业务数据前相互校验 HMAC；发现文件保持 0600，目录保持 0700，
并校验当前用户归属和 ACL。完整逻辑路径及 RPC 签名密钥位置保持不变，隔离不同实例。
Python 与 Node 使用相同选择规则，短路径继续使用 Unix Socket；测试覆盖长中文路径
及旧监听器关闭后新监听器仍可连接。原生安装验收使用使 Web RPC 超出 Unix 地址容量
的中文安装目录。PostgreSQL 保留原生 Unix Socket 和本机身份隔离，安装前按其实际
套接字文件名检查路径容量；超出时明确提示数据库地址过长。
后台服务使用
launchd 用户任务，首次初始化的数据库采用 UTF-8 编码及可用的 C locale。
应用的 HOME 隔离到实例后，通过 `TFI_MACOS_SERVICE_DIRECTORY` 保留操作系统用户的
LaunchAgents 目录；服务管理器和所有权检查共同使用该目录，不能回退到实例 HOME。
核心依赖清单检查禁用 pip 自身的在线版本查询。
私有文件以已打开的描述符核验所有者、模式和 ACL；Darwin 对不存在的扩展 ACL 返回
`NULL/ENOENT`，该状态按无 ACL 处理。扩展 ACL 允许限制访问的 deny 条目，以及经
Darwin membership UUID 确认为当前用户的 allow 条目；其他主体的授权（包括仅供子项
继承的授权）、未知条目、身份解析或 ACL 查询失败均拒绝，不清除或重写已有 ACL。
原生构建先验证私有文件读写、当前用户授权和 deny 条目的兼容性，以及其他主体
授权的拒绝行为，再启动实例服务。
RPC 监听器可保持非阻塞以支持代际切换，但每条已接受连接显式恢复阻塞读取，避免
macOS 继承监听器模式后把暂时没有请求字节误判为连接结束。
实例监听 loopback，首次管理员邀请保存在实例私有目录并交给浏览器，不进入安装日志。
启动健康检查直接连接本机端口，不读取系统 HTTP 代理设置；HTTP 错误的非 JSON
响应保留状态码，不显示 JSON 解码异常。失败诊断同时收集组件 stdout 与 launchd
独立的 `.error.log` 末尾，以便看见 Web 进程退出的具体原因。

Lenia 选择在解压前保存。构建机完成 seed 校验与工程生成，再分别打包基础和带案例工程。
安装时从应用包直接解压选定工程至 `.build/m`，不复制工程压缩包，不生成 seed 中间目录。
取消选择仅提取基础工程，数据库与资料使用同一选择。安装阶段跳过全量文件扫描、
逐文件 SHA 和共享代码重复比对；构建校验、解压时的 CRC、路径边界、实例归属及健康检查保留。
运行环境复制与工程解压显示文件数、已处理 MiB 和百分比；大文件按块更新、限频输出。
安装选项和目标参数均通过临时文件原子替换，写入中断后不遗留半截配置。
首次复制由启动窗口的工作线程处理，界面持续刷新；复制失败的日志保存在目标目录之外，
避免日志使空目录变成非空而阻止重试。
发生中断后沿用原工程与选项，不通过重试覆盖数据库。重复启动复用已有实例和账号。
欢迎页发现不同版本时提供“升级并保留资料”，命令行须显式传入 `--upgrade`。
桌面升级由 `tfi_macos_upgrade` 管理共享代码目录事务，沿用实例生命周期与静默任务检查，
不调用要求独立工程目录的通用 `upgrade`，也不重新导入案例、创建管理员或重置安装选项。
首次支持同芯片、相同内置 Python/PostgreSQL/NATS/Node.js、相同 Python 依赖声明及离线依赖回执的代码更新。
从没有离线 wheelhouse 的旧包迁移或更换锁定依赖时，使用独立目录试用，保留原资料。
运行环境变化、多实例、外部数据或数据库存储重定向仍拒绝自动升级。未完成初始化的实例先完成原安装。
升级关闭 Web/Society 入口，确认无运行或排队任务，停止核心服务和所属 Provider 后台。
本地资料、账号、配置、数据库和用户安装的工具复制到待切换目录；文件复制显示具体进度，
不重新做 Lenia 全量 SHA 校验。旧工程解压缓存不复制，原实例身份及首次 seed 记录保留；
当前应用版本由 macos-package.json 记录，区别于初始工程 manifest。
旧目录整体改名为备份，新目录切换到同一路径，既有服务和账号路径不变。
就绪后才完成事务。失败或崩溃重试按外部持久日志恢复原目录；新版本产生的写入保留在失败现场。
进程未退出时禁止恢复，保留两个目录等待处理。备份是私有用户资料，保存在相邻
`.<目录名>-launcher/upgrade-<id>/previous` 中；不会作为旧安装包自动删除。
升级和恢复先核验控制目录与备份容器的当前用户归属、0700 模式和扩展 ACL；
容器权限检查失败时不停止或切换原实例。新文件在写入数据前以 0600 创建并验证 ACL，
复制结束再恢复原模式和时间，保留工具的可执行权限。
升级记录与待切换目录不在活动实例内，避免备份递归及切换中断后丢失恢复入口。
每次原生构建用独立实例和真实数据库行验证兼容更新；模拟不同回执覆盖目录切换，
不将其称作对所有历史版本数据库迁移的验收。
停止与移除 launchd 项使用正式生命周期，并保留数据；删除应用不代表删除实例。
停止请求返回后等待进程实际退出，再移除启动项；超过等待上限则保留失败状态与诊断。
Codex 账号启动项按实例目录摘要定位，并核验完整命令、账号目录和日志归属；停止与注销
包含这些启动项，其他实例的账号不受影响，账号数据继续保留。
账号的 launchd 启动项显式保存内置 Node.js 所在的 PATH、实例 HOME、缓存目录及站点
配置路径；launchd 不继承发起登录的 Web 进程环境。代理凭据通过配置文件在后台启动时
读取，不写入 plist；账号 CODEX_HOME 由显式账号目录确定。首次修复旧启动项时，仅接受
命令、账号、日志和工作目录匹配的旧定义，在账号锁内停止并原子替换；允许补齐缺少的环境
字段，或将与配置入口指向同一文件的版本路径恢复为稳定入口。后续运行时切换版本不改变
账号启动项。比较不会接受不同程序、账号、工作目录或日志位置。
外来或被修改的启动项仍拒绝覆盖。进程启动后须等模型目录可用再提交测试；超时和启动失败
说明本地后台尚未就绪、授权仍保留，并允许重试。界面在登录、状态检查和后台启动期间显示
当前步骤与已等待时间，持续覆盖测试排队及运行阶段，关闭弹窗后停止轮询与计时。
登录状态读取失败保留错误提示，服务端取消登录视为终态。
macOS Unix socket 的地址按编码字节检查；超过系统路径长度限制时，后台和客户端使用
同一逻辑地址摘要定位 `/tmp/tfi-codex-<uid>-<digest>/rpc.sock`，私有目录按用户、实例和
账号隔离，不依赖各进程的 TMPDIR。短路径保持原地址，退出时只移除本次启动拥有的 socket。

发布流程分别在 Apple Silicon 和 Intel macOS runner 上构建，验证依赖、两种工程的
真实数据库导入、服务、登录页、重复启动与注销后重新启动后才组装 DMG。验收经过实际
应用可执行入口，并用 Tk 事件循环验证复制时界面响应、失败后的重试与浏览器交接；
浏览器交接使用测试替身，不启动外部浏览器。安装和清理同时失败时保留两处异常。
原生构建额外使用验证专用 Codex 和空账号，通过真实 launchd 执行生产启动项生成逻辑，
验证模型目录、未登录账号状态、短路径及长中文路径通信与退出清理。验证工具不写入
应用包，也不进行授权或模型推理；构建回执单独记录此项结果。
获得明确公开发布授权后，两种架构均通过才统一发布 GitHub prerelease，
校验源提交、原生验证记录和文件摘要。成功上传后调用共享
`tfi_preview_retention.py --platform macos`，由它核验完整新版后清理旧 preview Release、
附件及对应标签。仅保留最新成功的一版，arm64/x64 同版一并保留；构建失败或上传未完成
不删除当前可用版。应用在 Info.plist、运行环境和资源组装完成后做 ad-hoc 签名，原生
启动验证后再次执行严格签名校验；DMG 生成后只读挂载，核验其中应用签名及可执行入口。
发布要求两架构均有应用和 DMG 内应用的校验通过记录。签名及全量资源校验仅在构建机执行，
不增加安装阶段的扫描。ad-hoc 签名只验证内容完整性，不能证明开发者身份，也不构成
Apple 公证；Developer ID、公证和用户设备上的完整 Finder 交互验收仍独立于这些检查。
