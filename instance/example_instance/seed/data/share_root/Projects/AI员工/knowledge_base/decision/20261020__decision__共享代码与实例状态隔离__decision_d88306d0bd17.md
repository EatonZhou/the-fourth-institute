# Portal 实例协议

规范所有者：实例安装与生命周期模块。

## 实例是什么

实例是一个独立运行的 Portal 站点。它包含一整套业务内容，例如用户、权限、Resident、对话、知识、Lineage、Workspace 登记，以及为这套内容运行的全部服务和数据。

- **核心是数据库**：每个实例有自己的数据库。数据库里记录的内容，以及必须与数据库保持一致的文件，都属于这个实例。
- **判定规则**：一样东西如果必须和数据库一起备份、一起搬走才能保持一致，它就属于实例。多个实例或人可以同时使用、不需要彼此协调的东西，属于主机层或代码层。
- **实例之间**：不共享可写的东西。一个实例需要另一个实例的内容时，通过对方的网络接口访问，不直接读写对方的目录或数据库。
- **一台主机上的实例**：可以有多个，各自启动和停止。测试框架为一次完整测试搭建的站点也是实例，按本协议创建，用完退役。单元测试在共享测试数据库中用 schema 隔离的夹具不是实例；它们需要文件路径时，由夹具生成一个只有清单的临时实例根目录，同样从清单取得路径，不用环境变量逐项指定路径。

## 三层归属

一台主机上和 Portal 有关的东西分成三层：代码层是 Portal 的程序本身，主机层是主机和它的用户自己的东西，实例层是某一个站点独有的数据。属于哪一层，决定了谁可以修改它，以及备份、搬迁、退役时要不要带上它。

### 代码层

代码层是 Portal 的程序文件，包括：
- 应用代码；
- 数据库结构的定义，以及从旧结构更新到新结构的步骤；
- 按版本复用的依赖，例如 Python 环境、Node、PostgreSQL、NATS、TeX、浏览器、Provider CLI 程序。

一份代码放在一个代码目录里，也就是 Git 仓库的一个检出（clone 或 worktree），目录下有 `code/`、`instance/` 等子目录。依赖按版本放在代码目录的 `dependencies/` 中，可被多份代码复用。用哪个版本由代码决定：代码中的依赖清单写明需要的 Python 包、Node 等版本，服务按它找到对应版本的环境。实例清单不记录这些环境，代码换了依赖也不用改实例配置。

一台主机上可以有多个代码目录，例如一个实例的 Release 部署和 Dev 部署各用一个：Release 部署的代码与远端仓库一致；Dev 部署的代码是开发中的工作树，可以含未提交的修改。代码怎样提交、推送、从 Dev 发布到 Release，属于开发流程，见《Portal 共享运行基础与 Dev 到 Release 的发布流程》，本协议不规定。

规则如下：
- **只读**：多个实例可以同时使用同一个代码目录。实例的服务进程只读代码，代码目录也不记录任何实例的位置。开发者修改 Dev 代码目录属于开发流程，不是实例的写入。
- **核心 Skill**：`code/core_skills/` 下有四个 Skill，属于代码层：`tfi-agent-rule`（所有 Resident 的共用规则）、`tfi-unified-id`（资源 ID 与地址解析）、`manage-knowledge-base`（项目知识库的操作方法）和 `create-skill`（编写 Skill 的方法）。它们说明的是这一版代码的指令、路径和做法；后两个是共用规则要求必读的，如果放在实例里，新装的实例就会缺少它们。拼 Resident 系统规则的后台服务和 Resident 直接读取所运行代码目录中的这些文件，实例里不放副本。这样规则和执行指令的代码总是同一版本，也只能经开发流程修改。站点需要补充的规则，另写成实例中的 Skill。
- **随代码带来的实例内容**：有些内容由代码定义，却要写进实例、允许在实例中修改，例如内置权限方案的规则。创建实例时把它们写入数据库；以后代码更新、服务重启时，服务把代码中的新版本合并进数据库，保留实例中的编辑。写入后它们就是实例数据，随实例备份和搬迁。

### 主机层

主机层由主机和运行服务的操作系统用户拥有，可被多个实例和人共同使用。这些东西放在哪里、怎样组织，由主机和它的用户自己决定，本协议不规定；本协议只规定实例怎样使用它们。主机层包括：
- 订阅账号目录，见「执行账号目录」；
- 模型权重、数据集等大型资料；
- 操作系统用户的主目录（HOME），以及其中的工具配置、SSH 与 Git 身份、开发环境和下载缓存，例如 conda 环境和 pip、Hugging Face、PyTorch 缓存；
- 系统级配置，例如开机时启动的服务、文件共享、防火墙；
- 被登记为 Workspace 或代码仓库、位于实例各区域之外的目录，见「登记的目录」。

实例使用主机层的东西时：
- **只引用**：实例在数据库里记下它们的位置，用的时候到那里读写，但不移动、不改名、不删除它们。实例退役时它们原样留下。唯一的例外是账号目录中本实例登记过的会话，见「执行账号目录」的「会话」一项。
- **系统配置**：由主机管理员维护，安装器不修改。实例需要的系统配置（例如让局域网能访问网页端口），由安装器告诉管理员。

### 实例层

以下内容由实例独占，随实例创建、备份、搬迁和退役：
- 数据库集群和 NATS（实例内部服务之间传递消息用的程序）；
- 清单、站点设置与密钥；
- 各区域中的文件，见「目录布局与数据存储」；
- Portal 自己的缓存；
- 运行文件，即 socket、锁、日志、临时文件；
- 服务单元和端口。

### 登记的目录

Resident 的 Workspace、代码仓库（`repo_*`）等资源登记的是一个目录。Workspace 可以登记主机上的任意目录，代码仓库登记的是一个已有的 Git 检出。登记本身记在数据库里，属于实例；目录本身归谁，看它在哪里：

- **在实例的某个区域之内**：目录属于实例，例如每个 Resident 自有的 Workspace，它在所属 Lineage 的目录下。登记按“区域 + 相对路径”保存，目录随实例备份和搬迁。
- **在所有区域之外**：目录属于主机，例如人自己的项目目录。登记保存绝对路径；备份、搬迁、退役都不复制、不移动、不删除这些目录。
- **不登记其他实例的目录**：登记的目录不能落在本机其他实例的实例根目录或区域内，登记时按本机实例登记检查。实例之间不共享可写的东西，需要另一个实例的内容时，通过它的网络接口访问。

## 实例内的部署

一个实例运行一组后端服务（Resource、Society、Execution、Worker 等）和若干部署。部署是用某一份代码对外提供网页和接口的入口：
- **Release 部署**：每个实例都有。
- **Dev 部署**：可选，供开发使用。

部署之间的边界如下：
- **共用**：各部署共用实例的数据库、数据和后端服务。
- **各自拥有**：代码引用、网页端口、socket，以及部署自己的运行文件。
- **后端服务用哪份代码**：有 Dev 部署时使用 Dev 部署的代码，没有时使用 Release 部署的代码。

两个部署之间的发布流程见《Portal 共享运行基础与 Dev 到 Release 的发布流程》，路由规则见《Portal Dev 与 Release 部署、用户路由与服务控制面》。

用词约定：
- 进程通过 `PORTAL_DEPLOYMENT` 得知自己属于哪个部署，取值为 `release` 或 `dev`。
- “实例”只指整个站点，不用来称呼部署。
- 实例级的配置统称“实例配置”，不称为“部署配置”。

## 示例实例

`instance/example_instance/` 是随开源代码发布的示例实例，新用户从它创建自己的实例。

- **仓库中的内容**：仓库里只保存它的发布内容 `seed/`，包括数据库导出、文件、文件清单和完整性摘要，不含账号、密钥或运行产物。
- **内容来源**：发布内容由导出工具从来源实例生成并脱敏。
- **完整性**：发布内容带文件清单、摘要、数据库格式和资源路径映射。准备脚本 `prepare_install.py` 在安装前校验这些内容，并从当前代码组装安装工程；它不修改任何运行中的数据库。

从示例实例创建实例时，安装器读取代码目录中的发布内容，在代码目录之外建立实例根目录（见「本机实例登记」中的「实例放在哪里」）。代码目录里只有发布内容，不放任何实例的数据。同一份发布内容可以创建多个实例，每个实例有自己的名称和 instance_id，此后各自运行和维护。

## 身份与清单

### 身份

每个实例有三个标识：

- **`instance_id`**：创建实例时生成，此后不变；实例搬到新路径或另一台主机后仍用原来的 ID。浏览器本地存储等需要按实例区分的数据，以它作为命名空间，同一个浏览器访问两个实例时不会混在一起。
- **名称**：在一台主机上唯一，用来在命令行和管理界面中选择实例，也是实例根目录的默认目录名。
- **服务名前缀**：创建时确定并写入清单，此后不变，在主机上唯一。实例的每个服务单元命名为 `<前缀>-<组件>`，看服务名就知道它属于哪个实例。

### 实例根目录下的三类配置

实例根目录下的 `instance.json` 是实例的清单。实例的基础配置只写在这里，服务、脚本和工具都从它读取。它记录：

- **身份**：instance_id、名称、创建时间，以及创建时所用示例实例的版本。
- **部署**：每个部署的 ID、类型、代码根和网页端口。
- **网络**：监听地址、实例入口端口、PostgreSQL 与 NATS 端口。
- **服务**：服务名前缀和服务清单，包括入口网关。
- **依赖**：和实例数据绑定的程序的位置，例如版本必须与数据库集群一致的 PostgreSQL、保存本实例备份的备份程序。Python、Node 等运行环境跟着代码走（见「代码层」），不写在这里。
- **区域位置**：各区域的目录，见「目录布局与数据存储」。不写的区域使用默认位置；写了的必须是绝对路径。

另外两类配置：
- **站点设置**：`site.json` 保存认证、备份、Provider、Pulse、通知等功能的设置，不含路径。在管理界面中修改这些功能设置，改的就是它。
- **密钥**：数据库连接串、签名密钥、外部服务凭据放在实例根目录的 `secrets/`，不写进清单或站点设置。

### 读取清单

- **统一入口**：由一个模块读取和校验清单。服务、脚本、测试、安装器和桌面启动器都通过它取得路径与设置。
- **环境变量**：
  - 服务进程只接收 `PORTAL_INSTANCE_ROOT`，网页进程另加 `PORTAL_DEPLOYMENT`；
  - 命令行工具用 `--instance <名称>` 或 `PORTAL_INSTANCE_ROOT` 选择实例。
- **不使用的来源**：
  - 不从当前目录、进程的 HOME 或用户级全局配置推导实例位置；
  - 不接受逐项路径环境变量覆盖清单。

## 目录布局与数据存储

### 目录布局

```text
<实例根目录>/
  instance.json        清单
  site.json            站点设置
  secrets/             密钥
  database/            PostgreSQL 集群
  data/<区域>/          各区域的默认位置，见下文
  cache/               Portal 自己的、可以重建的缓存
  runtime/             运行文件：socket、PID、锁、日志、临时文件；各部署自己的在 deployments/<部署>/ 下
```

除各区域外，这些位置都固定在实例根目录下，不可配置。代码按固定位置找到它们，数据库不保存它们的路径。

### 区域

实例的业务文件按内容分成以下区域：

| 区域 | 内容 |
| --- | --- |
| `projects` | 项目文件夹，每个项目一个，结构见下文 |
| `lineages` | 不属于任何项目的 Lineage 目录 |
| `skills` | 共享 Skill；核心 Skill 属于代码层，不在这里 |
| `papers` | 论文库 |
| `uploads` | 用户上传的文件，例如对话中的图片和附件；头像存在数据库中，不在这里 |
| `features` | 各功能自己的持久数据，例如 Paper 工作区、对话工作区、归档任务、工作台应用的构建产物 |
| `provider-state` | Portal 为 Provider 保存的本实例状态 |

项目文件夹的结构：

```text
<项目>/
  knowledge_base/       项目知识库：Design、Plan、概念、项目 Skill 等知识条目
  agents/<lineage_id>/  属于这个项目的 Lineage 目录，其中有各 Resident 的文件夹和自有 Workspace
```

项目文件夹中还可以有项目自己的其他资料。

- **默认位置**：`<实例根目录>/data/<区域>`。
- **放到别处**：某个区域需要放到别的位置（例如空间更大的另一块磁盘）时，在清单中写这个区域的绝对路径，并用「移动区域」操作搬运文件。只改这一个路径，在任何平台上都不需要系统权限。
- **整体放置**：区域只能整体放置。单个文件夹需要放到别处时，它就不再是实例文件，应作为主机目录登记，按下文规则二保存。
- **独占**：一个目录只属于一个实例的一个区域，不能与代码目录、主机资源、其他实例或本实例的其他区域重叠。
- **Lineage 目录的位置**：由数据库中 Lineage 的所属项目决定。
  - 属于项目的，放在 projects 区域的 `<项目>/agents/<lineage_id>/`，与项目知识库 `knowledge_base/` 并列。Lineage 目录里是 Resident 的文件夹、Workspace 和工作中产生的文件，不是知识条目，所以不放进知识库。
  - 不属于项目的，放在 lineages 区域的 `<lineage_id>/`。
  - 修改所属项目时移动目录。要找一个 Lineage 的目录，按所属项目计算，不设指向它的入口软链接。
- **工作台的文件**：工作台由三部分组成，分别存放。
  - 定义：页面、版本、关联的项目和绑定的 Lineage 存在数据库中，不占用区域。
  - 应用源码：是登记的代码仓库，按仓库目录所在的位置归属，在区域内就是实例文件，在区域外就属于主机。
  - 构建产物：放在 features 区域。产物按内容哈希命名，写入后不再修改；已发布的工作台版本按哈希引用产物中的文件，产物丢了这个版本就打不开。所以它和可以重建的 `cache/` 不同，要随实例备份。
  - 构建产物不放在项目文件夹中：一个工作台可以关联零个或多个项目，换版本时关联可以改变；Portal 自带的系统工作台不属于任何项目；内容相同的产物只存一份，可以被多个工作台共用。

### 路径的两条规则

Portal 在数据库和配置中保存文件位置时，只用以下两种形式：

1. **实例文件：区域 + 区域内的相对路径**，例如 `projects:<项目>/knowledge_base/plan/<文件>.md`。不保存绝对路径，也不保存相对于实例根目录或其他目录的路径。区域搬到哪里，只改清单里这个区域的位置，数据库里的记录都不用改。位置能由结构推出的不另存路径，例如知识条目由项目、类型和文件名定位。
2. **实例之外的目录：规范绝对路径**，即解析掉软链接和 `..` 之后的完整路径。包括登记为 Workspace 或代码仓库、位于各区域之外的目录，订阅账号目录，以及设备登记中的 SSH 配置文件。它们属于主机，不随实例备份、搬迁或退役；实例搬到另一台主机时，由搬迁更新这些登记。

- **不用软链接和挂载**：实例数据放在哪里，只由清单中的区域位置决定。区域目录本身和区域内的内容，都不能是指向区域之外的软链接或 Windows 目录联接；也不靠挂载把别的磁盘接进实例目录。这样只看清单就知道数据在哪里，备份和搬迁不会漏掉数据，也不会带上别处的文件。
- **文档中的写法**：Skill、Design 等文档提到实例文件时，也写“区域 + 相对路径”，例如 `skills:create-skill/SKILL.md`、`projects:<项目>/knowledge_base/`，不写某个实例的绝对路径，也不用旧的数据根占位符。人和 Resident 用安装器的命令行工具把它解析成本实例的实际路径；Resident 的系统规则中列出本实例各区域的位置。代码目录中的文件仍按代码目录写。
- **旧格式的路径**：旧版本在数据库里保存的绝对路径，由一次性转换改成上面两种形式；历史消息正文里写的路径不改。
- **不随实例带走的内容**：`runtime/` 中的进程、socket、锁和部署的签名密钥只对本次运行有效（签名密钥缺失时由服务重新生成），`cache/` 可以重建。备份和搬迁不带它们，服务启动时重新生成。

## 服务进程的 HOME

程序按环境变量 `HOME`（即 `~`）决定把配置、登录状态和缓存写到哪里，例如 `~/.config`、`~/.ssh`、`~/.cache`。

实例的服务使用运行服务的操作系统用户自己的 HOME，不另设目录。服务以及由它启动的进程，包括 Resident 调用的 Provider CLI 和 Resident 在终端里运行的命令，与人登录主机时看到的是同一个 `~`。

- **主机的事**：Git、Python、开发环境和下载缓存属于主机，放在哪里由人和 Resident 决定，Portal 不规定。Resident 可以使用主机上任何允许访问的目录，Workspace 也可以登记主机上的任意目录。
- **共用的后果**：Resident 与人使用同一个操作系统用户和同一个 HOME。Resident 修改全局工具配置（例如 `git config --global`、`pip install --user`）会直接作用于这个用户。
- **多个实例**：一台主机上的实例共用这个 HOME。

实例数据不放在 `~` 下：
- **Portal 的私有文件**：会话签名密钥、两步验证密钥等放在 `secrets/`。头像的记录和图片存在数据库中，不另存文件。
- **Provider 运行包**：Portal 安装的 Provider CLI 程序和运行包属于代码层依赖，按版本放在代码目录的 `dependencies/` 中。
- **Provider 运行状态**：Portal 为 Provider 保存的本实例状态放在 provider-state 区域，启动 Provider 时用它自己的变量指向这里。订阅账号的位置由账号登记决定。
- **临时文件**：服务的临时文件放在 `runtime/`。
- **会冲突的工具状态**：工具默认写进 `~`、又属于某个实例并会与其他实例冲突的状态，用该工具自己的变量指向实例目录，不靠改写 `HOME` 隔离。

服务单元不设置 `HOME`、`XDG_CONFIG_HOME`、`XDG_CACHE_HOME`；Windows 不改写 `USERPROFILE`、`APPDATA`、`LOCALAPPDATA`。判断一个服务属于哪个实例，看服务名前缀和 `PORTAL_INSTANCE_ROOT`。

## 与主机层的接口

### 本机实例登记

一台主机上可以装多个实例。运行服务的操作系统用户有一份本机实例登记 `~/.config/tfi/instances.json`，只记录本机装了哪些实例：每个实例的名称和实例根目录。`~` 取操作系统用户记录中的主目录：Linux 和 macOS 取 passwd 条目，Windows 取用户配置目录。

模型、数据集、缓存等主机资源不记在这里。

使用方式：
- **登记与注销**：创建实例时登记，退役时注销，搬迁时改成新的实例根目录。
- **查找实例**：安装器、管理界面和命令行工具都从本机实例登记查找实例，不扫描代码目录。
- **实例放在哪里**：新实例默认放在代码目录之外，由安装器按平台选在操作系统用户的数据目录下。主机管理员可以在创建时指定其他位置，例如服务器上的 `/var/lib/tfi/instances/<名称>`。实例根目录不能放在代码目录里：删除或重新检出代码目录、安装包整体替换程序目录时，实例数据会被一起删掉。

### 端口与服务名

- **主机内唯一**：实例的端口和服务名前缀在主机上唯一。创建实例或修改端口时，安装器读取本机实例登记中其他实例的清单，确认没有重复。
- **服务单元都带前缀**：实例的服务单元都使用 `<前缀>-<组件>` 命名，包括入口网关。启动和停止实例时，只处理清单中列出的服务单元。

### 执行账号目录

订阅登录类执行账号（Codex、Claude Code、Kimi Code、Antigravity 等）各有一个 Provider 原生目录，例如 Codex 的 `CODEX_HOME`、Claude Code 的 `CLAUDE_CONFIG_DIR`。目录里是登录凭据、会话记录，以及 Provider 自己的数据库和锁。

这个目录属于主机：同一台主机上的多个实例和人在终端里直接运行的 CLI，只要用同一个目录，就共享同一份登录和会话。实例只保存账号登记，并在登记中记录目录的绝对路径。API Key 类和服务类账号没有账号目录，key 由实例的 secrets 保存。

- **位置**：账号目录放在哪里，由主机用户决定，Portal 不规定默认位置。它可以是一个新建的空目录，也可以是人已经在终端里登录过的目录。
- **登记**：账号登记保存目录的规范绝对路径，不能是软链接。启动 Provider 时，只用这个路径设置 `CODEX_HOME`、`CLAUDE_CONFIG_DIR` 等变量；不从实例目录或 `HOME` 推导路径，也不靠修改 Unix `HOME` 来选择账号。
- **创建与接入**：
  - 登记订阅账号时必须给出账号目录。目录还不存在时，Portal 创建这个空目录，再进入登录流程；目录已经存在时直接登记。
  - 接入主机上已经登录的目录时，直接登记这个路径，不复制凭据文件。复制会让两处各持一份 refresh token，一方刷新后另一方就失效。
- **删除**：删除登记不删除目录。Portal 不移动、不改名账号目录，目录的整理由主机用户负责。
- **目录内容**：账号目录只放 Provider 自己写的文件。Portal 自己的文件，例如 socket、索引备份和作业记录，放在实例的 `runtime/` 下，不放进账号目录或它的上级目录。
- **常驻进程**：有些账号由 Portal 在后台运行一个常驻的 Provider 进程，例如 Codex app-server、Kimi server，它持续读写账号目录里的会话记录和 Provider 自己的数据库。
  - 一个账号目录同一时间只给一个实例运行常驻进程。另一个实例已经在用这个目录时，后启动的实例报告冲突，不再启动第二个。
  - 人在终端里直接运行 CLI 不受此限制。
- **会话**：Provider 的会话记录留在账号目录，实例数据库保存会话 ID 与 Resident 的对应关系。Portal 清理会话时，只处理本实例登记过的会话。
  - 有些 Provider 按工作目录的绝对路径保存会话和信任设置，例如 Claude Code 的项目文件夹、Codex 的信任目录、Kimi 的会话目录。Resident 的工作目录换了位置时（移动区域、搬迁、修改 Lineage 的所属项目），Portal 把本实例登记过的这些会话改到新路径，Resident 在原来的会话里接着工作；其他会话不动。
- **额度**：额度读数来自上游账号，多个实例登记同一目录时读到同一份额度。并发占用由各实例分别计算。

## 生命周期

实例的生命周期操作由安装器执行。命令行、桌面启动器和管理界面调用的是同一套操作。

- **创建**：从示例实例的发布内容创建一个新实例。
  - 安装器写出清单，初始化数据库和各区域，安装服务单元，写入本机实例登记。
  - 写清单前，安装器确认清单内容完整，端口和服务名前缀不与本机其他实例重复。
  - 新实例由首次管理员初始化建立第一个账号。
  - 默认创建后立即启动，也可以只创建不启动。
- **启动与停止**：只启停清单中列出的服务。停止时保留全部数据，下次启动接着用。
  - 两个实例可以同时运行，各用自己的端口。
  - 想从一个实例换到另一个，停止这个、启动那个即可。两个实例的数据各自在自己的实例根目录中，换用时不需要搬动或转换数据。
- **代码更新**：实例没有单独的“升级”操作。
  - 部署运行的就是它的代码目录中的代码，运行环境也按这份代码的依赖清单选择。代码按开发流程更新后，重启相应服务就生效；新代码需要的依赖版本还没有时，先准备好再重启。PostgreSQL 换大版本要先迁移数据库集群，这时才改清单中的位置。
  - 服务启动时自己完成新代码需要的数据库准备：把数据库结构更新到新代码需要的样子，并把随代码带来的实例内容（例如内置权限方案的规则）的新版本合并进来，保留实例中的编辑。
  - 示例实例的发布内容只在创建实例时使用，代码更新不会重新导入它。
- **备份**：
  - 用什么备份软件、备份存放在哪里，由备份软件自己设置，本协议不规定。
  - 需要备份的内容：数据库、各区域、`secrets/`、清单和站点设置。数据库要用 PostgreSQL 的一致性备份（例如 `pg_dump`），不能直接复制正在写入的数据库文件。
  - 先导出数据库，再复制各区域。数据库引用的文件大多只增加、不再修改，例如工作台的构建产物和新写的知识条目；按这个顺序，备份中数据库引用的文件都在。
  - 不需要备份的内容：`cache/`、`runtime/`。实例之外的目录（规则二）属于主机，不在实例备份中。
- **移动区域**：把一个区域整体搬到新目录，例如搬到空间更大的磁盘。
  - 先停止使用该区域的服务，把文件复制到新目录，确认复制完整后把新位置写入清单，再启动服务。
  - 数据库中按区域保存的路径不用改。Resident 的工作目录随之换了路径，按「执行账号目录」的「会话」一项迁移会话。历史消息正文里写着原位置的链接不再能打开。
  - 服务在新位置正常运行后，删除原目录。
- **搬迁**：把整个实例搬到新路径或另一台主机。instance_id 和数据库中的全部内容保持不变，包括用户和密码、Resident 和对话、账号登记、Workspace 等各种登记。
  - 搬迁时实例保持停止。在同一台主机上换路径，可以直接移动整个实例根目录；换主机时，在新主机上用备份恢复数据库，并复制各区域、`secrets/`、清单和站点设置。
  - 搬完后按新位置修改清单中写了绝对路径的区域位置，重新安装服务单元，并在本机实例登记中记下新的实例根目录。实例根目录或区域换了路径时，同样迁移 Resident 的会话。
  - 实例之外的目录和账号目录属于主机，不随实例复制。换主机时，需要继续使用的由主机管理员先在新主机上准备好，再在实例中更新这些登记的路径。
  - 新位置启动前，旧位置的实例必须已经停止，不能两边同时运行；否则两边会各自执行同样的定时任务、回复同样的外部消息。新位置确认正常后，删除旧位置的文件。
- **退役**：
  - 停止服务，删除服务单元，从本机实例登记中注销，删除实例根目录及其中的数据库。
  - 放在实例根目录之外的区域目录，退役时列出来，由操作者确认后删除。
  - 主机层的东西不受影响，例如账号目录、模型、实例之外的 Workspace 目录。

## 隔离规则

- **路径来源**：实例代码只从清单取得路径和身份。
- **不写其他层**：不写其他实例的目录、数据库和服务，不写代码层，不移动主机资源。
- **服务环境**：服务单元只带清单所需的环境变量，不继承其他实例的数据库地址、socket 或凭据，也不改写 `HOME`。
- **导出内容**：实例导出的内容（示例实例的发布内容、备份）不含主机资源，也不含其他实例的路径。

## 管理界面中的实例控制

Portal 管理在网络设置之后提供「Portal 实例」页面，用来查看本机的实例，并启动或关闭它们。

- **权限**：只有当前站点的 Portal 管理员可以读取同一主机的实例列表，并提交启动、关闭请求。权限系统关闭时也不放宽这个限制。
- **服务器接受的输入**：只有实例名称和 start/stop。不接受客户端指定的路径、命令，也不接受删除或安装操作。
- **列出哪些实例**：只列出本机实例登记中、并且清单能正常读取的实例。

实例状态：
- **来源**：按清单中的服务读取，区分运行、部分服务运行、关闭和无法读取。
- **限制**：尚未创建完成的实例不可启动。关闭时保留数据库、账号登记、对话和其他持久内容。
- **访问地址**：网页服务运行时，展示监听地址对应的主机 IP 与端口，不把通配地址当成可访问的网址。只监听本机的会明确标注。显示地址不代表已经验证客户端到主机的网络连通。

控制作业：
- **执行方式**：启动、关闭等操作由安装器执行。界面通过独立的控制作业调用安装器的 start/stop。
- **作业环境**：使用操作系统服务所有者的环境，不继承当前实例的数据库连接或 socket 配置。
- **Linux**：作业使用独立的 systemd 用户单元，所以关闭当前网页所在的实例时，作业仍能完成。
- **作业记录**：放在目标实例的 `runtime/` 下，保留失败信息。同一实例上一个作业还没结束时，不接受新的作业。
- **关闭提示**：关闭当前实例前，提示连接将断开。全部实例关闭后，需要从服务器的安装器或桌面启动器重新启动。

### 数据目录

Portal 管理中的「数据目录」页面只作用于当前实例。

- **显示**：实例根目录，以及各区域的位置、占用大小和所在磁盘的剩余空间。`secrets/`、`database/` 等固定位置只显示，不可修改。
- **修改**：Portal 管理员可以给某个区域填写新的绝对路径。服务器确认路径是绝对路径、不与其他位置重叠、磁盘空间足够后，通过控制作业执行「移动区域」，页面显示进度和结果。
