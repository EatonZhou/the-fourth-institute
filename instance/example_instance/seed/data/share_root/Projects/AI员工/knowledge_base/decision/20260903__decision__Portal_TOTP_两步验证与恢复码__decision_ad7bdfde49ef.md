# Portal TOTP 两步验证与恢复码

Portal 的安全设置允许用户把认证器应用加入自己的账号。启用后，密码登录还要输入认证器当前显示的六位动态口令；认证器不可用时，用户可以使用预先保存的一次性恢复码。本 Design 先介绍用户在设置页和登录页经历的流程，再说明动态口令算法、服务端存储和精确接口。

## 先认识两步验证

**TOTP** 是“基于时间的一次性密码”的英文缩写。认证器应用与 Portal 共享一段秘密种子，并根据当前时间独立计算六位数字，通常每三十秒变化一次。

**认证器**是保存种子并显示动态口令的用户设备或应用。Portal 通过二维码和可复制文本把种子交给认证器，后续不会向第三方服务发送它。

**恢复码**是在认证器不可用时使用的一次性备用凭据。启用两步验证或重新生成时，Portal 只向用户显示一次原文，服务端只保存摘要。

**待确认设置**是用户扫描二维码后、两步验证真正启用前的短期状态。用户需要输入新认证器生成的正确口令，证明种子已经保存成功。

**登录挑战**是密码正确后的短期中间步骤。它保存账号和剩余尝试次数，完成后才签发普通浏览器会话。

## 用户会经历什么

未启用两步验证时，安全设置显示“设置认证器”入口。用户输入当前密码后获得二维码和种子文本，扫描并输入六位口令完成确认。成功页面显示十枚恢复码，用户需要自行安全保存。

启用后，设置页显示剩余恢复码数量，并提供重新生成和停用操作。密码登录会在密码正确后进入验证码页面。任何操作失败都保留既有二步状态，Portal 不会因存储错误退回单因子登录。

## 设计点

### 设置与确认

- **用户通过当前密码开始设置认证器。** 已经启用 TOTP 的账号不能再次开始；成功开始只产生十分钟待确认状态，不会立即改变登录要求。
- **设置页同时提供二维码和可复制种子。** 两种形式包含同一账号、Portal 发行者名称和动态口令参数，用户可以选择适合认证器的录入方式。
- **用户必须用新认证器生成的口令确认设置。** 错误、过期或属于其他用户的设置 Token 不会启用 TOTP。最终写入在事务内再次确认账号尚未启用，较早创建的其他设置不能覆盖已启用种子。
- **确认成功后立即启用两步验证并显示恢复码。** Portal 保存种子和首次口令计数、生成十枚恢复码、撤销该用户全部 `dbu_` 个人令牌和其他浏览器旧会话，并只在本次响应展示恢复码原文。
- **Portal 重启会丢弃未确认设置。** 用户需要重新开始扫描；已经确认并保存的二步状态不受影响。

### 登录

- **启用 TOTP 的账号在密码正确后进入验证码页面。** 此时尚未建立普通浏览器会话，挑战默认五分钟有效并最多允许五次失败。
- **动态口令和恢复码都可以完成登录挑战。** 成功后 Portal 清除挑战、记录实际使用的因子类型并签发普通 `db_session`。
- **挑战失败会减少剩余次数。** 次数耗尽、挑战过期或 Portal 重启后，用户需要回到登录页重新输入密码。按账号累计的第二因子窗口保存在数据库中，重新建立挑战不会清除，见 decision_3bce8b455a3c。

### 恢复码

- **每枚恢复码只能成功使用一次。** 服务端在同一事务内验证并删除匹配摘要，之后再次输入同一码会失败。
- **重新生成会整体替换旧恢复码。** 操作要求当前密码和现有第二因子；新列表成功保存后，所有旧码与该用户全部 `dbu_` 个人令牌立即失效。
- **页面只显示恢复码剩余数量。** 日常安全状态不会返回种子、已接受口令计数或恢复码摘要。

### 停用和账号生命周期

- **停用 TOTP 要求当前密码和现有第二因子。** 成功后删除二步状态、撤销该用户全部 `dbu_` 个人令牌和其他浏览器旧会话，并让当前浏览器获得新版本会话。
- **停用账号保留 TOTP，永久删除才清理。** 停用用户无法登录，但恢复 active 后继续使用原有认证器；永久删除账号时移除二步记录。
- **同时遗失认证器和恢复码时，用户无法自行跳过两步验证。** 当前管理员控制面也没有直接重置他人 TOTP 的动作；无法提供所需的第二因子时，操作继续失败。

### 与其他账户操作的关系

- **启用 TOTP 后，修改密码和新增 Passkey 需要第二因子。** 这些操作先验证当前密码，再验证动态口令或消费恢复码。
- **不同因子的失败只影响自己的状态。** 错误动态口令不会消费恢复码，错误恢复码不会推进动态口令计数。
- **TOTP 状态不可读时不会跳过验证。** 密钥、密文或数据库状态损坏都会阻止登录和敏感操作，错误响应不暴露种子与密钥细节。

## 动态口令怎样产生和验证

Portal 按 RFC 6238 标准验证六位 TOTP。当前使用 HMAC-SHA1、三十秒周期，并接受前一个、当前和后一个时间窗口，以容忍设备时钟的轻微偏差。HMAC-SHA1 在这里是标准规定的口令计算函数；它使用共享种子和时间计数产生短数字，不用于保存普通密码。

PortalTwoFactorStore 记录最近已经接受的时间计数。新口令只有在匹配允许窗口且计数大于旧值时成功，因此同一口令不能重放。并发请求在同一数据库事务中读取最新计数并串行提交。

种子由 20 字节安全随机值产生，以 Base32 文本交付认证器。设置地址使用 `otpauth_uri` 格式，发行者名称缺省读取当前站点配置的 `site_name()`，显式传入的 `issuer` 优先，并绑定当前用户名；站点改名只影响展示名称，不改变已有种子或 TOTP 计算。二维码在 Portal 本地生成，不把种子发送到外部二维码服务。

## 服务端状态和秘密保护

PortalTwoFactorStore 按用户名保存三类状态：加密种子、最近接受的时间计数和恢复码摘要。种子使用 AES-GCM 加密；这是一种同时保护内容和检测篡改的加密方式，用户名参与完整性校验。独立 32 字节密钥和数据库状态只允许服务账号读取。

恢复码每枚包含 16 个随机字符，展示时采用便于抄写的分组形式。服务端使用带密钥的 HMAC-SHA256 保存摘要。开始设置的种子和登录挑战只存在当前 Portal 进程；确认后的二步状态持久保存。

最近一次成功动态口令计数存为 `last_counter`，其防重放规则见上文。

## 页面和接口协议

| 用户动作 | 接口 | 主要条件与结果 |
| --- | --- | --- |
| 读取安全状态 | `GET /api/account/security` | 返回是否启用、启用时间和恢复码剩余数量，不返回秘密 |
| 开始设置 | `POST /api/account/two-factor/setup` | 要求有效会话、同源和当前密码；返回设置 Token、种子、二维码与剩余时间 |
| 确认设置 | `POST /api/account/two-factor/confirm` | 要求当前用户的有效设置 Token 和匹配动态口令 |
| 完成密码登录 | `/login/verify` | 接受动态口令或恢复码，成功后签发统一浏览器会话 |
| 重新生成恢复码 | `POST /api/account/two-factor/recovery-codes` | 要求当前密码和现有第二因子；只返回新码一次 |
| 停用 TOTP | `POST /api/account/two-factor/disable` | 要求相同强度再认证；成功后删除二步状态 |

登录挑战通过独立 Cookie 交付，限制在 `/login` 路径，页面脚本不能读取，跨站请求不能携带。可信 HTTPS 入口还要求安全传输。挑战成功后 Cookie 被清除。

这些限制对应精确 Cookie 属性 `HttpOnly`、`SameSite=Strict` 和 `Path=/login`；可信 HTTPS 时增加 `Secure`。登录验证结果使用 `totp` 标记动态口令，使用 `recovery` 标记恢复码，便于审计记录实际采用的因子。

确认设置成功后写入 `two_factor_enabled` 审计事件，并增加账号 `session_version`。停用成功同样增加 `session_version`。两种操作都会为当前浏览器重签会话，使其他浏览器持有的旧版本会话失效。

## 组件职责与恢复

| 组件 | 职责 |
| --- | --- |
| Settings 前端 | 显示状态、收集当前密码和验证码、展示二维码及一次性恢复码 |
| 登录编排 | 在密码成功后建立短期挑战，并在第二因子成功后签发会话 |
| PortalTwoFactorStore | 持久保存并验证种子、计数和恢复码 |
| SessionAuthority | 使用验证结果签发统一浏览器会话，不接触 TOTP 种子 |

强制启用策略或新的第二因子应进入认证编排层。TOTP Store 继续只负责 TOTP 和恢复码证明。新的恢复流程必须明确认证强度、审计和失败处理，不能通过忽略不可读状态实现降级。
