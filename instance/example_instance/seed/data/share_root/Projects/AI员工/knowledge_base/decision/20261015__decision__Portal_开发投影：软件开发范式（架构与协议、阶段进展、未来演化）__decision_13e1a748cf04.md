# Portal 开发投影：软件开发范式（架构与协议、阶段进展、未来演化）

Portal 开发投影是 Portal 工程自身的软件开发工作台。它按投影协议 v2（decision_7a5ae487e2e9）把 Portal 的代码仓库、设计规范（`SPEC.md` 与 `decision_*`）、改进计划（`IMPROVE.md` 与 `plan_*`）和开发团队的工作组织成三个功能区，并在右侧提供与开发团队门面交谈的对话区。用户对 Portal 的理解、反馈和实现需求都在这个界面里表达：看架构、看进展、看方向，有想法或需求时直接告诉门面，由背后的 Lineage 完成设计、开发、验证和汇报。

这个工作台也是软件开发投影范式的第一个实例。功能区、产物和团队职责按通用方式描述，其他软件工程可以替换事实源后使用同一套范式。

Portal 的内置入口 `/development` 使用一个 Activity Rail 组合三个原生工作区：第一个是架构、进展、演化与开发团队 Chat，第二个是 WALL，第三个是 Test。WALL 和 Test 分别由 `/development?view=wall` 与 `?view=test` 直接定位。它们保留各自的资源、业务入口、所属 Lineage、权限和状态；WALL 与开发投影继续读取同一批 Design 和 Plan。切换仅改变可见性，保留已装配的投影 iframe、原生 Chat、草稿和原生面板实例；外层显隐同时通知面板生命周期和 SDK。WALL/Test 首次选中后才装配，其资源失败只影响相应视图，默认开发投影与 Chat 的启动不等待这些工作区。

实现状态：设计已确认，由专属开发 Lineage 实现和维护。

## 作者立场

这个工作台的每一部分都由团队成员作为**作者**完成。作者的工作是让读者真正理解 Portal、被它的进展和可能性打动，满足条文只是最低要求。本篇只规定每个功能区要回答的问题、内容的含义和应当避开的倾向，不规定呈现形式；形式由作者在研究内容之后自己决定，也可以推翻本篇中任何具体做法，只要效果更好。

AI Agent 有完成一件事的智能，却容易表现出一种保守的性格（见 thinking_c72047ece30c）：交出最难被挑错的东西而不是最好的东西；先选一个通用容器再把内容倒进去，于是处处是同一种形式；把要求中的例子当成标准照搬；花篇幅证明自己没做错。团队成员要有意识地反着做：

- **先研究内容，再为它决定形式。** 弄清每一块内容是什么、读者想用它做什么，再为它找到合适的呈现。不同的内容应当有不同的形式；同一种形式在工作台里反复出现，说明作者没有真正研究内容。
- **做自己作品的第一个用户。** 完成之后以读者的身份从头用一遍：是否一眼看懂，是否想继续探索，是否有地方让人厌烦。自己不满意就推翻重做，直到愿意把它拿给别人看。
- **有主见。** 敢于选择不常见但更好的方案，并为它负责。平庸才是失败；越出规范的具体做法不是。
- **说结果，不自我辩护。** 交付物和汇报讲做成了什么、效果如何，不附证据链，不罗列自己可能没做好的地方。

## 组织原则：以软件架构为骨架

界面以 Portal 的软件架构作为稳定骨架，Design、Plan、进展和反馈都挂在架构模块和协议上。设计点（Design 中的单句说明）只在追查依据时展开。

这样组织的原因是：脱离位置的设计点数量多、背景少，读者需要自己重建语境；挂在模块上的内容自带位置，读者先知道“这是哪一部分、和谁协作”，再决定是否深入。模块名称和导航层次保持稳定，变化集中在当前问题的表达上。

### 模块与协议的含义

**模块**是软件中承担相对稳定职责、可以单独指认的组成部分。架构从系统整体逐层深入，层次由真实职责与实现决定，不限定为“系统—运行单元—直属组件”三层，也不把文件目录或部署进程当作唯一的分解方式。一个组件可以继续包含有明确职责和协作契约的内部组件；没有进一步分解价值时，进入它自身的机制展示。

职责分解与部署位置分别表达。同一执行能力可能由调度服务、Runtime、Worker、Adapter等部分跨进程共同实现，进入该能力时应能理解这些关系；实际不在同一进程中的对象仍保留真实部署位置和边界。多个视角中的同一模块使用同一身份，不为让图看起来完整而制造包含关系。

**协议**是两个或多个模块之间约定的接口。协议是可以被搜索、被单独打开的一等对象，连接参与它的模块。

Design 文档本身不是模块，也不是协议，它描述某个模块或协议，挂在对应对象下面。跨多个模块的流程是**场景**，用来演示协议如何协作，不是架构中的组成部分。

检验架构表达是否合格的方式：拿它给一位新加入的工程师讲 Portal 架构，他很快就能说出系统由哪些主要部分组成、各在哪里、彼此怎样通信。

## 功能区一：架构与协议（`pattern: architecture`）

- **回答的问题**：Portal 由哪些部分组成，各自负责什么，模块之间靠什么协议协作，改动一处会影响哪里。
- **读者需要**：先看到整体，再按兴趣深入某个部分、某条协议、某个场景，最后才是 Design 正文和代码位置；任何模块、协议或 Design 都能被找到。
- **对象状态**：模块、协议、Design 为 `current`；挂在其上的 Plan 为 `proposed`，与现状区分。
- **动作**：在模块或协议上 `feedback`；`focus` 当前对象，其他功能区跟随。


### 逐层进入仍然是架构

进入模块以它为当前理解范围，主视图展示内部组成、组件之间的协作，以及必要的对外联系。连线解释谁与谁交互、交换什么、由谁拥有状态或承担决定；协议在发生交互的位置可被打开。继续进入一个内部组件，遵循同样的语义，不因进入第二层或更深层就退化成说明文字与子模块按钮。面包屑、返回和视野恢复维持方向感，不能代替内部架构内容。

图中的结构需要帮助读者理解一个具体过程怎样经过这些部分，或者一处规则变化会影响哪些契约。调用、事件、数据流、共享状态与部署关系各有含义，按真实机制区分，不能把参与者集合当作调用顺序，也不能把同属一个父模块画成彼此调用。复杂关系可以分层、分场景渐进展开，当前视图应保留足够的上下文，让读者知道未展开部分如何接入。

系统总览也遵循这一原则。概览中的模块关系可以从已研究的真实跨模块交互按组成层次汇总，但汇总必须保留实际端点、交互种类、协议与依据，展开时能回到这些原始关系。同一父模块内部的交互不成为该父模块的自调用；协议参与者集合不能直接推作彼此调用。没有关系不能用无连线的模块网格冒充完整架构。

总览以相近的职责粒度呈现主要模块。一个对外能力由多个独立进程或服务共同实现时，可以把它们收拢为可进入的能力视图；例如模型执行在总览中作为一个 ExecutionService 能力模块，进入后再呈现请求协调服务、Worker 与 Provider 运行时的实际协作。能力视图使用明确的视图身份并保留真实成员身份、职责和部署边界，不修改事实模型的 parent/child，也不把不同进程伪装成同一服务进程的内部对象。聚合节点的说明和反馈上下文指出其成员范围；选择具体成员后仍回到原对象。跨聚合边界的关系按实际方向和协议汇总，保留原始端点、关系身份和依据；内部关系只在进入后显示，不能变成总览自环。返回总览时恢复聚合状态与阅读位置。此取舍用于降低理解整体架构时的细节负担，不改变软件实现或部署事实。

默认总览解释整个系统的主要组成及其协作。请求与执行路径、资源访问、持久化、通知等实际存在的重要关系，都应在默认视图中有可理解的位置；不能因选择一条主路径，把其余关键模块画成孤立入口。主题选择可加强相关关系的视觉重点，更多细节可通过选择和深入显现，但这些交互不能成为看懂基本架构的前提。关系缺失时应继续研究实际实现，不凭模块名称或协议参与集合补造调用。

布局由职责、依赖方向、协作密度和边界决定。作者灵活安排从上到下的层次、横向协作者、分组、节点尺寸、连线路径和留白，让读者看出主次及模块间的关系；不把各级架构套进相同尺寸的卡片矩阵或固定蛇形流程。进入不同模块后保持相同的探索语义，其内部图的构图则适合该模块的真实结构。协议标签清楚归属于对应的线，必要的汇总可以展开为原始关系；减少遮挡和交叉不以隐藏关键协作为代价。

### 协议各有自己的机制界面

双击协议或使用等价的键盘、触屏入口，进入该协议的完整解释与体验。协议作者研究其实现、参与者、契约、状态与典型使用，再选择最能帮助理解的可视化和操作。协议工作台保留原协议身份和来路，可返回原架构位置；字段、源码和Design是继续追查的入口，不承担默认解释的全部工作。

例如，HATG Instruction协议可以按真实指令类别组织浏览和搜索，进入一条指令后解释它要解决什么问题、目标与参数的含义、负责服务、返回结果和适用失败情境，并通过合适的本地演示观察这些关系。它的分类目录不应成为所有协议的模板。租约协作可能需要可调时间与竞争者，原子写入可能需要观察临时内容、替换和读者所见，消息协议可能需要观察信封、路由和响应。这里的例子说明表达由内容决定，不规定每类协议必须使用某个固定组件。

共享画布、文本、播放控制、来源解析和无障碍基础设施可以复用；各协议的状态、规则和解释属于其机制，不通过替换标题或字段把同一个展示套在所有协议上。演示中的操作默认只影响本地情境，真实指令的执行仍按投影协议走正式权限与确认流程；本地演示不伪装成真实执行结果。

**架构说明面向当前工作区，不绑定 Git 提交。** 研究内容、模块关系、指令目录和教学示例可能落后于实现，这不影响它们作为说明的可读性。本区域只显示当前架构与协议，不提供历史架构查看、提交选择或提交对比。生产与存储侧只保留当前架构文档和必要来源证据，不枚举 Git 提交、不保存历史架构或历史提交快照。当前文件的摘要仅用于交付定位，不作为显示说明或打开指令教学的准入条件，也不通过兼容清单证明说明与当前代码一致。内容更新由作者负责；页面只检查能否读取和渲染所需的文档结构。

架构入口定位模型文档；指令目录可以通过单独的附件入口定位目录与教学内容。默认显示不读取历史验证报告，不要求入口与镜像、目录与模型、教学与目录的提交或字节摘要相等。入口用 `currentSource` 定位唯一的当前地图文件、文件索引和协议文本；`current_commit` 只标识当前来源，不是历史选择键。探索模型与指令目录的当前正文继续可用；来源按需读取当前文件与 Design。生产器覆盖固定位置的当前产物，并在确认当前依赖完整后清理旧快照和仅被历史引用的对象，原 Workspace 与运行副本执行同一规则。不得通过旧 `base_manifest`、兼容清单或审计目录把历史闭包重新带入。阶段进展报告、Git 提交历史和 Resident 普通历史分别由其原有领域维护，不属于这项清理。目录中的参数拥有服务、互斥参数组及嵌套参数仍按文档表达，不把这些字段推导成真实调用结果。

源码在读者打开时读取当前工作区的文件，Design 读取当前正文。来源链接是继续理解实现的入口，不是整页内容的担保。单条来源失效只影响该来源，附加教学材料不可读只影响相应补充说明；总览、导航和其余内容继续可读。实际请求仍使用当前调用者的正式资源入口，是否允许访问由服务端本站权限设置决定，前端不另建权限判定。文件缺失、格式错误、服务错误与服务端明确的权限拒绝分别表达，不能从“不可读”推断为 permission_denied。

教学示例明确标为本地模拟，可独立于源码版本继续帮助理解。真实指令执行仍走正式入口；内容更新、演示状态及业务执行分别拥有自己的职责，不以自动校验把过时说明变成整个功能不可用。

### 叶模块继续进入实现机制

没有下一级模块不意味着探索结束。再次进入叶模块，应看到它如何完成职责：可按实际内容呈现算法、状态转换、资源分配、数据变换、缓存失效、生命周期或其他有解释力的机制。读者可以用适合该机制的输入、选择和观察理解结果，以及该模块为什么需要独立存在。简单机制可以采用简洁的交互，不为统一外观虚构复杂度；模块介绍、文件列表和源码全文是辅助材料，不代替机制表达。

### 内容研究与事实更新

模块和协议的作者必须深入研究相关源码、当前Design、正式接口目录及实际实现行为，形成清楚的职责、关系和机制理解之后再设计呈现。事实产物服务于这些理解任务，发现现有地图只记录目录、某个关键机制没有身份或缺少内部关系时，应补齐权威事实与消费合同，而不是让旧数据形状限制产品表达。不同视图仍引用同一事实，不能在前端另造业务真值。

无法证实的关系不得编造，权限或历史资料不足要如实表达。当前产品要求研究和展示的内容尚未补齐时，它仍属于待完成工作；缺失提示只是对当前状态的诚实说明，不是该理解任务完成的替代物。一个代表性演示通过不代表其余模块和协议已经覆盖，正式交付中的可进入对象都应有经过内容研究的表达。

实现机制、教学情境与运行观察分别表达。源码研究和 Design 说明系统如何工作；教学情境用明确标识的输入解释规则与结果；真实运行观察说明特定账号、请求或时刻实际发生了什么。工程研究的完成以职责、内部关系、协议、状态归属及实现分支是否得到解释为准。实时账号目录或运行样本不可读时，保留这一观察缺口，只限制依赖该观察的运行结论；已有充分依据的实现机制仍继续研究、展示和验收。教学输入不冒充账号能力、线上授权或实际执行结果。

界面应呈现观察的含义，而非逐字段翻译默认值。某条情境没有执行设置校验、能力查询、内容写入或终态观察时，应显示相应阶段未发生或结果未观察，不能把初始 false、空值或零显示成已拒绝、不存在、未写入或已停止。演示中可选择的输入与可见结果应让读者理解具体对象之间的因果，不能用通用状态表替代该机制本身。

## 功能区二：阶段进展（`pattern: progress`）

- **回答的问题**：这一阶段 Portal 做成了什么，带来了什么效果。
- **立场**：像一位能干的员工向负责人汇报阶段工作。篇幅几乎全部用在做了什么、做到了什么效果，最重要的成果最先被看到，读者能直接去体验。
- **避开的倾向**：把汇报变成自我辩护，例如罗列待回应事项、未解决问题、风险、证据缺口、验证状态和证据链。团队能解决的问题由团队解决，真正需要用户决定的事由门面在对话中提出。
- **动作**：打开 Dev 体验；对成果 `feedback`；调整优先级的意见交给门面，页面不直接改 Plan。
- **日期筛选**：按成果所属日期选择起止范围，边界包含所选当天；可以清除范围查看全部成果。标题、日期筛选与查找组成紧凑的同一工具栏，窄屏有序换行，内容获得主要空间。
- **阅读状态**：成果不区分已读、未读，不提供阅读记录、水位或标记已读操作。日期范围、搜索和当前视图可以作为本地界面偏好保存，不写成果阅读状态。

## 功能区三：未来演化（`pattern: evolution`）

- **回答的问题**：Portal 将来可以变成什么样，还能拓展出哪些新的可能。
- **内容**：演化成员自己构想的、有想象力有主见的产品与思想方向：Portal 未来可以拓展出什么新的能力和体验，让人看到之后想去实现它。方向来自对 Portal 理念和现有能力的理解，不来自当前工程问题清单。已有 Plan 可以作为通往某个方向的具体步骤挂在下面。
- **避开的倾向**：让系统更保守、记录更多信息的方向，例如权限、约束、可解释、审阅、可追溯、审计、稳健性。这类方向让系统积累越来越多无效信息、越来越拘谨；工程上的具体问题由团队在日常开发中直接解决，不作为演化方向。
- **动作**：认可、否决或补充方向，要求把方向展开为 Plan，均以 `feedback` 交给门面。正式写入 Plan 和 `IMPROVE.md` 遵守知识库规则。

## 功能区联动与对话区

三个功能区共用一个情境通道 `focus`，都可以发布和订阅。在架构区选中一个模块，进展区筛出该模块的变化，演化区高亮影响它的 Plan。对话区连接开发团队的 Family 门面（清单中的 `facade` 角色），门面同时收到当前情境，用户说“这里”时，门面知道指的是哪个对象。

用户在对话区或通过 `feedback` 提出的任何需求，包括 Portal 功能开发、缺陷修复、设计调整以及这个工作台自身的改进，都由门面交给团队处理。

## 体验水准与交互设计

这个工作台是一个独立的软件，复杂度与 Portal 本身的图编辑、对话等界面相当，用投影应用包（decision_7a5ae487e2e9）实现，水准对标人们愿意天天使用的专业工具。

**设计、实现与自检由作者连续完成。** 每个功能区先研究内容和读者需要理解的问题，再形成设计与可运行原型，并以读者身份检查能否高效理解和继续探索。设计与体验成员提供可直接使用的成果，作者不等待同伴评审或批准才开始实现；明确安排的独立体验验收继续按职责执行（decision_78134209e5c9）。

**屏幕留给内容。** 读者打开页面看到的应当主要是内容本身，控制和说明退到需要时才出现，不让标题、横幅、按钮占据读者的注意力。

**先让当前内容可用。** 首屏只读取入口和可渲染的架构说明，让读者看到主要关系并开始探索。来源全文、指令详情和其他尚未进入的内容在需要时读取，不检查说明是否与某个源码提交同步。内容可能过时，单个附加来源失效不阻断已展示内容。加载体验按真实入口到可理解、可操作内容的时间判断，并观察深入和返回是否顺畅，不能以请求最终停止或占位框出现代替。

**按读者体验验收。** 作者以读者身份在真实页面上走完要回答的问题，并由体验验收成员和 TAU 从真实入口复核。“能显示、能点击”不算完成；作者自己不愿意拿给别人看的，也不算完成。

架构探索的验收要走过整体、内部组成、下一层组件、叶机制与协议，并检查读者是否能够解释各部分怎样协作、某个输入为什么产生这个结果、协议各方分别保证什么。导航、布局和来源打开的技术正确性需要验证，但不能代替这些理解结果。每处内容的表现是否适合其机制，由实际阅读和操作判断；不能用统一版式、控件齐全或少数样例的通过替代整体效果。

## 团队维护的产物

### 模块地图 `architecture/modules.yaml`（Portal 仓库）

按“模块与协议的含义”记录模块的层级、职责、代码路径、负责的指令 `owner` 和挂在其下的 Design；协议单独列出：名称、参与模块、要点、相关 Design、一个具体交互例子。架构成员需要的其他信息（例如布局提示）可以自行增加。模块地图随代码一起版本化，投影通过 `repo_5d287fed9c7e/file/architecture/modules.yaml` 读取。

模块地图由架构成员按自己对 Portal 架构的理解设计，像架构师画架构图一样决定层次和取舍，不从 Design 列表或目录结构机械生成。

当前地图写出 `tfi.portal-architecture.v1`，数组与 ID 地址结构保持不变，以 `model_version: 2` 标记运行单元模型。读取器只接受该精确格式，不接受其他格式名或版本，当前地图覆盖更新，不另建历史地图副本或提交索引。`system` 与 `external_actors` 说明系统边界；`modules` 用 `level` 区分运行单元、组件和外部系统，`parent` 表达真实的组成归属，可以继续指向内部组件，`layer` 提供布局提示。共享库可用 `deployed_in` 说明实际嵌入哪些进程，不把共享库假设为独立服务。部署位置不能穷尽职责分解，跨运行单元的能力视图通过明确关联组织现有对象，不改变真实归属。模块关系、协议和机制事实由同一架构权威维护，视图选择不建立另一套事实。流程放在 `scenarios`，必须区分规范演示与实际执行记录。

每份 Design 的主归属写在唯一一个模块、协议或 `system` 节点的 `designs` 中；`system` 只用于描述整体运行边界的总览 Design。协议的 `related_designs` 只声明交互依据，不增加主归属；参与者数组不表示调用先后。核对脚本收到未标记 `model_version` 的输入时，按该输入格式判断模块拥有 Design、协议的 `designs` 只是引用；这种输入格式兼容不生成历史架构视图或历史快照。

记录演化方向及挂在方向下的 Plan，内容组织由演化成员决定。Plan 本身的格式不变。

### 自动核对

每次发布后由 Lineage Effect 运行确定性脚本（RunScript）核对，不使用模型：

- `SPEC.md` 中的每份 Design 挂在唯一一个模块、协议或系统总览节点下。
- Design 的 `links.source` 按引用类型分别核对：
  - **Portal 仓库内的实现文件**按归属核对：落在所属模块代码路径内的文件符合预期；落在其他模块的实现文件说明该 Design 涉及跨模块协作，模块地图中应有连接这两个模块、并列出该 Design 的协议边，没有对应的边才算偏离；不属于任何模块的仓库内实现文件报为“未映射实现”。测试文件不参与归属核对。 Design 由协议拥有时，参与模块及其组件的代码路径构成该协议的实现范围；范围外的实现仍需有列出该 Design 的协议边连接相关模块。父级协议端点覆盖后代组件，组件端点不覆盖兄弟组件。文件存在性独立检查，未映射的失效路径不能因缺少归属而漏报。
  - **组成关系的范围**：模块拥有的 Design，其实现范围是该模块及其全部后代组件的代码路径，与协议端点的后代覆盖一致。此外还包括祖先模块**自身**的代码路径（不含祖先的其他后代），因为父模块的组装与门面文件是子组件的组成方式，例如子组件 Design 引用父聚合的装配文件。兄弟组件、祖先的其他后代、其他运行单元的文件不在范围内，仍需要列出该 Design 的协议边。系统节点不作为祖先参与这条放宽。 在运行单元模型中，一个文件同时命中祖先的目录或通配符和已登记的后代组件时，以后代组件判定该文件的归属，不能借祖先的宽路径把兄弟组件当作祖先自身代码；未被后代组件认领的组装文件仍属于祖先。
  - **层级深度**：`parent` 链按真实层级逐级解析，核对器不限制层数。`parent` 指向不存在的模块或形成环时报为地图偏离。
  - **系统级 Design**：描述 Portal 整体运行边界的总览 Design 可以把主归属写在 `system` 节点下。它的仓库内来源只核对存在且能映射到某个模块，不要求协议边；这类 Design 在报告中单列，便于看到哪些 Design 挂在系统级。只描述某个模块或协议的 Design 不能挂在系统节点下来回避协议核对。
  - **仓库外路径**（如 `${share_root}/Skills`、`${share_root}/Agents` 下的规则、文档与脚本）、**URL** 和 **资源地址**（`resident_*`、`decision_*` 等 Resource ID 及其嵌套地址）不参与模块归属与协议边核对，只核对引用是否存在、可读；路径不存在、URL 格式无效或地址无法解析时报为“失效引用”。这些引用在报告中单列为外部引用清单，便于看到 Design 依赖了哪些仓库外的规则和资源。
- 每个 HATG 指令 `owner` 对应到一个模块。
- 模块地图登记的代码路径存在。
- 演化图引用的 Plan 存在且仍在 `IMPROVE.md` 中。

核对结果写成偏离报告；有偏离时由事件交给架构成员判断应修改地图、代码还是 Design。偏离如实列出，不通过扩大模块代码路径来消除。

### 架构检查的本站开关与发行映射

Portal 管理中的架构检查开关控制本站配置的 RunScript Effect。配置位于 `deployment.development_projection.lineage_id` 与 `architecture_audit_effect_id`；稳定语义标识为 `architecture_audit`。它与 Pulse 共用 `portal_feature_switches` 的组件映射合同，但只接受一个实际 Effect。

发行时，`installation_mapping` 以显式站点配置、所选普通 Lineage ID 和实际定义行核对目标。缺配置、未选择的 Lineage 或缺组件返回 `needs_configuration`；重复组件、错误归属或类型返回 `conflict`。仅带出架构代码不证明检查流程已安装或默认关闭。返回 `ready` 只证明唯一映射，启用默认值、代码选择与 manifest 由发行模块统一维护（decision_15aab18c0ab3）。

管理端使用 `component_runtime.views/set_paused` 读取和修改 Effect 的 `paused`。真值属于 `operator_work.checkpoint_json`，既有 Effect 准入和恢复逻辑在执行及指令间检查它；暂停保留原激活和恢复记录，不建立另一套工作状态。目标安装器在目标定义就绪后使用同一原生状态语义初始化，升级保留本站映射与当前暂停值。开关映射接口提供合同与诊断，不直接连接目标库、执行安装或启动流程。

### 发布完成事件 `portal.release_published`

“每次发布后”由 Portal 的原生事实事件表达。Lineage 事件源可以选择事件类型 `portal.release_published`，用于发布后核对、发布后补一轮进展摘要等任何需要跟随 Release 变化的流程。

- **事实先持久化，事件从事实产生。** 发布器在新提交已激活、健康检查通过、Release 当前提交等于本次提交之后，写入一条发布事实：发布 ID、提交、上一个 Release 提交、发布时间和发起来源。事实保存在 PostgreSQL 中；发布日志文件只用于排障，不作为事件来源。
- **事件源用稳定游标读取事实。** 每个事件源记住已处理到的发布事实位置，只为之后的新事实产生 Event；Event 的 payload 携带发布 ID、提交和上一个提交。SocietyService 暂停或重启期间产生的发布事实，在恢复后按游标补发，不会遗漏或重复。多次发布积压时按事件源的 misfire 策略处理，核对类流程通常只需针对最新一次。
- **新事件源从当前水位开始。** 事件源首次建立游标时不补发此前的历史发布；同一提交再次发布是一条新的事实，会再次产生事件。
- **只有成功的发布产生事实。** 发布失败、健康检查失败或提交未激活时不写成功事实，也不产生这个事件；发布失败由发布流程自己报告。代码已激活但发布事实写入失败时，发布结果如实标明事件未记录，不回滚代码。
- **事件消费者的失败不影响发布。** 核对失败、核对脚本出错或下游 Resident 处理失败，只产生偏离报告或运行失败记录，不回滚、不阻止已经完成的发布。
- **手动触发不能伪造这个事件。** `TriggerEvent` 只触发 `manual.triggered`；需要人工补跑时，使用单独的手动事件源连到同一流程。

## 开发团队

开发团队是一个独立的普通 Lineage，整体组成 Family，对外由门面接待。团队既维护投影产物，也承担 Portal 开发，包括这个工作台的界面实现与维护。总 Family 下按工作领域嵌套三个局部 Family，每个局部 Family 有自己的门面、Router 和 steward；领域内的事件源、Effect 和连线也属于这个局部 Family，折叠后整体收在一起。

| 组成 | 成员与稳定职责 |
| --- | --- |
| 总门面 | 接收对话和反馈，按 Family 路由规则交给各局部 Family 或直属成员；steward 在职责缺口出现时新增成员 |
| 汇报成员（直属） | 按时整理阶段汇报 |
| 开发团队（局部 Family） | 架构成员：设计和维护模块地图，处理核对偏离，向用户讲解架构与协议；演化成员：提出和维护演化方向；Portal 开发成员：承接 Portal 功能开发与缺陷修复。模块地图、演化图的起草事件与架构核对流程在这个 Family 内 |
| 测试团队（局部 Family） | 测试成员：测试目录、选测、发布门禁、失败分类，统一调度回归和 TAU；回归执行成员：执行回归基线、复现失败、维护测试基础设施；TAU 模块执行成员：每个功能模块一名，按 TAU 协议从真实入口完成本模块用户任务（decision_c953eab654cd）。回归基线流程和各 TAU 模块验收流程在这个 Family 内 |
| 投影前端团队（局部 Family） | 负责人、交互设计、宿主与 SDK 平台（含投影应用包）、各功能区可视化工程和体验验收；负责投影协议宿主能力和本工作台三个功能区的设计、实现与维护 |

团队的角色、成员自足（`resident.md` 与具名工作项）、并行派生、标准事件和创建原则遵循通用模板 decision_78134209e5c9。

定时与自动触发：汇报成员由时间事件源定时触发，发布后再由 `portal.release_published` 事件补一轮；自动核对由同一事件触发 RunScript。成员的开发工作遵守 Portal 的发布、测试和 `SPEC.md` 维护规则。 这些事件更新进展产物和核对结果，不自动触发成员进度通知；实际交付与用户明确要求的通知按 decision_78134209e5c9 执行。
