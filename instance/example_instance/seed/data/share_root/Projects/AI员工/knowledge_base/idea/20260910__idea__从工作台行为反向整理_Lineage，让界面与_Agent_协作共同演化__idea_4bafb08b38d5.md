# 从工作台行为反向整理 Lineage，让界面与 Agent 协作共同演化

## 想法

用户先拥有一个 Lineage，再投影出适合自己的工作台。工作台经过真实使用，常常会增加、合并或调整操作流程，这些变化可以成为重新整理背后 Agent 职责和协作结构的依据。

让投影从一次性“生成页面”变成双向演化：Lineage 提供能力，页面组织使用方式；页面的真实工作流程反过来帮助识别哪些能力应成为共享职责、哪些步骤应连接成可直接操作的 HATG 流程。

## 反投影整理什么

- 找到页面操作与现有成员、Event、Effect、对话目标、业务服务和正式产物的对应关系。
- 将稳定的 AI 职责与一次请求分开，让固定提示词归明确操作、本次输入归 invocation。
- 将持续聊天直接连接到同一 Resident；把首次创建初始化与日常对话分开。
- 将多阶段 AI 工作整理为有因果身份、结果协议和失败边界的协作流程。
- 保留筛选、布局、草稿及确定性业务的原有 owner，不把每个界面控件或回调变成 Agent 节点。
- 让任何获授权入口产生的正式产物都能被工作台发现，而不是只有点击页面按钮才“看起来完成”。

## 可能的使用循环

```text
已有 Lineage → 工作台投影 → 实际使用与界面改进
      ↑                         ↓
  验证后的团队整理 ← 审查差异方案 ← 反向分析操作与职责
```

反向分析使用页面源码、调用关系、业务规范、已有图和授权运行证据，不仅依据截图或按钮名称。结果是可审查的对应清单与修改方案，不是立即执行的命令。

## 边界

“反投影”不是严格可逆变换：页面只展示团队的一部分能力，不同页面可以映射同一团队，同一个操作也可能隐藏多个业务阶段。缺失的职责与权限信息必须向 owner 确认，不能让模型猜测后自动修改团队。

保留已有 Resident、会话、消息、产物和历史身份；默认复用，而不是根据新页面重新创建整套团队。整理方案应区分页面修改、领域合同修改与 HATG 修改，并考虑其他页面和在途任务。

分析与应用分开。删除成员、改变归属或权限、启动业务工作及发布页面，均需明确授权。部分失败保留各服务实际接受的回执，不以恢复前端版本冒充撤销任务。

## 值得验证的问题

1. 从哪些页面调用和业务事实能可靠识别稳定职责，哪些必须依赖用户解释？
2. 不同页面表达同一能力时，如何帮助用户发现重复实现而不误合并不同职责？
3. 怎样展示“保留在前端、复用现有对象、需要新增或调整”的差异，让 owner 能理解和确认？
4. 整理后能否让同一功能既从页面使用，也从 Lineage 使用，并产生同样可发现的正式产物？
5. 面对再次修改的界面，是否能复用原身份，稳定地收敛到无额外图变更的状态？

## 最小探索

选择一个用户自建的普通 Lineage，先实现其工作台，再调整一条真实工作流程。让工坊给出操作分类、已有能力映射和整理差异；owner 确认后只应用有关变化。验证两种入口、已有会话、跨入口产物与错误恢复，并观察纯样式修改是否保持图不变。
