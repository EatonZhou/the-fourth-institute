# 计划（`plan`）条目归档规则

## 语义与收录门槛

一份 Plan 文件叙述一个值得独立审查的显著改进。它让读者理解具体场景、为什么值得改变、准备形成什么体验或机制，以及如何检验结果。新能力、已有功能重构和演化方向都可以成为 Plan，前提是有清楚的核心变化与实际价值。

优先保留能明显改善完整使用过程、消除反复发生的重大成本、解决关键障碍或形成新能力的方案。改动代码多、名词新、覆盖领域多均不能单独证明价值。零散微调、常规修复、孤立字段变动和可有可无的润色通常留在任务或主方案细节中；缺少独立价值的片段直接舍弃，不为填满索引归档。

## 条目边界

- 一个 Plan 对应一个核心变化和一个完整审查单位，正文可有多个章节、场景、步骤和技术细节；这些内容都应服务同一改进。
- 多项变化必须一起成立才能形成价值时，放在同一 Plan 解释其关系。能够分别判断取舍、独立交付且各有显著价值时，才拆成不同 Plan。
- 多份 Design 可以共同支撑一个 Plan；一份 Design 可以没有 Plan，也可以关联多个独立高价值 Plan。引用真实来源，不要求唯一 `derived_from`，不设每领域数量配额。
- Design 解释稳定的系统设计，可包含多个设计点；Plan 解释一个拟议变化。粗略设想归入 `idea`，推理权衡归入 `thinking`，执行清单或普通修复进入任务记录。

## 写作

让读者沿着“场景背景—显著价值—完整方案与交互—边界及成功检验”理解同一个变化。按内容自然组织段落和小节，不要求固定栏目、改进点列表、条数、篇幅或模板填空。

- 先说明谁在什么情况下遇到什么困难，以及当前如何工作。区分实际观察、静态分析、待验证判断和未来设想；证据不足时明确未知点，不虚构复现、收益或工期。
- 解释为什么值得占用一次独立审查，哪项可感知的结果会改变。只有标题或一句“优化体验”不能承担完整方案。
- 面向用户的方案解释入口、动作、反馈和完整过程；内部改造解释责任归属、状态或信息如何流转、共享机制如何减少重复。术语在首次使用时解释。
- 说明本次范围、必要依赖、主要代价和可观察的成功结果。探索方向保留关键待验证问题，不把尚未确定的实现写成现状。
- 细节用于支撑主改进，保留必要证据、图示和约束，不把内部步骤拆成独立改进卡，不增加没有实际内容的流程与表格。

## 登记与维护

1. 确认项目，读取相关 Design、实际实现和相邻 Plan，核实来源并查重。
2. 按核心变化筛选与组织内容；现有条目仍承载同一核心改进时保留 ID，独立新主题通过受认证资源入口登记，不手造 ID。
3. 按 `./knowledge-base-rules.md` 提交 title、body 和支持的可选字段，由服务生成 YAML 与版本审计。`importance` 表达重要度；可选 `metaness` 依据正文抽象层级评分，与重要度及未来时间性独立。
4. 正文使用一级标题；省略时服务按 title 补齐，自带时须一致。不要套旧的加粗冒号标题抽取流程。
5. 存在改进索引的项目，将 Plan 的稳定 ID 和标题登记到索引；完成或失效后移出待推进索引，保留真实来源和可追溯关系。已成立的设计写回 Design。

服务生成的文件名遵循 `YYYYMMDD__plan__<Title>__<kb_id>.md`，身份为 `plan_*`。Portal 工程按当前 SPEC/IMPROVE 索引中的规范维护计划，不依赖源站固定 Design ID；不把实施日志当作当前 Design。实施结果在 Plan 正文说明，通过正式更新维护版本，不发明未支持的 Plan 状态字段。
