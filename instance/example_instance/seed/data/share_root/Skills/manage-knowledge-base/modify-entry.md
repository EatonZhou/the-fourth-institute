# 修改已有条目

## 准备

1. 完整读取目标条目。
2. 按 `./search.md` 查找相关概念、当前 Design、实现说明、替代条目和相邻术语。
3. 确认修改目标、事实来源和会受影响的其他条目。
4. 只读、审校或预览请求先输出建议；用户明确要求修改后再写回。

## 修改

- 先改核心定义或事实来源，再改引用它的说明。
- 保留已有定义中的核心关系、作用边界和确定程度，不临时发明近义口径。
- 引入外部框架概念时，先写该概念的基本定义，再写项目如何扩展或使用。
- 使用明确主语和具体动作；每句话承载一个主要判断。
- 比较、优势和风险应给出指标、场景、机制或证据。证据不足时明确写为待验证。
- 机制说明按真实链路组织：谁写入什么状态，什么规则产生事件，谁消费事件，最终改变什么输出。
- 不用抽象名词、术语列表或模板章节填充信息不足。
- 不把不确定设计包装成完整字段表或确定结论。
- 保留身份字段、创建日期、`version.created_at`、`version.created_by`、有效链接、附件关系和承担语义的 Markdown 结构；通过 `UpdateResource` 携带读取到的版本提交，修改审计由服务维护，回读验证。

## 复查

1. 搜索旧术语和旧口径，确认没有留下会造成冲突的当前表述。
2. 对照相关条目，确认定义、路径、状态、版本和责任边界一致。
3. 查看差异，确认没有无关改写、信息丢失或 YAML 头部变化。
4. 运行目标项目已有的结构检查或构建；没有检查工具时，至少重新读取修改后的文件。
