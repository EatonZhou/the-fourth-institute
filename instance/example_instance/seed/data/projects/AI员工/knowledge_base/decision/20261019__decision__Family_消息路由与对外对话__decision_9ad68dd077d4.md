# Family 消息路由与对外对话

Family 通过门面接收请求，由一个实际成员承接，并把该成员的处理过程投影回原请求。门面不运行模型，也不复制成员回复。本文负责消息身份、路由、转交、改派、控制与对外联络；[Family 主文](/resource/knowledge?item=decision_44cf587c1721) 负责结构，[角色工作流](/resource/knowledge?item=decision_89b9df038a95) 负责具体 Event、Effect 和 prompt。

## 原请求与执行身份

门面保存外部原输入；family_relays 保存原输入到成员输入的转交关系，是回复与状态投影的依据。转交副本携带 business_ref，原发送者、内容、附件及引用保持不变。门面原消息在投递成功后结束自身排队；这表示已转交，不表示实际工作完成。

Router 选人输入另外保存 `family-route/<门面ID>/message/<原消息ID>`。其完成事件把 input_business_ref 交给转交 Effect，使输出绑定正确请求，不依赖 Router 复制 ID、当前上下文或完成顺序。

内部通知以门面署名，真实引起者记为 initiated_by；亲自向内部角色发消息仍保留本人身份。转交副本不把成员加入外部发送者的会话列表，未读落在门面；直接给成员发过消息才形成直接会话。

引用直交的自动调用由生成的本 Family `router` Effect 取得一次有限门面转交身份：运行时须核对 `resident.message_received` 的门面主体与原消息 ID、保存消息的真实作者、当前 Family 归属及保存引用算出的当前承接成员；只允许 `resident_id/message_id/member_id` 三个转交参数。跨 Project 回复也沿此路径逐层回到原写信成员，无需给外部发送者增加 Project contributor。普通 Effect、跨 Family/消息/目标替换以及改派、额度或职责复核参数均不取得此授权；直接 ISA 调用仍按声明权限检查。转交领域继续核验取消、接单、额度、媒体能力和原文附件来源授权。Effect 终态调用记录保留实际 caller；不把实际调用门面身份改写为原作者。

延续直交取得同一有限转交身份，核对方式相同：运行时按已存转交关系重新算出延续成员，与转交参数、到达事件的 `continued_member_id` 三者一致才放行，不只信任事件载荷。

无有效引用目标时，包括有延续直交目标的请求，同一生成的 `router` Effect 可用门面身份调用 `DispatchFamilyTask(trigger="route")`，但参数只含本门面与该到达事件对应的 `source_message_id`，原输入须仍 queued、真实作者须匹配。该授权只让本 Family Router 对已接收请求选人；不得附任意 facts、选择其他 trigger 或替换原消息。普通内部通信仍沿既有通路，不因这一限定阻止成员正常互发。

**原作者和对外署名不授予通用工具权限。** Router、Steward 与成员仍按实际执行主体核权。平台只对经过校验的门面原请求提供有限转交授权：校验转交者及 Family 目标，允许原样转交的附件和引用沿用来源授权；不能据此冒充发送者执行其他读写或继承其管理权限。具体权限规则见 [权限模型](/resource/knowledge?item=decision_b820faf42218)。

门面接收时检查附件与引用；原样转交只有 content_parts 与保存原文一致时沿用原来源的读取权限，改写后按转交者检查。成员 accepts_images/accepts_files 仍约束投递。跨 Family 的门面署名不改变实际发件成员拥有附件的事实。

## 选择承接者

### 对话、通知与自动路由的个人设置

三类设置分别回答“我现在和谁说话”“谁的结果需要提醒我”“自动分派可以选谁”，独立保存于「当前调用者 × 门面」。刷新与重开保留，不改变成员名册、接单状态、权限、在途工作或其他用户的偏好。

| 设置 | 作用 | 保持的行为 |
|---|---|---|
| **S / Solo：对话模式** | 门面暂时代表一个直属业务成员；普通新消息直接交该成员，跳过本层 Router 选人，只显示该成员关联的往来 | 可选被 Mute 或 Exclude 的成员；额度、媒体准入、故障恢复仍有效；子团队门面继续其内部路由 |
| **M / Mute：通知模式** | 不为该成员之后的结果、失败、取消及主动发件新增当前用户的 Mailbox 提醒 | 保留原消息、收件人、处理过程、问题卡片和回复；仍参与自动路由，不改变旧未读或标记已读 |
| **E / Exclude：路由模式** | 从当前用户后续普通请求的自动候选中排除该成员，也不自动延续到该成员 | 展示与通知不变；显式引用该成员的回复、Solo 与原问题回答仍可直达 |

Solo 一次一个；点另一成员的 S 切换，点亮着的 S 或头部“退出 Solo”退出。M/E 可分别选择多个，三者可以同时生效，任何一项不自动关闭或修改另外两项。所有普通输入在受理时冻结 Solo/Exclude 路由约束；后续切换不重分配已受理、排队或运行的工作。Mute 在新提醒事件写入时读取当前通知设置，解除后不补发静音期间的提醒。

问题卡片答案保持原问题组、原 Execution 与原承接者，即使偏好改变也不按 Solo 改交。普通引用在 Solo 时服从 Solo，未 Solo 时直接交合法引用的写信成员；Exclude 只限制自动选择。全部成员被 Exclude 时明确提示允许至少一位参与自动路由或进入 Solo，不暗中选回被排除的成员。Solo 成员离开或不能投递时保留真实目标与失败／等待状态，提供退出入口，不回退其他成员。

#### 门面的 Solo 代理界面

普通状态显示团队身份与团队往来。进入 Solo 后，头部以“团队 → 当前成员”明确显示代理关系，并持续提供“退出 Solo”按钮；输入目标同时标明当前成员。代理提示与退出入口位于对话头部，不能只靠回复底部的 S 颜色表达状态。退出后回到团队标题与完整团队往来，M/E 不变，原始对话与转交关系始终保留。目标离开时显示已失效目标及退出入口，不显示成正常团队模式。尚未确定承接者的输入与门面公共提示保留可见。

成员表、回复底部归属链接和成员自己的 Chat 头部使用同一套 M/E/S 偏好入口；嵌套回复按转交链取当前门面的直属业务成员，Router/Steward 不作为个人候选。每项有完整含义的提示、键盘焦点和按下状态；提交期间禁用重复操作，失败显示错误且允许重试。Mute/Exclude 不参与对话过滤，服务端翻页和浏览器增量展示仅按当前 Solo 过滤。

`GetFamilyChatPreferences(resident_id)` 返回 `muted_member_ids`、`excluded_member_ids`、`solo_member_id`；`UpdateFamilyChatPreferences(resident_id, member_id, control="mute"|"exclude"|"solo", enabled)` 只修改实际调用者，不接受代填用户身份。门面 @viewer 可管理自己的偏好；已离开的成员只能关闭其仍保存的设置。通知是否静音由通知写入 owner 在同一领域事务内判断：按当前门面的直属成员识别转交链或主动发件的真实发起者；未知或歧义归属保持提醒，不把静音扩大到其他成员或用户。

`family_chat_preferences` 保存三类个人偏好；`family_chat_inputs` 只保存按原输入 ID 冻结的 Exclude/Solo。结构为 LineageData v66。显式 v65→v66 迁移把旧 M 的路由排除迁入 Exclude，新的通知 Mute 默认关闭，取消旧 M 的隐藏视图；保留个人身份、Solo 和每个既有输入的原路由约束。迁移完整预演并回滚后才能协调代码与结构切换，业务请求不自动升级结构。

到达事件中的 `direct_member_id` 由平台根据持久原输入的偏好与合法问题回答归属计算。生成的 router Effect 仅在原消息作者、事件主体、目标与平台重算值一致时取得有限转交身份；不信任单独提供的目标字段。普通路由同时约束 Router 的候选 facts 与 `RelayFamilyMessage` 的最终成员检查，不能仅靠 prompt 绕过 Solo/Exclude。Conversation、翻页及浏览器增量显示均使用当前查看者偏好；原消息与权限本身不被删除或收紧。

| 条件 | 行动 |
| --- | --- |
| 无 Solo 时，引用门面中某个成员的回复或主动发件 | 直接交写信成员；该成员已离开、已删除或不能接收所带媒体时，回到普通路由 |
| 引用 Steward 经门面提出的问题 | 直接交本 Family Steward，不作业务成员额度复核；Steward 同时承接组织请求，但不加入业务名册 |
| 无 Solo 时，Family 以外的 Resident 发来不带引用的请求，它在本门面最近一条已转交的请求 4 小时内交给了未被 Exclude 的业务成员 | 延续直交：直接交该成员，不询问 Router。上一条交给 Steward、超过 4 小时、该成员已离开、已删除或不能接收所带媒体时，回到普通路由 |
| 无引用直交或延续直交目标，包括单成员或空业务名册 | DispatchFamilyTask 发给持续 Router，区分业务工作和本 Family Steward 的组织职责；有 Steward 时不因空名册阻止原事件 |
| 创建成员、调整分工等组织请求 | Router 选择本 Family Steward，scope=in；复用原输入，不把创建职责交给新建成员，也不扩大为撰写业务 |

嵌套转交时，内层会话若只有引用摘录，平台沿已接受输入的持久转交关系追溯外层原请求和外发记录，以记录中的实际写信者及当前名册确定本层目标；每层原作者与正文必须一致。不能从摘录、调用者提供的 business_ref 或失效名册推造归属，不复制外发消息或改写原引用。

嵌套转交的结构化问题回答继续保留原 `async_question_answer` 及问题来源 ID。接收端沿已接受、双向匹配的持久转交链找到实际发件门面的问题组，逐层核对回答身份、原作者和完整正文，并按当前层 Family 归属校验原写信者；只持有引用摘录不构成问题来源授权。原问题组的关闭、一次回答与全组校验不变，恢复复用原回答并跳过已成功投递的层。问题组与回答的权威契约见 `decision_1e2eb869bc10`。

延续直交只看发送者最近一条已转交的请求，并且只计这条请求到达之前完成的转交，因此请求等待期间结果不变；改派后按改派后的成员计。它只用于 Resident 发送者：一个 Resident 连续发给同一门面的工作，Router 几乎总是交回同一成员，而人常在同一门面换话题，按上一条交接会频繁交错，所以人发的请求仍由 Router 判断延续。引用会改变延续关系，带引用的请求按引用规则处理。

引用发送者以前的请求不强制交回上次承接者，避免把被质疑的错误路由再次固定。引用摘录随副本保留，原文不在成员会话中时仍可看到摘录。

路由任务只给当前目标、原消息与作者、必要标识及指南路径。成员职责、摘要、状态、历史和纠正记录由 Router 按需读取，平台不固定灌入“最近三轮”。Router 先判断是否延续先前讨论，再按明确职责选择；primary_ownership 表示直接负责，supporting_expertise 表示辅助经验。用户点名、要求换人或有效纠正优先；存在多个可能延续对象时结合时间和内容判断，没有固定会话绑定。

每条消息到达后即时触发路由，Lineage 对账作为漏送补偿，共用事件幂等键。route 和 relay 连线并行接收，Router Resident 自己按队列回答，不因另一条投递等待而丢弃后续请求。Router 模型与账号属于该 Resident 的运行设置；门面设置兼容接口读写 Router 的设置，脚本不自行调用模型。

## 转交、职责缺口与低置信度

一条请求交一个当前业务成员或本 Family Steward。Route Packet 的格式、解析、target/confidence/scope/gap 以及 Effect 分支见角色工作流。缺 target 或目标既不在名册也不是本 Family Steward 时保留原请求，派发诊断复核并以失败结束；不按固定候选兜底。

直达、引用直交、延续直交和模型选人都经过 RelayFamilyMessage，检查当前归属、来源授权、媒体能力、取消、接单和额度。成员关闭接单而阻塞由 Steward 恢复；业务额度复核见 [运行维护](/resource/knowledge?item=decision_a64b3ea2c3c5)。

scope=in 表示职责覆盖；寒暄或成员顺手可答的问题也属于 in。真正无职责覆盖才 scope=out，gap 写缺口、target 写最接近成员。忙碌或队列长不是职责缺口。scope=out 保留原输入，向 Steward 派发 recruit，由它招募、调整分工或交现有成员；安排后以 scope_reviewed=true 和理由继续同一请求，再经过额度检查。私人 Family 先遵守组织变更确认要求。

低置信度表示覆盖候选之间不确定。Effect 先尝试转交，再按 route_threshold 派发 route_review；已转交的任务不能因为复核通知再次派发。缺置信度按 0 处理。原请求已撤回则返回 withdrawn，不再转交或复核。

嵌套 Family 沿转交链查找实际承接者；Router 脚本在到达事件的 relay_depth >= 4 时明确失败，不再转交。各层门面的开始/完成事件带实际处理者，不另造独立业务任务。

## 改派与纠正

原发送者、有门面管理权限的主体和本 Family Steward 可以显式 reassign，指定新成员及理由。排队副本先撤回，原副本正在运行时拒绝改派，须先停止；改派不强行中断工作。新副本保留原文、原作者和请求身份，转交关系改指新成员，reassigned_from 保留沿革。

平台保存最近 20 条改派纠正至 family_corrections_<门面>，包含请求摘录、原成员、新成员、判断者及理由。Router 按需读取，Steward 可据此调整明确分工。归纳只覆盖该次纠正所说明的范围；只有被新纠正推翻或成员已离开的记录才清理，不把个案扩大为整类职责。

用户改派另以 info 告知 Steward；Steward 自己的操作无需自我通知。界面入口和确认由界面 Design 定义。

已在路由复核输入完成的组织成果，通过 `ResolveFamilyRequest` 归档到原失败请求。前提、授权、来源验证和失败沿革保留由 [原输入恢复](/resource/knowledge?item=decision_a64b3ea2c3c5) 定义；不重复执行业务。

## 状态、停止与撤回

GetInputState 沿 family_relays 读取实际成员状态，保留门面原输入 ID，返回真实最终回复、更新时间和失败原因。include_progress 使用成员队列及活动，尚未转交时显示路由进度；include_context 使用实际成员的上下文，门面本身没有 Provider 上下文。GetMessage 通过门面投影读取同一个回复身份。

| 控制 | 范围与结果 |
| --- | --- |
| 撤回尚未转交的请求 | 原输入取消，后来的 Router 结果或 Steward 放行得到 withdrawn |
| 撤回成员队列中的副本 | 取消这份转交，门面保留位置和撤回提示，隐藏正文、引用、附件 |
| 停止正在执行的请求 | 只停止该转交的成员工作，保留原文和已有输出，标记已撤销 |
| 门面全局停止 | 确认后停止所有正在处理的门面请求并撤回正在选择成员的请求；成员队列中的其他请求不受影响，可逐条撤回 |

取消提示由投影生成，不补发“取消回复”、不删除保存的原请求。是否已经执行取决于持久输入状态、轨迹和输出；清空成员上下文后也不能误判成未送达撤回。旧失败事件、迟到选择和重试必须再次检查当前终态。路由重试仍失败时明确显示失败，允许显式重试；不伪造已完成。

## 对话投影

门面展示外部原输入、该输入的处理过程及回复；内部路由、成员间往来、Steward 巡检留在内部。直接与成员对话不投影到门面，私人 Family 的迁移前历史有独立边界。

每条请求独立显示路由、转交、队列、活动、中间输出和最终回复，不用对话末尾一个状态代替多条并行任务。实际成员的事件沿链使门面刷新。读取以当前页的请求集合批量解析转交、状态和回复，同一成员数据复用；保持每轮自己的顺序、完成边界和回复上限。历史最终回复使用保留的轨迹身份读取，不因成员清空上下文而消失。

### 成员问题卡片及门面答复

门面原请求关联的成员输出中，结构化异步问题组与原生 `request_user_input`、`request_approval`、`mcp_elicitation` 卡片均随本轮投影。原生工具卡片不是最终回复，也不因此将工作标记完成；其他任意工具日志不扩大为对外对话。直接给成员的无关私聊仍不投影。

卡片保留原成员消息、问题组或工具调用 ID，关闭、已答复与过期状态读取原成员的权威记录。刷新、`GetMessage`、`GetResidentRequest` 与 `ListResidentRequests` 的门面视图均沿同一持久转交关系解析。

用户在门面提交原生卡片时，平台先检查门面管理权限，再核验此卡片确实属于门面原请求的转交轮次；沿原成员的 Execution、turn 与 request ID 提交答案。异步问题答案继续使用原问题组和既有引用直交路径。无需开放成员的全部会话权限，也不得仅凭用户提供的成员/消息 ID 读取或回答其他问题。取消检查读取真实成员输入的当前状态，已取消请求不能继续答复；门面投递回执的 completed 不代替该状态。

Family 的整体活动统计与单请求状态不同：其他成员继续工作可使整体显示运行中，但不能重新打开已完成请求或扩大“停止本轮”的范围。显示细节见界面专题。

## 对外联络与回复

成员和 Steward 继续使用 DeliverMessage。Family 内互发以本人署名；发往外部通常以包含发送者而不含收件方的最外层 Family 门面署名，真实成员记为 initiated_by。附件、引用按实际发件成员权限核对，门面署名不能借用别人的上传。

对方最近亲自写给该成员时，成员的主动发件回到直接会话；最近亲自写给内层门面时用该门面；写给最外层或从未直接写过时用最外层。门面转交的副本和 Fork 前复制的历史不算对方亲自写给新成员。

以门面发出的消息保存在门面对话，能读门面的人可见；只在实际收件人的 Mailbox 提示。给 Resident 发件时，对方得到消息、门面得到含收件人的发件记录，不把回复自动广播回发起者。

回复 Family 主动发件时，平台把回复关系换算成门面的发件记录，直接交原写信成员：

- 对方在处理该消息的当前轮次向原门面回信，可自动关联；同轮有多条来自该门面的输入时不猜。
- 后续轮次用 reply_to_message_id 指定收到的原消息；不是该门面发出的消息则拒绝错误关联。
- 经对方 Family 转交后，实际成员在同一轮回信也沿原业务关系关联。

需要人类决定的业务事项先追溯本次输入的真实人类发起人，没有则使用 human_familizer_id；两者皆无则保留待处理并说明缺失。不从最近会话、Resident 创建链、Project 管理员或权限持有人推测联系人。持续角色自身故障升级另按运行维护契约只找实际真人创建人。

## info 的去向

发给门面的 info 到达即由平台以门面署名转给 Steward，原作者记入来源说明，重复投递只转一次；不等待下一条业务请求来决定接收成员。Router 不处理 info。

Steward 只处理与分工、图维护、队列和恢复相关的变化，不承担广播或逐条回复。organization 的 info 路径额外携带 runtime_context，具体组成见角色工作流。门面对话先显示已交 Steward，下一条请求转交后按普通 info 规则折叠。
