# Telepus 微信提醒：把聊天室 @ 和待回答问题发到用户的微信

绑定了微信的 Portal 用户可以自己开启两类提醒：有人在聊天室 @ 了他，或者有 Agent 在等他回答问题。开启后，Telepus 在这些事情发生后几秒内给他的微信 ClawBot 发一条简短提醒，写清是谁、在哪、说了什么，不附链接。用户可以直接引用提醒来处理：引用 @ 提醒回复，文字发到聊天室；引用问题提醒回复，作为对这个问题的回答提交。提醒本身不替用户标记已读。

一般聊天消息、表情回应和其他 Mailbox 变化不发提醒。Telegram 渠道不在本文范围内，以后需要时按同样的结构接入适配层。

## 分工

一条提醒涉及三方，每件事只有一个负责方：

| 事项 | 负责方 | 说明 |
| --- | --- | --- |
| 谁被 @、是否未读、能否访问聊天室 | Chatroom 与 User Mailbox | Mailbox 条目的 `unread_mentions` 是唯一依据，Telepus 不解析消息正文判断 @ |
| 哪个问题在等哪位用户回答 | 提出问题的 Portal 模块，投影到 Mailbox | 规则见“待回答问题” |
| 是否提醒、发到哪、何时发、发过没有 | Telepus | 通知偏好、监听游标、去重记录、待发与重试，发送复用微信适配层的额度与待发队列 |

Telepus 不保存第二份消息、已读或问题状态。它只记录“这条提醒发过没有”。决定发送时，以发送那一刻向 Portal 读到的状态为准。

## 用户开启提醒

每位用户分别开关两类提醒，默认都关闭：

- **聊天室 @ 我**：别人在用户所在的聊天室 @ 了他。
- **待我回答**：有 Agent 的问题在等他回答。

开关有两个入口：

- 微信里的 `/notify` 命令：`/notify` 查看当前设置，`/notify mention on|off`、`/notify question on|off` 修改。
- Telepus Watchboard 中该用户微信绑定行上的两个开关。

两处改的是同一份设置。页面通过两项应用工具读写（不属于 ISA，注册与信封见 decision_ccbb1cac24aa）：`GetTelepusWeixinNotifications` 和 `UpdateTelepusWeixinNotifications`（参数 `mention`、`question` 为布尔值）。两项工具都接受可选的 `user_id`，权限规则与绑定指令相同：本人可以操作，操作他人须为 Portal 管理员。

开启时已经存在的 @ 和问题不发提醒（见“读取的字段”中“开启之前的旧事”），用户打开开关时不会一下收到一批旧提醒。解除微信绑定时，提醒设置与绑定一起删除；重新绑定后需要重新开启。

## 来源

### 聊天室 @

Chatroom 发消息时把收件用户写入该用户的 `user_mentions`：精确 @ 用户名、正式的 @全员（展开为除发送者外的全部成员），以及引用某人消息时的自动 @。用户读到该位置时清除，消息被编辑掉 @ 或撤回时移除。Mailbox 的聊天室条目以 `unread_mentions[{message_id, ordinal}]` 给出这位用户尚未读的 @。

Telepus 沿用这一收件语义，@全员 与精确 @ 同样提醒。Chatroom 目前没有给出 @ 的类别，所以 Telepus 不单独区分 @全员。如果以后要给 @全员 单独设开关，由 Chatroom 在 `unread_mentions` 里给出类别，Telepus 再加一个开关。

### 待回答问题

只有明确属于这位用户的问题才提醒：

- 问题写明了收件 User；或者
- 问题出现在由这位 User 发起的工作中，并且仍在等待回答。Family 转交的工作沿原请求追溯到可信的原始用户输入，以它的发起 User 为准。转交消息表层的 `origin` 不能作为依据。

能管理某个 Resident 的人并不都是它问题的收件人。没有明确 User 来源的问题（Resident 发起、定时触发）不提醒，也不根据 owner 推断收件人。只有原生提问和消息中的问题组算问题，普通回复里的问号不算。

判定由提出问题的模块完成，投影到 Mailbox 条目上，Telepus 只读取结果，不自行推断收件人，Mailbox 也不另建一份问题状态。投影的服务批量方法由 Chatroom 与会话的维护者实现，Web 集成由 User Mailbox 一方完成。投影与本设计一起实现，Telepus 读取的字段见下一节。

### 读取的字段

Telepus 只依赖 `GetMailbox(user_id)` 结果中的下列字段。`GetMailbox` 由服务端读完全部分页，`items` 和 `pending_requests` 都是完整列表，没有分页参数。

`WatchMailbox(user_id, after_cursor?, timeout_seconds?)` 每批返回 `keys`、`cursor` 和 `snapshot_required`。其中 `keys` 只提示哪些对话或聊天室有变化，不是提醒键，也不是待回答项的键。所以 Telepus 不按 `keys` 逐项处理：只要收到变化（包括首次和重连时的 `snapshot_required`），就完整重读一次 `GetMailbox`，再和发送记录比较。

**聊天室 @**（`items[]` 中 `kind == "chatroom"` 的条目）：

| 字段 | 用途 |
| --- | --- |
| `key`、`chatroom_id`、`title` | 来源与聊天室名称 |
| `unread_mentions[].message_id` | 提醒键 `<用户>:mention:<chatroom_id>:<message_id>` |

`unread_mentions` 每项提供 `message_id`、`ordinal`。提醒要写出谁 @ 了你、说了什么，所以发送前 Telepus 以用户本人身份调用 `ListChatroomMessages(chatroom_id, cursor=str(ordinal+1), limit=1)`，只取这一位置的一条消息，核对 `message_id` 后取作者和正文。位置缺失或不匹配时不扫描整个聊天室，按读取失败重试。读取用的是用户自己对这个聊天室的读权限，读不到时这条提醒按“读取失败”处理，不发、不作废。

**待回答问题**（顶层 `pending_requests[]`，与 `items` 分开，返回完整列表）：

| 字段 | 用途 |
| --- | --- |
| `key` | Mailbox 中这一项的不透明键，不解析其格式，也不用于跨投影去重 |
| `source_resident_id`、`source_message_id` | 稳定来源，提醒键为 `<用户>:question:<source_resident_id>:<source_message_id>`，与问答卡片共用去重 |
| `resident_id`、`message_id` | 打开这个问题的对话与消息，用于 `/route` 提示；提醒中的名称用该 Resident 的标题 |
| `kind` | `question`、`approval` 或 `question_set` |
| `created_at` | 发现时间 |

`pending_requests` 不含问题正文。提醒要说清问的是什么，所以发送前 Telepus 以用户本人身份读取问题：`kind` 为 `question` 或 `approval` 时调用 `GetResidentRequest(resident_id, message_id)`，取 `questions`；原生批准请求的 `questions` 为空时，从同一次返回的 `interaction` 读取请求理由、命令、文件变更或权限事项。`kind` 为 `question_set` 时调用 `GetMessage` 读取这条消息里的问题组。读不到时这条提醒按“读取失败”处理，不发、不作废。

**有效与复核。** 某一项出现在 Mailbox 的最新完整读取结果中，就表示它仍然有效：@ 未读、未撤回、仍可访问；问题仍在等待，并且这位用户仍是收件人。

- **发送前复核**：发出前，以用户身份完整读取 `GetMailbox`，确认这一项仍在其中。发现提醒后立即发送的同一次回调可复用刚读到的完整快照，时限从完整读取返回时计算，不足 2 秒才复用；超过时限、排队后再发、重试或另一进程发送均重新读取。绑定、开关、已发状态仍在发送锁内复核，缓存不跨进程或持久化。Telepus 不调用 `GetChatroom` 或 `GetResidentRequest` 重新判断有效状态；读取原消息和问题接口只用于生成提醒内容。
- **读取失败**：读取失败时，这一轮什么都不发、什么都不作废，也不把任何一项当作已处理，下一轮重试。
- **字段缺失**：结果中没有 `pending_requests` 字段时，暂停这一类扫描。这和“读到了空列表”不同：缺字段时不建立基线，不作废，也不发。

**基线（开启之前的旧事）。** 基线是“开始提醒时已经存在、不再提醒”的那批项，不依赖 Mailbox 给出的时间。每一类提醒各有一条基线，建立的时机是：

- 对于已经支持的类别，开启操作先完整读取 `GetMailbox` 快照，再在同一事务里保存开关和这份快照的基线，提交成功后才返回开启成功。读取失败时开关保持原状；快照读取后到提交之间，以及开启成功后到首次扫描之间出现的新项，都由后续差异比较进入待发；
- “待我回答”的开关如果在 `pending_requests` 出现之前就打开了，基线推迟到第一次真正读到 `pending_requests` 字段时再建。这样投影上线时，已经积压的旧问题不会一下全部补推。

基线建立时，快照里已有的项记为“开启前已有”，之后新出现的项才进入待发。基线一类只建一次：服务重启、监听重连或 `snapshot_required` 时不重建，而是把完整快照与发送记录比较，所以离线期间真正新增的项照常提醒。关掉再打开开关时，重新建立基线。

### 与已有手机问答去重

Telepus 已经会把个人助手门面回复里的问题组作为问答卡片发到微信（decision_e1f177f05e4c“问答卡片”）。同一个问题不发两次：问题提醒和问答卡片都按问题的稳定来源键记录，门面展示的投影也换算到同一个来源键。某个来源的问答卡片已经确认发送成功，就不再为它发提醒；反过来，已经发出提醒的问题，之后照常可以作为问答卡片出现在对话里。去重只按问题来源判断，不会因为用户在用手机对话就跳过整个个人助手或所有手机会话的提醒。

## 发现与去重

回复刷新服务（`telepus-portal-refresh`）为每位“绑定状态为 `active`、至少开启了一类提醒”的用户维持一个 Mailbox 监听：

1. 以该用户本人身份长等待调用 `WatchMailbox(user_id, timeout_seconds=25)`，有变化时立即返回，保存返回的游标后马上发起下一次等待。返回 `snapshot_required` 或首次启动时，用 `GetMailbox` 重读整个 Mailbox。每位用户一个常驻监听，监听数量随开启提醒的用户数增长，不受固定线程池大小限制。
2. 读到完整结果后，取出 `unread_mentions` 和 `pending_requests`，按“读取的字段”中的规则为每一项生成提醒键。
3. 提醒键不在发送记录中（包括“开启前已有”），就写入发送记录，状态为“待发”，并立即把这位用户放入微信待发队列、唤醒微信适配层发送。读取不完整时跳过这一步。

发送记录按提醒键唯一，保存在桥接库。服务重启、监听重连或 Mailbox 重读后，同一件事不会再提醒一次。

### 时效

从聊天室里出现 @、或问题开始等待，到微信发出提醒，正常情况下不超过 5 秒。这段时间由三步组成：Mailbox 监听返回变化，Telepus 读一次 `GetMailbox` 和需要的原消息，微信适配层发出。任何一步都不设固定等待：监听用长等待代替短轮询，发现后立即入队，发送不等合并窗口。每条发送记录保存发现时间和发出时间，用来核对实际耗时；额度不够、没有 `context_token` 时的延迟不计入这一目标。

## 发送

### 发送前复核

每条提醒在真正发出前都要复核。先确认三件事：用户的微信绑定仍为 `active`，该类提醒仍开启，并且没有为同一来源发过成功的提醒或问答卡片。然后以用户身份完整读取 Mailbox（发现后的即时发送可在不足 2 秒内复用快照），见“读取的字段”中的“有效与复核”。两类提醒失效的条件不同，都由 Mailbox 投影反映：

- **@**：已读、撤回、@ 被编辑掉，或用户已不能访问这个聊天室时失效，表现为这条 @ 不再出现在 `unread_mentions` 中。
- **问题**：已回答、已取消、已失效，或这位用户不再是它的收件人时失效，表现为它不再出现在 `pending_requests` 中。用户读过那段对话并不等于回答了问题，所以不能据此作废问题提醒。

失效的提醒标为“已作废”，不发。读取失败或分页没读完时不发、不作废，留待下一轮再试。

### 内容

提醒是一条短消息，按微信格式规则排版：

- **@**：第一行 `🔔 **<发言人>** 在 **<聊天室名>** 里 @了你`；第二行是这条消息的摘录，按可见文字取前 120 个字，超出部分用“…”结尾，图片和文件写成“[图片]”“[文件 <名称>]”；第三行提示“引用这条消息回复，会以你的名义发到聊天室”。发言人是用户时写用户名，是 Resident 时写 Resident 标题。
- **问题**：第一行 `❓ **<Resident 名>** 在等你回答`；下面逐个列出问题，每个问题写标题（取前 120 个字），有选项时在下一行列出选项文字，批准请求写出要批准的事项；一次最多列 3 个问题，其余写“另有 N 个问题”；问题编号从 1 开始，选项写成 `1. <选项>`；最后一行提示“引用这条消息回答”，并给出回答格式的一句示例（一个问题回选项序号或文字；多个问题每行一个“<问题序号> <答案>”；批准请求回“同意”或“拒绝”）。超过 3 个问题、只列出一部分时，提示改为“问题较多，请回 Portal 回答”，这条提醒不接受微信回答。

个人助手门面回复里的问题组仍按现有的微信问答卡片处理；本节的问题提醒覆盖其他 Resident 发给用户的问题和批准请求。

摘录和问题内容只发给这位收件用户，他在 Portal 里本来就能读到。日志、审计和桥接库都不保存摘录、问题和正文。

### 在微信里回复聊天室 @

用户在微信里引用一条 @ 提醒并发出文字，Telepus 把这段文字以用户本人身份发到对应聊天室，并引用被 @ 的那条消息，在 Portal 中显示为普通的引用回复。

1. **找到目标。** 每条 @ 提醒发出后，Telepus 把微信返回的消息 ID 登记到这条提醒的发送记录上。用户引用回复时，先按引用标识查找（与 decision_e1f177f05e4c“引用”相同：`svr_id`，没有时取 `message_item.msg_id`），找不到再按引用摘录在本用户的 @ 提醒中唯一匹配。命中一条 @ 提醒时，按聊天室回复处理；没有命中时，按原有的引用规则交给个人助手门面或被引用的成员。
2. **发出。** 调用 `CreateChatroomMessage(chatroom_id, content_parts, quote={message_id})`，`content_parts` 为用户发来的文字；同条消息里的图片先作为本聊天室附件上传再一起发出，上传不支持时只发文字，并在回执里说明图片没有带上。正文里的 `@resident_<ID>` 照常投递给对应 Resident。
3. **回执。** 成功后在微信回一句“✅ 已发到 **<聊天室名>**”，失败时说明原因（没有发言权限、聊天室已删除、网络错误），不改发到别处。
4. **已读。** 发言成功后，Portal 按聊天室已有规则处理这位用户的已读状态；Telepus 不另外调用 `MarkChatroomRead`。

只有逐条发出的 @ 提醒可以这样回复。多条合并成的汇总不对应单一聊天室，引用汇总回复时，Telepus 回一句提示，请用户在 Portal 中回复，或等下一次逐条提醒；这段文字不转给个人助手。

### 在微信里回答问题

用户在微信里引用一条问题提醒并发出文字，Telepus 把这段文字解析成答案，以用户本人身份提交，效果与在 Portal 里点选作答相同。

1. **找到目标。** 问题提醒和 @ 提醒一样，发出后把微信返回的消息 ID 和引用摘录指纹登记到发送记录上。用户引用回复时，先按引用标识查找，再按摘录在本用户的问题提醒中唯一匹配。命中问题提醒时按回答处理；引用的是汇总或列不全问题的提醒时，回一句“请回 Portal 回答”，这段文字不转给个人助手；没有命中时，走原有引用路由。
2. **确认仍待回答。** 提交前以用户身份重新读取这条请求：原生工具问题和批准请求调用 `GetResidentRequest`；消息问题组（`question_set`）调用 `GetMessage`，按消息里问题组的状态和回答位判断，与网页一致。已经回答、已取消或已过期时，回“这个问题已经处理过了”，不再提交。
3. **解析答案。**
   - 一个问题：回复是选项序号或与某个选项文字完全一致时，取这个选项；问题允许自由填写时，其余文字作为自由答案；不允许自由填写又对不上选项时，不提交，回执列出可选项。
   - 多个问题：每行一个 `<问题序号> <答案>`，每行按单个问题的规则解析。缺少任何一个问题的答案或有一行解析不了时，整组都不提交，回执说明缺哪一题或哪一行有误。
   - 批准请求：“同意”“批准”“通过”“可以”“yes”“y”视为批准；“拒绝”“不同意”“不行”“no”“n”视为拒绝；其他文字不提交，回执给出这两个选项。
4. **提交。** 使用 Portal 网页回答这类请求时的同一正式入口，以用户本人身份提交，不另建写入路径。权限、重复提交和 Resident 唤醒都由这个入口处理。
   - 原生工具问题：`AnswerResidentRequest`，按问题 ID 给出 `answers`。
   - 原生批准请求：`AnswerResidentRequest`，`action` 为 `accept` 或 `decline`。
   - 消息问题组：`DeliverMessage` 发给提问的 Resident，携带问题组回答（`async_question_answer`）、原问题的 `source_message_id` 和正式的 `answer_message_id`。
   - 含权限请求的问题组：同意就要把用户的权限交给 Resident。微信提醒列不全要交出哪些权限，所以这类问题组不在微信里回答，提醒写“这个问题要授权，请回 Portal 回答”，引用回复只回同样的提示。
5. **回执。** 正式入口只确认异步受理、尚未确认答案入库时，提示等待确认，不宣称已回答；网络中断造成结果未知时请用户回 Portal 核对，避免重复提交。成功后回 `✅ 已回答 **<Resident 名>**`，附上解析出的答案摘要，便于用户核对；失败时说明原因（问题已处理、无权回答、格式不对、网络错误），不转发到别处。

答案正文只在提交请求里出现，日志、审计和桥接库都不保存。

### 不带链接

提醒不附 Portal 链接。微信内置浏览器会拦截未备案的域名，用户在公司又多用内网地址，链接经常打不开，留着只会占篇幅。@ 提醒在微信里就能看懂并直接回复；需要回 Portal 时，用户从 Portal 的 Mailbox 进入。

### 额度

微信限制用户两次发言之间机器人能发的条数（见 decision_e1f177f05e4c“发送额度”）。提醒的使用规则：

- 提醒进入微信适配层的待发队列，排在已有回复之后，不占用最后那条预留的“还有 N 条回复”提示位。
- **合并。** 合并只改变发送的条数，不丢掉任何一项。同一来源重复发现时，只保留一条待发记录。提醒发现后立即发送，不设合并等待；只有发送那一刻已经同时待发的多项才放在一起处理。一批不超过 3 条且额度够用时逐条发出，这样每条 @ 提醒都能直接引用回复；超过 3 条或额度不够逐条发时，发一条汇总：“🔔 你有 N 条提醒”，下面逐条列出发言人、聊天室和摘录（问题列出 Resident 名和问题标题摘录），每批最多列 5 条，只有本批实际展示的来源在确认发送成功后记为已发；未展示的项继续待发，提示“另有 M 项待发送，将继续分批提醒”，下一批仍按回复优先和额度规则发送。
- **额度不够时暂停并提示。** 本轮额度只剩最后一条、而复核后仍有有效的待发提醒时，用这最后一条发一句暂停提示：“⏸ 微信提醒已暂停：机器人连续发送已达上限。回复任意消息即可继续接收，期间的提醒会合并补发。”这最后一条由回复和提醒共用：回复路径已经发出“还有 N 条回复”时不再发暂停提示，反之亦然，所以每次入站之后最多发一条额度提示。提示发出后额度用尽，提醒留在队列中，不再发送；复核时已没有有效提醒的，不发提示。没有 `context_token` 时不发提示。暂停提示返回 `ret=-2` 时标记阻塞，不重试。
- **恢复补发。** 用户下一条消息到达、额度重置后，先补发待发回复，再补发提醒：发出前照常复核，已失效的作废；仍有效的不超过 3 条且额度够用时逐条发，否则发汇总。
- 网络错误按普通失败退避重试，不当作额度用完。

提醒发出后，Portal 中的已读状态不变。用户在微信里看到提醒，不等于在 Portal 里读过。

## 权限

Telepus 以绑定的用户本人身份、带微信渠道来源调用 `WatchMailbox`、`GetMailbox`、`ListChatroomMessages`、`CreateChatroomMessage`、`GetResidentRequest`、`GetMessage`、`GetInputState` 以及网页回答请求所用的正式入口，不使用服务身份或管理员身份读取别人的 Mailbox 或代人发言。在聊天室发言要求用户对该聊天室持有 `@contributor`，与网页发言相同。`WatchMailbox` 与 `GetMailbox` 要求调用者对目标 User 持有 `@admin`；权限模板中本人对自己的账号节点（`account_self`）有这一项。权限验证使用隔离环境的两个 User、真实 ISA kernel 和默认权限方案，确认本人可读、访问另一 User 被拒绝；Mailbox 后端使用合成数据。线上仅检查服务健康、注册 schema 与静态入口，不使用真实用户 token、不读取真实用户 Mailbox、不外发测试消息。读不到时修正权限方案，不在 Telepus 中绕过。聊天室调用也通过真实 kernel 验证：当前默认方案的 `everyone_reads` 允许非成员读取共享聊天室；成员可以发言，非成员没有额外授权时不能发言。显式拒绝读取时 kernel 阻止访问。Telepus 沿用该方案，不附加独立的成员限制。

## 桥接数据

| 表 | 内容 |
| --- | --- |
| `notification_preferences` | Portal 用户、提醒类别、是否开启、开启时间 |
| `notification_deliveries` | 提醒键、用户、类别、来源 ID、状态（开启前已有、待发、已发、已作废）、发现时间、发出时间、作废原因，以及逐条发出的 @ 提醒在微信中的消息 ID |
| `meta` | 每位用户的 Mailbox 监听游标 |

当前桥接 schema 为 11。版本 9 启动时建立两张提醒表；10→11 在同一事务内持有 advisory lock，只为 `notification_deliveries` 增加 `external_message_id`（TEXT）、`quote_fingerprints`（JSONB）和 `is_summary`（BOOLEAN）列，保留已有记录。偏好中的 `baseline_ready` 保存每类基线是否已建立，投递记录同时保存确认发出的问答卡片来源。提醒正文和摘录仅在发送时构建，不写入桥接库；引用匹配持久保存可见文本的 SHA-256 指纹，按绑定用户隔离，完整提醒或摘录指纹恰好匹配一个来源时才采用。关闭开关保留已发提醒的引用对应，解绑时清除。基线完成只在首次建立时写入；重复扫描不更新已为真的标志。持久游标和重试恢复字段只在值实际变化时保存，静态状态不会为了表示观察过而重写。三十秒兜底读取的节拍只保存在进程内存，进程重启先完整重读 Mailbox，再沿持久游标监听；不为兜底计时频繁更新数据库。 监听因提醒关闭或绑定失效而退出时，清除该用户的本地读取节拍与即时快照；变更来自另一进程、或在网络读取成功/失败期间发生时，同样回收。其他用户的监听和持久发送记录不受影响。

## 代码位置

- `question_answer.py` 处理问题提醒引用：先完整读取用户 Mailbox 复核收件关系，再读取原生请求或消息问题组。消息问题组通过 `GetMessage`、`GetInputState` 检查正式回答位，沿网页的 `DeliverMessage` 提交 `async_question_answer`；原生问题和批准沿 `AnswerResidentRequest`。权限问题组返回 Portal 提示，不申请或签发凭证。`weixin_adapter._private_receipt` 在内存中发送答案摘要和解析错误，避免进入持久外发队列；发送异常只保留安全错误类别。`test_telepus_question_answers.py` 覆盖解析、幂等、状态竞态、读取与发送失败，以及完整回答流程经过真实 kernel 默认权限时本人通过、另一用户在读取复核被拒绝。

- [`notifications.py`](https://github.com/EatonZhou/the-fourth-institute/blob/main/code/management_portal/telepus/notifications.py)：负责偏好、持久基线、监听游标、提醒键、发送复核与分批合并。验证入口为 `tests/cases/test_telepus_notifications.py`，覆盖真实 ISA kernel 与默认 `account_self` 权限，以及模拟 Mailbox/iLink 的生命周期；界面验证为 `tests/cases/javascript/telepus_weixin_binding.cjs`。
- `refresh_service.NotificationScheduler` 为每位开启提醒的用户运行一个常驻长等待线程，不受固定线程池数量限制，独立于普通回复刷新。每次 WatchMailbox 最长等待 25 秒；接近 30 秒完整读取期限时缩短等待。断线沿持久游标与退避恢复，不重建基线。完整 Mailbox 网络读取在用户发送锁之外进行；取得锁后再核对绑定、开关、去重并提交扫描结果。发现待发记录后，直接使用同进程微信适配器，在既有跨进程用户锁下刷新持久队列。
- `weixin_adapter` 负责入队与额度：额度充足且一批不超过三项时逐条发出，否则最多五项汇总；只有成功发出的那组来源记为已发，失败的余项沿原队列重试。接收引用时优先查提醒的微信服务端 ID，再查同用户的文本指纹；汇总引用只返回说明。
- `mention_reply.py` 通过用户 ISA 客户端分页读取原消息、提取作者和摘录，并调用 `CreateChatroomMessage` 携带原消息 `quote`，幂等键来自绑定和微信输入 ID。`chatroom_reply` 仅记聊天室、结果与安全原因。回归入口 `tests/cases/test_telepus_mention_reply.py` 使用合成 Mailbox、Chatroom 和 iLink，覆盖失败、歧义、分页、重试、权限及正文不进入日志/桥接库。
- 当前 Telepus ISA 传输没有已认证的附件字节上传通道，聊天室引用回复采用文本降级：带图片/文件只发文字并在回执说明附件未发送；纯附件不产生空发言，提示补文字或回 Portal。
- `weixin_format.notification_text` 生成无链接提醒，保留发言人、聊天室、摘录与问题来源；源摘录中的链接也去除，其可见文本用于引用指纹。提醒不再读取公网地址配置。
- 扫描与发送耗时属于瞬时诊断，不写入数据库，也不把每次扫描改为文件日志。`notification_scan`、`notification_latency` 不再作为审计事件生产；已有这两类记录可按明确事件类型清理。时效由隔离 Mailbox/iLink 测试直接观察事件到达、实际读取次数及发送完成边界；发送状态、引用对应、去重和业务失败回执保留。异常诊断只按已有退避节拍输出安全错误类别。
- `question_reminder.py` 以收件 User 身份读取 Mailbox 给出的可见对话与消息，保留稳定来源 ID 用于去重；通过统一问题组解析器读取消息内问题，内容仅在发送内存中使用。`weixin_format.notification_text` 展示问题标题、选项和批准事项。验证入口 `tests/cases/test_telepus_question_reminders.py` 覆盖三类问题、读取失败保留待发、内容不落库和真实 kernel 默认权限。
- `weixin_http.py` 在线程内复用有界 HTTPS 长连接，逐请求带当前账户请求头；支持 HTTP 代理隧道，HTTPS 代理沿已有传输。失败丢弃连接，由原队列重试，不在传输层自动重放 POST。Web 重启关闭监听连接时，`instruction.owner_unavailable` 短暂退避并保留游标，持续失败后报告；权限错误不静默。
- `/notify` 命令放在微信呈现层，`/help` 的“命令”分组补上这一项。
- 两项设置工具由 telepus/tools.py 声明并执行，引用 application:telepus.weixin_notifications_read、application:telepus.weixin_notifications_update，与绑定工具共用目标 User 校验。
- 两个开关加在 Watchboard 应用 `static/watchboard_applications/telepus.js` 的微信绑定行上，新文字加入 `translations/telepus.json`。

## 失败与恢复

| 情况 | 表现 | 处理 |
| --- | --- | --- |
| 额度只剩最后一条且有有效待发提醒 | 发一次暂停提示，提醒留在队列 | 用户下次发消息后复核补发：逐条或汇总，失效的作废 |
| 额度用完、无 `context_token` 或 `ret=-2` | 提醒留在队列，不再提示 | 用户下次发消息后复核补发 |
| 发送前已读、已答、已撤回或失去访问 | 不发 | 标为已作废 |
| Mailbox 监听断开或服务重启 | 暂不发现新提醒 | 从保存的游标续读，需要时重读快照；按提醒键去重 |
| 用户本人读不到自己的 Mailbox | 不发提醒，记录脱敏诊断 | 修正权限方案 |
| 绑定失效（`-14`） | 停止监听与发送 | 重新绑定后需要重新开启提醒 |
| 回复 @ 时没有发言权限或聊天室已删除 | 不发到聊天室 | 微信里告知原因，不转发到别处 |
| 回答问题时问题已处理、无权回答或格式不对 | 不提交 | 微信里告知原因和正确格式，不转发到别处 |

微信回复聊天室成功或失败都记一条 `chatroom_reply` 审计，只含聊天室 ID、结果和失败原因，不含正文。微信回答问题记一条 `question_answer` 审计，只含 Resident ID、请求消息 ID、结果和失败原因，不含问题和答案。
